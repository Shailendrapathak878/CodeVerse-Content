Sealed Classes & Advanced Type Modeling in Kotlin

Design bulletproof, type-safe domain models. Learn how Sealed Classes and Sealed Interfaces restrict class hierarchies so the compiler knows all possible states, eliminating else branches in when expressions and preventing invalid application states.

1 Understanding Sealed Classes: What & Why?

In standard object-oriented programming, any class marked open can be inherited by an unlimited number of unknown subclasses anywhere in your project.

A Sealed Class represents a restricted class hierarchy. All direct subclasses of a sealed class are known at compile time. No unknown third party can create new subclasses outside your defined package/module.

🚦
Real-Life Analogy: The Traffic Signal.
A traffic light has a strictly closed set of possible states: Red, Yellow, and Green. A random driver cannot suddenly invent a "Purple" signal light. A Sealed Class models this closed universe: every state is known and accounted for!

2 Exhaustive when Expressions (No else Needed!)

The greatest superpower of a sealed class is its synergy with the when expression. Because the Kotlin compiler knows every possible subclass, it can verify that your when expression covers 100% of the cases.

Diagram 2.1: Compiler Guarantees All Cases Are Handled
💡
Why omit the else branch? If you use an else branch, you lose compile-time safety! When a teammate adds a new state tomorrow (like Cancelled), the compiler won't warn you—it will silently run the default else code. Without else, the compiler forces you to handle the new state immediately!

3 Practical Sealed Classes (Examples 1 – 10)

Examples 1 – 4: Basic Sealed Class with Exhaustive when

Kotlin SealedClassBasic.kt
KOTLIN Script
KOTLIN 
sealed class Shape {
    class Circle(val radius: Double) : Shape()
    class Rectangle(val width: Double, val height: Double) : Shape()
    object Point : Shape() // Singleton object state!
}

fun computeArea(shape: Shape): Double = when (shape) {
    is Shape.Circle -> 3.14159 * shape.radius * shape.radius
    is Shape.Rectangle -> shape.width * shape.height
    Shape.Point -> 0.0
    // No 'else' branch needed: all Shape subclasses are handled!
}

fun main() {
    val c = Shape.Circle(4.0)
    val r = Shape.Rectangle(3.0, 5.0)
    println("Circle Area: ${computeArea(c)}")
    println("Rect Area: ${computeArea(r)}")
}
Terminal Output Circle Area: 50.26544
Rect Area: 15.0

Example 5: Payment Processing States

Notice how each subclass can carry distinct data (e.g. transactionId, errorCode) or no data at all.

Kotlin PaymentStatusDemo.kt
KOTLIN Script
KOTLIN 
sealed class PaymentStatus {
    object Pending : PaymentStatus()
    data class Success(val txnId: String, val amount: Double) : PaymentStatus()
    data class Failed(val reason: String, val errorCode: Int) : PaymentStatus()
}

fun renderPayment(status: PaymentStatus) = when (status) {
    PaymentStatus.Pending -> println("⏳ Awaiting bank gateway confirmation...")
    is PaymentStatus.Success -> println("✅ Paid \$${status.amount} (Txn: ${status.txnId})")
    is PaymentStatus.Failed -> println("❌ Error [${status.errorCode}]: ${status.reason}")
}

fun main() {
    renderPayment(PaymentStatus.Pending)
    renderPayment(PaymentStatus.Success("TXN_9482", 49.99))
    renderPayment(PaymentStatus.Failed("Insufficient funds", 402))
}
Terminal Output ⏳ Awaiting bank gateway confirmation...
✅ Paid $49.99 (Txn: TXN_9482)
❌ Error [402]: Insufficient funds

4 Advanced Type Modeling: Eliminating Invalid States

Beginner developers often use "Boolean flag soup" to manage application states: var isLoading = false; var data: String? = null; var error: String? = null;.

This leads to dangerous impossible states (e.g., what if isLoading == true AND error != null AND data != null at the same time?). Type Modeling solves this by making impossible states unrepresentable in code!

Examples 11 – 14: Real-World Order Tracking State Machine

sealed class OrderStatus {
    data class Placed(val orderId: String, val timestamp: Long) : OrderStatus()
    data class Shipped(val trackingNumber: String, val carrier: String) : OrderStatus()
    data class Delivered(val signedBy: String) : OrderStatus()
    object Cancelled : OrderStatus()
}

fun printOrderStatus(status: OrderStatus) = when (status) {
    is OrderStatus.Placed -> println("Order #${status.orderId} received.")

    OrderStatus.Cancelled -> println("Order was cancelled.")
}

fun main() {
    val current = OrderStatus.Shipped("TRK-9021", "BlueDart Express")
    printOrderStatus(current)
}

Examples 19 & 20: Media Playback State Modeling

Kotlin MediaPlaybackDemo.kt
KOTLIN Script
KOTLIN 
sealed class Playback {
    object Stopped : Playback()
    data class Playing(val title: String, val positionSec: Int) : Playback()
    data class Paused(val title: String, val positionSec: Int) : Playback()
}

fun main() {
    val states: List = listOf(
        Playback.Stopped,
        Playback.Playing("Kotlin Symphony", 45),
        Playback.Paused("Kotlin Symphony", 45)
    )

    for (s in states) {
        when (s) {
            Playback.Stopped -> println("⏹ Player idle")
            is Playback.Playing -> println("▶ Playing '${s.title}' at ${s.positionSec}s")
            is Playback.Paused -> println("⏸ Paused '${s.title}' at ${s.positionSec}s")
        }
    }
}
Terminal Output ⏹ Player idle
▶ Playing 'Kotlin Symphony' at 45s
⏸ Paused 'Kotlin Symphony' at 45s

6 Common Beginner Mistakes & How to Fix Them

❌ 1. Adding unnecessary 'else' in sealed when

when(state) { ... else -> Unit } // Silences compiler warnings!

Fix: Omit else so the compiler alerts you whenever a new state is introduced.

❌ 2. Trying to instantiate a Sealed Class

val s = ScreenState() // Error: Cannot create instance of sealed class

Fix: Instantiate a concrete subclass: ScreenState.Success(...).

❌ 3. Using Enum when states need different data

Enums force all entries to have the exact same constructor fields.

Fix: Use a sealed class so Success has data while Loading has none.

❌ 4. Subclassing outside allowed module

Subclasses must be declared in the same package and compilation module.

Fix: Keep all subclasses inside the package where the sealed class is declared.

❌ 5. Forgetting 'data' keyword on state class

class Success(val user: User) : State() // Missing equals/hashCode

Fix: Use data class Success(...) for automatic structural equality.

❌ 6. Using mutable boolean flag soup

Managing isLoading, isError, isSuccess flags creates invalid overlaps.

Fix: Model states with a sealed class to guarantee mutually exclusive truth.

7 Quick Revision: 12 Key Takeaways

  • 1. Sealed Class: A restricted class hierarchy where all direct subclasses are known at compile time.
  • 2. Exhaustive 'when': The compiler knows every subclass, so no else branch is required.
  • 3. Future Proofing: Adding a new subclass forces you to handle it in every when expression.
  • 4. Non-Instantiable: Sealed classes are abstract by default and cannot be instantiated directly.
  • 5. Varied Data: Unlike Enums, subclasses of a sealed class can have completely different properties.
  • 6. Singleton States: Use object or data object for states that carry no data (e.g. Loading, Idle).
  • 7. Data States: Use data class for states carrying payloads (e.g. Success(data), Error(msg)).
  • 8. Sealed Interfaces: Allows classes to participate in multiple sealed hierarchies and enables Enum integration.
  • 9. Type Modeling: Designing types so that impossible or illegal application states cannot be represented.
  • 10. Package Boundary: Direct subclasses must be in the same package and compilation unit.
  • 11. Pattern Matching: when (res) { is Success -> ... } automatically smart-casts res to Success!
  • 12. Industry Standard: Sealed classes are the foundation of state management in Android and Jetpack Compose.

✖ D) Enums can only hold String values, while sealed classes can only hold numbers
Explanation: Sealed classes are an extension of enum concepts: each state in a sealed hierarchy can be a distinct class with its own customized fields and methods.
2. Why is omitting the `else` branch in a sealed class `when` expression recommended?
✔ A) Because if a new subclass is added later, the compiler will trigger an error reminding you to handle it
✖ B) Because the else branch slows down execution on mobile processors
✖ C) Because Kotlin 2.0 has deprecated the else keyword entirely
✖ D) Because sealed classes cannot execute code inside an else branch
Explanation: Omitting else ensures compile-time exhaustiveness: adding a new subclass forces you to explicitly handle the new state everywhere.
3. Where must direct subclasses of a sealed class be declared?
✔ A) In the same package and module as the sealed class itself
✖ B) In any package across any library jar
✖ C) Strictly nested inside the sealed class body only
✖ D) Inside a companion object
Explanation: In modern Kotlin, direct subclasses of a sealed class can be top-level or nested, provided they reside in the same package and compilation module.
4. How should a state that carries no parameters (like `Loading` or `Idle`) be represented inside a sealed class?
✔ A) As an `object` or `data object` singleton declaration
✖ B) As an empty function pointer
✖ C) As a private constructor parameter
✖ D) As a nullable String property
Explanation: States without parameters don't need multiple instances; using a singleton object avoids allocating duplicate objects in memory.
5. Can an enum class implement a `sealed interface` in Kotlin?
✔ A) Yes, enum classes can implement sealed interfaces
✖ B) No, enums can only implement standard non-sealed interfaces
✖ C) Only if the enum has zero constant values
✖ D) Only if the sealed interface has a constructor
Explanation: One major benefit of sealed interfaces is that enum classes can implement them, enabling flexible hybrid type hierarchies.
