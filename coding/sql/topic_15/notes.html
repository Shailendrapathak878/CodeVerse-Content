Normalization & Relational Design

Organize database tables systematically to eliminate redundant data, ensure consistency, and prevent update anomalies.

A The Problem with Unnormalized Data

Normalization organizes database columns and tables to reduce unnecessary data duplication and prevent insert, update, and deletion anomalies.

Consider this unnormalized college enrollment table:

student_id student_name branch course
101 Rahul Repeated CSE Repeated SQL
101 Rahul Repeated CSE Repeated Python
102 Priya AI SQL

Rahul's name and branch are repeated for every enrolled course. If Rahul switches branches, updating one row while missing another creates conflicting records (an update anomaly).

The Normalization Steps (1NF → 2NF → 3NF)
1NF — Atomic Values
Each column holds a single, indivisible value per cell (never comma-separated lists like "SQL, Python"), and each row is unique.
2NF — No Partial Dependency
Must satisfy 1NF, and all non-key columns must depend on the entire candidate key, rather than only part of a composite key.
3NF — No Transitive Dependency
Must satisfy 2NF, and non-key columns must depend strictly on the primary key, never on other non-key attributes (e.g., branch names depend on branch_id).

B A Better Relational Design

We split the unnormalized table into three dedicated entities with distinct responsibilities: students, branches, and enrollments.

Each table manages its own domain. student_id and branch_id connect related records. The Enrollments table represents the student-course relationship using a composite primary key (student_id, course).

Normalized Schema Definition 3NF SCHEMA 
CREATE TABLE Branches (
    branch_id INT PRIMARY KEY,
    branch_name VARCHAR(30) NOT NULL UNIQUE
);

CREATE TABLE Students (
    student_id INT PRIMARY KEY,
    student_name VARCHAR(50) NOT NULL,
    branch_id INT,
    FOREIGN KEY (branch_id)
        REFERENCES Branches(branch_id)
);

CREATE TABLE Enrollments (
    student_id INT,
    course VARCHAR(50),
    PRIMARY KEY (student_id, course),
    FOREIGN KEY (student_id)
        REFERENCES Students(student_id)
);

◆ Visual 2: Relational Keys & Table Relationships

↓ One-to-Many Relationship: Branches.branch_id → Students.branch_id
Students Table: PK student_id • student_name • FK branch_id Connected via branch_id
↓ One-to-Many Relationship: Students.student_id → Enrollments.student_id
Enrollments Table: PK (student_id, course) • FK student_id Composite Primary Key
★ Quick Revision & Takeaways

1. Goal: Store each piece of data in exactly one place.
2. Keys as Links: Foreign keys reference primary keys to reconstruct relationships when queried with JOINs.
3. Integrity: Normalization eliminates update, insertion, and deletion anomalies.
