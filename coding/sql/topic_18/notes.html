Transactions & ACID Properties

Ensure reliable data updates, manage multi-step operations safely with COMMIT and ROLLBACK, and master the four ACID guarantees.

A What Is a Transaction?

A transaction is a group of database operations treated as one logical unit of work.

Real-Life Example: When a student pays college fees or transfers money between accounts, the payment record should be saved correctly. If part of the operation fails, the database should not be left in an inconsistent state.

Initial Accounts Table
account_id student_name balance
101 Rahul 5000
102 Priya 3000
Transferring Money with a Transaction

The following syntax is broadly supported, but transaction behavior and exact syntax can vary by database:

Transfer Transaction SQL 
BEGIN;

UPDATE Accounts
SET balance = balance - 1000
WHERE account_id = 101;

UPDATE Accounts
SET balance = balance + 1000
WHERE account_id = 102;

COMMIT;

This example transfers ₹1,000 from Rahul to Priya. After a successful commit, expected balances are:

student_name balance
Rahul 4000
Priya 4000

Transaction control commands:

  • BEGIN starts the transaction.
  • COMMIT saves the transaction's changes.
  • ROLLBACK cancels uncommitted changes when supported by the transaction context.
Illustrative Rollback Example
Rollback Cancel ROLLBACK 
BEGIN;

UPDATE Accounts
SET balance = balance - 1000
WHERE account_id = 101;

ROLLBACK;

Rahul's balance returns to its original value of 5000 if the update was uncommitted and the rollback succeeds.

BEGIN; — Opens a new protected transaction scope.
2. Debit Sender
Rahul −₹1,000 — Pending balance: 4000.
3. Credit Receiver

✔ Success Path (COMMIT)
Both updates succeed together. COMMIT; saves changes permanently to disk.
✘ Failure Path (ROLLBACK)
If any step fails, ROLLBACK; cancels pending changes, restoring Rahul's initial 5000 balance.

B ACID Properties

To ensure reliability during concurrent operations and system crashes, transactions adhere to four core properties:

  • Atomicity: Both transfer updates succeed together, or the transaction is rolled back with no partial updates.
  • Consistency: Database rules and constraints remain satisfied before and after the transaction.
  • Isolation: Concurrent transactions should not interfere in ways that violate the database's isolation guarantees.
  • Durability: Once a transaction is committed successfully, its changes are preserved according to the database's durability guarantees.
◆ Visual 2: The Four ACID Guarantees
A Atomicity
All or Nothing: Either both the deduction and credit take place, or zero changes are applied.
C Consistency
Valid State: Balances follow business rules and cannot become invalid or corrupted.
I Isolation
Concurrent Safety: Other active transactions cannot observe partial, uncommitted balances.
D Durability
Permanent Record: Committed fee payments survive power outages and server reboots.
