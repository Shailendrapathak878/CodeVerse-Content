Topic 19: Generics & Type Constraints

Master writing flexible, reusable, and statically type-safe code using type parameters, generic functions, generic classes, and bounds.

1. Introduction to Generics (What and Why)

In programming, we frequently write algorithms that do identical work across multiple data types. Imagine writing a storage box: you could make an IntBox, a StringBox, and a UserBox. Repeating identical code for every type is tedious, error-prone, and violates the DRY (Don't Repeat Yourself) principle.

Generics solve this cleanly: they allow you to write a single function, class, or interface with type placeholders (called type parameters). When you instantiate or invoke that component, you supply the actual type, and the Dart compiler ensures strict type safety at compile time.

Figure 19.1: One generic component creates type-safe specialized variants for any type.
Core Benefit of Generics
Generics provide the ultimate balance: Maximum Code Reusability combined with 100% Compile-Time Type Safety and Zero Performance Penalty.

2. Problem Without Generics (Object / dynamic Risks)

Before generics existed in languages, developers used Object or dynamic to store any value. However, this loses all type information. You are forced to perform manual runtime type casts (using as), which can easily crash your app if someone passes unexpected data.

Figure 19.2: Object/dynamic leads to dangerous runtime casts vs Generics' compile-time safety.
unsafe_box.dartDart 3.x
DART Script
DART 
// UNSAFE: Using Object requires manual casting
class UnsafeBox {
  final Object value;
  UnsafeBox(this.value);
}

void main() {
  var box = UnsafeBox("Hello Dart");
  // Danger: Must cast manually. If someone passes an int, this crashes at runtime!
  String message = box.value as String;
  print("Extracted: ${message.toUpperCase()}");
}
Terminal Output Extracted: HELLO DART
The Danger of Manual Casts
If another developer creates UnsafeBox(42), calling box.value as String compiles without warnings but explodes at runtime with TypeError: int is not a subtype of type String. Generics catch this at compile time before your code ever runs.

3. Generic Type Parameters & Naming Conventions

By standard convention across Dart and Flutter, type parameter names are written as single uppercase letters. Each letter signifies a specific semantic role:

Figure 19.3: Standard Dart naming conventions for generic type parameters.
Symbol Semantic Meaning Typical Examples
T Type (general purpose) Box<T>, T getValue<T>()
E Element (items inside collections) List<E>, Set<E>, Queue<E>
K, V Key and Value Map<K, V>, Pair<K, V>, Cache<K, V>
R Return type R Function<T, R>(T input)

4. Generic Functions (<T>)

A generic function declares one or more type parameters directly after the function name. This tells Dart: "Whatever type the caller passes in, preserve that exact type throughout the function's return value and logic."

Figure 19.4: Anatomy of a generic function in Dart.
generic_functions.dartDart 3.x
DART Script
DART 
// Generic function: works with ANY type T
T getFirst(List items) {
  if (items.isEmpty) {
    throw StateError("List cannot be empty");
  }
  return items.first;
}

void main() {
  // 1. Explicit type arguments
  int firstNum = getFirst([10, 20, 30]);
  
  // 2. Inferred type arguments (Dart figures out T = String automatically)
  String firstWord = getFirst(["Dart", "Flutter", "Generics"]);
  
  print("First Number: $firstNum");
  print("First Word: $firstWord");
}
Terminal Output First Number: 10 First Word: Dart

6. Generic Classes (e.g., Box<T>, Pair<T, U>)

A generic class defines a reusable blueprint where fields, getters, setters, and method parameters all operate on the generic type T. You specify the type argument upon instantiation, or let Dart infer it.

9. Type Constraints with `extends` (<T extends num>)

Sometimes, an unconstrained generic <T> is too broad. If you want to write a mathematical function, you cannot call addition + or comparisons < on an arbitrary T because strings or booleans don't support numeric operations.

To restrict allowable types, use the extends keyword in the type parameter declaration: <T extends num>. This restricts T strictly to num, int, or double.

Figure 19.9: Type bounds restrict T to num and its subclasses int and double.
bounded_clamp.dartDart 3.x
DART Script
DART 
// T is constrained to num, allowing  operators
T clampValue(T val, T min, T max) {
  if (val  max) return max;
  return val;
}

void main() {
  int boundedInt = clampValue(15, 0, 10);
  double boundedDouble = clampValue(2.4, 5.0, 10.0);

  print("Bounded Int (15 -> 0..10): $boundedInt");
  print("Bounded Double (2.4 -> 5.0..10.0): $boundedDouble");

  // clampValue("hello", "a", "z"); // COMPILE ERROR: String does not extend num!
}
Terminal Output Bounded Int (15 -> 0..10): 10 Bounded Double (2.4 -> 5.0..10.0): 5.0

10. Custom Class Hierarchy Constraints (<T extends Animal>)

Type constraints work with your own custom classes and abstract interfaces. When you constrain <T extends Animal>, the Dart compiler guarantees that any instance of T contains all methods and properties defined in Animal.

Figure 19.10: AnimalShelter accepts Dog and Cat but rejects unrelated classes.
animal_shelter.dartDart 3.x
DART Script
DART 
abstract class Animal {
  String get name;
  void speak();
}

class Dog extends Animal {
  @override final String name;
  Dog(this.name);
  @override void speak() => print("$name says: Woof! 🐶");
}

class Cat extends Animal {
  @override final String name;
  Cat(this.name);
  @override void speak() => print("$name says: Meow! 🐱");
}

// Bounded generic class
class AnimalShelter {
  final List _residents = [];
  void adopt(T animal) => _residents.add(animal);
  void callRoll() {
    for (var a in _residents) {
      a.speak(); // Compiler knows .speak() exists on T!
    }
  }
}

void main() {
  var dogShelter = AnimalShelter();
  dogShelter.adopt(Dog("Buddy"));
  dogShelter.adopt(Dog("Max"));
  dogShelter.callRoll();
}
Terminal Output Buddy says: Woof! 🐶 Max says: Woof! 🐶

12. Generics and Inheritance (ChildBox<T> extends Box<T>)

When a subclass extends a generic parent class, it has two choices:

  1. Propagate the generic parameter: class GiftBox<T> extends Box<T>
  2. Bind the parent parameter to a concrete type: class StringBox extends Box<String>

Figure 19.12: Propagating generic parameters through class inheritance hierarchies.
generic_inheritance.dartDart 3.x
DART Script
DART 
class Box {
  final T content;
  Box(this.content);
}

// Option 1: Keep it generic and forward to super
class GiftBox extends Box {
  final String ribbonColor;
  GiftBox(super.content, this.ribbonColor);

  @override
  String toString() => "GiftBox [$ribbonColor ribbon, item: $content]";
}

// Option 2: Bind parent to a concrete type
class IntCounterBox extends Box {
  IntCounterBox(super.content);
  int next() => content + 1;
}

void main() {
  var watch = GiftBox("Gold Watch", "Crimson");
  var counter = IntCounterBox(99);

  print(watch);
  print("Counter content: ${counter.content}, Next: ${counter.next()}");
}
Terminal Output GiftBox [Crimson ribbon, item: Gold Watch] Counter content: 99, Next: 100

13. Generic Type Aliases / Typedefs

Dart allows declaring type aliases for function signatures and complex types using typedef. When combined with generics, typedefs make higher-order function parameters clean, concise, and easy to read.

14. Generics and Null Safety

In Dart's sound null safety system, understanding how generic type parameters interact with null is crucial:

  • <T>: By default, T is bounded by Object?, meaning T can be instantiated as either a nullable or non-nullable type (e.g. Box<int> or Box<int?>).
  • <T extends Object>: Explicitly forbids null. The caller can only supply non-nullable types.
  • T?: Explicitly designates that the value can be null, regardless of whether T itself is nullable.

Figure 19.14: Nullable bounds vs strictly non-nullable bounds with Object.
null_safe_generics.dartDart 3.x
DART Script
DART 
// Strictly non-nullable: T cannot be int? or String?
class StrictContainer {
  final T item;
  StrictContainer(this.item);
}

// Permissive: allows null values via T?
class NullableHolder {
  final T? item;
  NullableHolder([this.item]);
  bool get hasValue => item != null;
}

void main() {
  var validStrict = StrictContainer("Clean");
  // StrictContainer(null); // COMPILE ERROR: String? doesn't extend Object

  var holder1 = NullableHolder(42);
  var holder2 = NullableHolder();

  print("Strict item: ${validStrict.item}");
  print("Holder1 hasValue: ${holder1.hasValue}, val: ${holder1.item}");
  print("Holder2 hasValue: ${holder2.hasValue}, val: ${holder2.item}");
}
Terminal Output Strict item: Clean Holder1 hasValue: true, val: 42 Holder2 hasValue: false, val: null

16. Generics Covariance in Dart (List Covariance & Runtime Safety)

In Dart, generic classes are covariant by default. This means that if Dog is a subtype of Animal, then List<Dog> is considered a subtype of List<Animal>.

While this is convenient for reading collections, it creates a subtle runtime hazard when mutating collections:

Figure 19.16: Dart covariance allows assignment, but invalid runtime mutations throw a TypeError.
covariance_demo.dartDart 3.x
DART Script
DART 
class Animal {}
class Dog extends Animal {}
class Cat extends Animal {}

void main() {
  List dogs = [Dog()];
  
  // Allowed at compile time due to covariance:
  List animals = dogs;
  
  print("Animals length: ${animals.length}");

  try {
    // Runtime failure: animals is actually backed by a List!
    animals.add(Cat());
  } catch (e) {
    print("Caught Expected Runtime Error: ${e.runtimeType}");
  }
}
Terminal Output Animals length: 1 Caught Expected Runtime Error: TypeError
Architectural Note on Covariance
If a method only reads items from a generic collection, covariance is completely safe. But if you mutate collections received as parameters, ensure the underlying collection type matches the elements being added, or use defensive copies like List.of(items).

17. Runtime Type Inspection with Generics (is T, Type)

Unlike languages with type erasure (like Java), Dart retains reified types at runtime. You can check if an object is an instance of T using is T, print T.toString(), or compare type tokens directly.

Figure 19.17: Reified types allow runtime introspection in Dart.
reified_generics.dartDart 3.x
DART Script
DART 
class Inspector {
  bool check(Object item) {
    return item is T; // Checked at runtime!
  }

  void describe() {
    print("Inspector configured for type parameter: $T");
  }
}

void main() {
  var stringInspector = Inspector();
  stringInspector.describe();
  print("Is 'Hello' a String? ${stringInspector.check('Hello')}");
  print("Is 42 a String? ${stringInspector.check(42)}");
}
Terminal Output Inspector configured for type parameter: String Is 'Hello' a String? true Is 42 a String? false

19.6 Pattern 6: Generic Event Bus / Notification Handler

Dispatching and listening to typed events in modern reactive architectures.

pattern6_eventbus.dartDart 3.x
DART Script
DART 
abstract class AppEvent {}
class UserLoggedIn extends AppEvent {
  final String username;
  UserLoggedIn(this.username);
}

class SimpleEventBus {
  final List _listeners = [];

  void on(void Function(E event) callback) {
    _listeners.add((e) {
      if (e is E) callback(e);
    });
  }

  void emit(AppEvent event) {
    for (var l in _listeners) {
      l(event);
    }
  }
}

void main() {

  bus.emit(UserLoggedIn("Sarah_Dev"));
}

20. Common Mistakes & Anti-Patterns with Generics

Figure 19.20: Avoid dangerous anti-patterns when using generics in Dart.
  • Anti-Pattern 1: Casting raw values to as T: Never do value as T without checking if (value is T). Blindly casting defeats the entire point of generics.
  • Anti-Pattern 2: Unnecessary Generics: If a class or method only ever deals with String, do not add <T> just to make it look advanced. Generics add complexity; only use them when true polymorphism across multiple types is needed.
  • Anti-Pattern 3: Forgetting Type Bounds: Writing <T> and then trying to call item.toJson() or item > 0 causes compile errors. Always constrain with <T extends DesiredClass> when specific methods are required.
  • Anti-Pattern 4: Mutating Covariant Collections: Storing a List<Cat> into a List<Animal> variable and attempting to insert a Dog crashes at runtime.

Figure 19.21: Summary of key best practice rules for Dart Generics.
Principle Rule Why
Naming Use single uppercase letters (T, E, K, V) Follows Dart style guide; clearly distinguishes type parameters from regular classes.

      .transform((n) => n * 3)            // 15 (int)
      .transform((n) => "Result is $n")  // String
      .transform((s) => s.toUpperCase()); // String
  print(result.value); // RESULT IS 15
}
