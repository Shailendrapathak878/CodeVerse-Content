Topic 20: Exceptions & Error Handling

Build robust, crash-resilient software by mastering try-catch, on-specific clauses, stack traces, custom domain exceptions, and resource cleanup.

1. Introduction to Errors

An error in programming represents any condition that prevents software from behaving as intended. When an unexpected issue strikes without proper handling, your application terminates abruptly — giving users a frustrating crash.

Real-Life Analogy (Traveling by Bus): Imagine planning a bus trip. Several distinct problems might occur:

  • No Ticket: You are barred from boarding at the station entrance (like a compile-time error before code even runs).
  • Bus Engine Breakdown: The bus stops dead on the highway mid-journey (like an unexpected runtime exception).
  • Boarding Wrong Bus: You ride smoothly the entire way, but arrive in the wrong city (like a logical error where code runs fine but calculation is wrong).
Figure 20.1: Journey analogy: exception handling provides the spare tire so execution reaches its destination safely.
Why Error Handling Matters
Errors will always happen: network cables get unplugged, servers return 500s, and users mistype numbers. Exception handling transforms catastrophic crashes into clean, friendly user recovery messages.

Software defects fall into three primary categories:

3. What Are Exceptions?

An exception is an object representing an abnormal or unexpected event encountered during program execution. Unlike ordinary code paths, when an exception occurs, normal execution stops immediately and Dart begins looking for an enclosing handler.

ATM Analogy: If you request a withdrawal of ₹5,000 from an ATM, but your account balance is only ₹2,000, the ATM machine must not shut down or blow a fuse! Instead, it detects the exceptional condition, creates a friendly message ("Insufficient Balance"), and returns your card safely.

Figure 20.3: Normal sequential execution vs diversion to exception handler.

4. Introduction to Exception Handling

Exception handling is Dart's mechanism to catch unexpected runtime events and steer execution toward graceful recovery. Dart provides six core keywords for this:

  • try: Wraps suspicious or risky code that might throw an exception.
  • catch: Intercepts the thrown exception object and optional stack trace.
  • on: Filters and matches specific exception types (e.g. on FormatException).
  • finally: Code that always executes after try/catch, ideal for resource cleanup.
  • throw: Explicitly generates and raises an exception.
  • rethrow: Passes an intercepted exception up to the next enclosing handler while preserving its stack trace.
Figure 20.4: The six essential keywords in Dart's error handling toolkit.

5. The `try` Block

A try block acts as a protective boundary around statements that may potentially fail at runtime (such as network calls, file reading, or parsing text).

  • If everything succeeds: the try block finishes normally, and all attached catch blocks are completely bypassed.
  • If an exception occurs: execution in the try block immediately aborts at that exact line and jumps directly into the matching catch block.
Figure 20.5: Execution paths for successful vs failing try blocks.
try_clean.dartDart 3.x
DART Script
DART 
void main() {
  try {
    int result = 10 ~/ 2;
    print("Result: $result"); // Runs smoothly
  } catch (e) {
    print("Something went wrong: $e"); // Skipped!
  }
}
Terminal Output Result: 5

6. The `catch` Block

The catch block captures the exception object thrown inside the try block. By catching the exception, the application prevents unhandled process termination, allowing remaining code outside the block to continue executing normally.

Figure 20.6: Exception transfer from try to catch, preserving program continuation.
catch_demo.dartDart 3.x
DART Script
DART 
void main() {
  try {
    int result = 10 ~/ 0;
    print(result);
  } catch (e) {
    print("Error occurred: $e");
  }

  print("Program continues successfully!");
}
Terminal Output Error occurred: IntegerDivisionByZeroException Program continues successfully!

7. Understanding the Stack Trace

When an exception occurs, Dart can provide two arguments to catch:

  1. e: The exception object itself (the error description).
  2. stackTrace: The call stack recording every function call leading up to the exact file and line number where the failure occurred.
Figure 20.7: Catch block capturing both the exception entity and diagnostic stack trace.
stack_trace.dartDart 3.x
DART Script
DART 
void main() {
  try {
    int result = 10 ~/ 0;
    print(result);
  } catch (e, stackTrace) {
    print("Exception: $e");
    print("Stack Trace Available: ${stackTrace.toString().isNotEmpty}");
  }
}
Terminal Output Exception: IntegerDivisionByZeroException Stack Trace Available: true

8. Using `on` to Catch Specific Exceptions

Using a general catch (e) intercepts every conceivable error, making tailored recovery difficult. The on keyword allows you to specify the exact exception type you expect and want to handle differently.

Figure 20.8: Specific type filtering using the 'on' keyword.
on_specific.dartDart 3.x
DART Script
DART 
void main() {
  try {
    int result = int.parse('hello');
    print(result);
  } on FormatException {
    print("Please enter a valid number");
  }
}
Terminal Output Please enter a valid number

9. Multiple Catch Clauses

A single operation can fail for multiple reasons. Dart supports chaining multiple on clauses. Dart evaluates them sequentially from top to bottom:

  • Place specific exception types first (e.g. on FormatException).
  • Place general exception handlers last (e.g. on Exception catch (e) or generic catch (e)).
Figure 20.9: Ordered cascading catch clauses: specific to general.
multi_catch.dartDart 3.x
DART Script
DART 
void main() {
  try {
    int value = int.parse('abc');
    print(value);
  } on FormatException {
    print("Invalid number format");
  } on Exception catch (e) {
    print("Other exception: $e");
  }
}
Terminal Output Invalid number format

10. The `finally` Block

The finally block executes whenever control leaves the try/catch construct in normal execution. It runs whether:

  • No exception occurred at all.
  • An exception occurred and was successfully caught and handled.

This makes finally the gold standard for resource cleanup (closing database connections, network sockets, or open files).

Figure 20.10: The finally block runs reliably after both normal and exceptional paths.
finally_demo.dartDart 3.x
DART Script
DART 
void main() {
  try {
    print("Opening file");
    int result = 10 ~/ 2;
    print(result);
  } catch (e) {
    print("Error: $e");
  } finally {
    print("Cleanup completed");
  }
}
Terminal Output Opening file 5 Cleanup completed

11. The `throw` Keyword

In addition to catching exceptions produced by Dart or the runtime system, you can raise exceptions deliberately using the throw keyword when business invariants are violated.

12. Understanding `rethrow`

Sometimes a function catches an exception locally to log it, show an animation, or free a temporary lock, but wants the caller to also know about the failure. Using rethrow forwards the exact original exception upward without resetting the call stack origin.

Figure 20.12: Rethrow propagates the original exception while preserving call stack diagnostics.
rethrow_demo.dartDart 3.x
DART Script
DART 
void processData() {
  try {
    int value = int.parse('abc');
    print(value);
  } catch (e) {
    print("Logging error locally: ${e.runtimeType}");
    rethrow; // Propagate original exception upward
  }
}

void main() {
  try {
    processData();
  } catch (e) {
    print("Handled by main caller: ${e.runtimeType}");
  }
}
Terminal Output Logging error locally: FormatException Handled by main caller: FormatException

14. Custom Exceptions

Generic exceptions (like Exception('something broke')) lack semantic context. By creating custom classes that implement Exception, you can define clear, domain-specific error types that can be caught individually.

Figure 20.14: Defining, throwing, and intercepting custom exception classes.
custom_exception.dartDart 3.x
DART Script
DART 
class InvalidAgeException implements Exception {
  final String message;
  InvalidAgeException(this.message);

  @override
  String toString() => message;
}

void checkAge(int age) {
  if (age < 18) {
    throw InvalidAgeException('Age must be 18 or above');
  }
  print('Registration successful');
}

void main() {
  try {
    checkAge(16);
  } on InvalidAgeException catch (e) {
    print(e);
  }
}
Terminal Output Age must be 18 or above

15. Creating Multiple Custom Exceptions (Banking Example)

Enterprise applications typically define families of custom exceptions for specific business operations. Here is a bank account with distinct custom exceptions for invalid amount vs insufficient balance:

Figure 20.15: Multi-exception architecture for financial transaction validations.
bank_account.dartDart 3.x
DART Script
DART 
class InvalidAmountException implements Exception {
  final String message;
  InvalidAmountException(this.message);
  @override String toString() => message;
}

class InsufficientBalanceException implements Exception {
  final double requested;
  final double available;
  InsufficientBalanceException(this.requested, this.available);
  @override String toString() => "Requested: \$$requested, but only \$$available available.";
}

class BankAccount {
  double balance = 500.0;

  void withdraw(double amount) {
    if (amount  balance) throw InsufficientBalanceException(amount, balance);
    balance -= amount;
  }
}

void main() {
  var acc = BankAccount();
  try {
    acc.withdraw(650.0);
  } on InvalidAmountException catch (e) {
    print("Error: $e");
  } on InsufficientBalanceException catch (e) {
    print("Funds Alert: $e");
  }
}
Terminal Output Funds Alert: Requested: $650.0, but only $500.0 available.

16. Assertions in Dart

An assertion (assert(condition, message)) is a development-time sanity check that halts execution during debugging if an internal assumption is violated.

Figure 20.16: Assertions execute in debug mode but are disabled in production releases.
assertions_demo.dartDart 3.x
DART Script
DART 
void main() {
  int age = 20;
  assert(age >= 18, 'Age must be at least 18');
  print('Age is valid');
}
Terminal Output Age is valid
Critical Rule: Never Use assert for User Input
Because assertions are disabled in production releases, using assert() to check user forms or payment amounts is a catastrophic security vulnerability. Always use standard if (...) throw ... for real application validation.

17. Exception Handling with Functions

When an exception is thrown inside a function, if that function does not catch it, the exception automatically unwinds the call stack to the calling function, then the calling function's caller, and so on until a handler is found.

Figure 20.17: Exception propagation bubbling up through the function call stack.
propagation.dartDart 3.x
DART Script
DART 
void divide(int a, int b) {
  if (b == 0) throw Exception('Cannot divide by zero');
  print(a ~/ b);
}

void calculate() {
  divide(10, 0); // Does not catch; passes up
}

void main() {
  try {
    calculate();
  } catch (e) {
    print('Error handled: $e');
  }
}
Terminal Output Error handled: Exception: Cannot divide by zero

18. Exception Handling with Collections and Type Conversion

A classic beginner pitfall is using int.parse() inside a try-catch just to parse user strings. Dart provides tryParse(), which returns null when conversion fails instead of throwing a costly exception.

Figure 20.18: parse() throws exceptions vs tryParse() returning null.
try_parse.dartDart 3.x
DART Script
DART 
void main() {
  String input = 'abc';
  int? number = int.tryParse(input);

  if (number == null) {
    print('Please enter a valid number');
  } else {
    print('Parsed: $number');
  }
}
Terminal Output Please enter a valid number

19. Exception Handling Best Practices

Figure 20.19: Cardinal principles of professional exception handling.
  • 1. Catch only what you can recover from: Don't catch an exception just to do nothing.
  • 2. Avoid empty catch blocks: catch (e) {} swallows crashes and makes debugging impossible.
  • 3. Don't use exceptions for normal control flow: Exceptions are slow; use null-safety checks or boolean returns instead.
  • 4. Never print sensitive secrets: Avoid printing API keys or user passwords in exception messages.

Program 2: Student Marks Input

program2_marks.dartDart 3.x
DART Script
DART 
class InvalidMarksException implements Exception {
  final String message;
  InvalidMarksException(this.message);
  @override String toString() => message;
}

void recordMarks(String raw) {
  try {
    int? score = int.tryParse(raw);

      throw InvalidMarksException("Marks must be in 0..100 range.");
    }
    print("Marks recorded: $score");
  } on FormatException catch (e) {
    print("Format error: ${e.message}");
  } on InvalidMarksException catch (e) {
    print("Validation warning: $e");
  }
}

void main() {
  recordMarks("92");
  recordMarks("120");
}

Program 3: ATM Withdrawal System

Figure 20.20b: ATM transaction failure handling preventing illegal balance deductions.
program3_atm.dartDart 3.x
DART Script
DART 
class OverdraftException implements Exception {
  final double amount;
  OverdraftException(this.amount);
  @override String toString() => "Cannot withdraw \$$amount. Insufficient funds!";
}

void processWithdrawal(double currentBalance, double amount) {
  try {
    if (amount > currentBalance) throw OverdraftException(amount);
    double remaining = currentBalance - amount;
    print("Dispensed \$$amount. Balance: \$$remaining");
  } on OverdraftException catch (e) {
    print(e);
  }
}

void main() {
  processWithdrawal(300.0, 100.0);
  processWithdrawal(300.0, 500.0);
}

Program 6: Resource Cleanup Simulation

program6_cleanup.dartDart 3.x
DART Script

class NetworkSocket {
  void connect() => print("Socket connected to server.");
  void send() => throw StateError("Transmission dropped!");
  void disconnect() => print("Socket disconnected safely.");
}

void main() {
  var socket = NetworkSocket();
  try {
    socket.connect();
    socket.send();
  } catch (e) {
    print("Caught error: $e");
  } finally {
    socket.disconnect(); // Always runs!
  }
}

21. Common Mistakes & Anti-Patterns

Figure 20.21: Dangerous traps to avoid when writing exception logic.
  • Trapping every Error: Treating Error (like NoSuchMethodError) as routine user input instead of fixing your code.
  • Wrong Catch Order: Writing catch (e) before on FormatException makes the specific handler completely unreachable.
  • Rethrow vs Throw e: Writing throw e instead of rethrow erases original stack trace origin.
  • Assuming Finally Only Runs on Failures: The finally block executes in both success and failure cases.
