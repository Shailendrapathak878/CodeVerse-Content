01
Core Foundation

What Are Generics?

In modern software engineering, writing clean code means solving problems without repeating yourself. Java Generics allow classes, interfaces, and methods to operate on parameterized types, providing strong compile-time type checking and eliminating dangerous manual type casting.

📖 Formal Definition: Generics
Generics (introduced in Java 5) enable types (classes and interfaces) to be parameters when defining classes, interfaces, and methods. Much like the more familiar formal parameters used in method declarations, type parameters provide a way for you to re-use the same code with different inputs—specifically, different type inputs.

1.1 The Real-Life Analogy: Laboratory Storage Boxes

Imagine a busy university engineering laboratory. The lab maintains hundreds of durable storage boxes:

  • One box has a clear label: "Microcontroller Chips Only". If a student tries to drop a heavy steel hammer into it, the lab supervisor stops them before the lid is closed.
  • Another box is labeled: "Reference Textbooks Only". If someone tries to pour liquid chemicals into it, the label prevents the mistake.
  • A generic box design is identical in dimensions and hinges, but its label designates its exact contents at the moment it is deployed.

Without labels, every box is just an unlabeled container of generic "Things". You would have to inspect, test, and cast whatever you pull out, hoping you don't grab something toxic or incompatible. Generics give your Java containers clear, compiler-enforced labels!

Figure 20.1 The Generic Blueprint: One Class Defining Multiple Type-Safe Containers
Figure 20.1: A single generic class Box<T> is parameterized at instantiation into dedicated, type-safe containers: Box<String>, Box<Integer>, and Box<Double>.

1.2 A First Look at a Generic Class

Here is the standard, idiomatic generic box implementation in Java:

Java 21 Box.java (Generic Class Definition) 
// T is a type parameter standing for any reference type
class Box<T> {
    private T item;

    public void setItem(T item) {
        this.item = item;
    }

    public T getItem() {
        return item;
    }
}

public class Main {
    public static void main(String[] args) {
        // Specify String as the type argument
        Box<String> box = new Box<>();

        box.setItem("Java Notes");

        // No explicit casting required!
        String content = box.getItem();
        System.out.println(content);
    }
}
Expected Console Output 
Java Notes

1.3 Step-by-Step Code Deconstruction

Syntax Component What It Represents Compiler & Runtime Behavior
class Box<T> Generic Type Parameter Declaration Tells the compiler that T is a placeholder representing a type to be specified upon instantiation.
private T item; Field of Parameterized Type The field item will assume whatever reference type is provided for T.
Box<String> box Type Argument Specification Binds T = String for this specific variable reference.
new Box<>() Diamond Operator Instantiation Compiler automatically infers <String> from the variable declaration type.
String s = box.getItem() Safe Value Extraction Compiler guarantees getItem() returns a String. No (String) cast required.
02
Historical Evolution

Why Do We Need Generics?

To truly appreciate Java Generics, we must examine the software landscape of Java 1.0 through Java 1.4, when developers relied entirely on java.lang.Object to build reusable data structures.

2.1 The Pre-Generics Era: The Universal Object Container

Because Object is the superclass of all classes in Java, developers wrote reusable containers by holding references to Object:

Java (Pre-Generics Style) OldBox.java (Non-Generic Object Container) 
// Legacy non-generic container
class OldBox {
    private Object item;

    public void setItem(Object item) {
        this.item = item;
    }

    public Object getItem() {
        return item;
    }
}

While OldBox can store any reference type, it creates two major structural defects:

  1. Clumsy Manual Type Casting: Every time you retrieve an item, you must explicitly cast it back to the intended type (e.g., String s = (String) box.getItem();).
  2. Silent Runtime Disasters: The compiler has no idea what type was placed into the box. If another programmer accidentally places an incompatible object into the box, the compiler remains completely silent. The error only manifests as a fatal crash during runtime!
Java The ClassCastException Trap 
OldBox box = new OldBox();
box.setItem("Hello, World!"); // Stored as Object

// Programmer mistakenly assumes the box holds an Integer
// This line COMPILES without error, but CRASHES at runtime!
Integer number = (Integer) box.getItem(); // Throws ClassCastException!
Runtime Failure Output 
Exception in thread "main" java.lang.ClassCastException: 
class java.lang.String cannot be cast to class java.lang.Integer
Figure 20.2 Non-Generic Object vs Generic Container Architectural Comparison
Figure 20.2: With non-generic containers, incorrect casts compile silently and crash in production. With generics, type mismatches are caught immediately by the compiler.

2.2 How Generics Solve Both Problems

When we rewrite the container using a generic type parameter:

Java 21 TypeSafeUsage.java 
Box<String> box = new Box<>();
box.setItem("Hello, World!");

// 1. No casting needed: compiler knows getItem() returns String
String text = box.getItem(); 

// 2. Immediate compile-time error if type contract is violated:
// box.setItem(100); // Compile-time error: int cannot be converted to String
💡 Key Principle: Shift Left on Error Detection
In software engineering, bugs discovered during compilation cost 100x less to fix than bugs discovered at runtime by end users. Generics shift type errors from runtime crashes to compile-time build errors.

Quality Assurance

Type Safety and Compile-Time Checking

Type Safety means that the programming language prevents type errors by ensuring that operations are applied only to values of compatible types. In Java, generics act as an unbreachable compile-time type shield.

3.1 The Three Categories of Software Defects

To understand why compile-time verification is so prized, consider how different categories of errors behave throughout the software development lifecycle:

Figure 20.3 The Three Bug Categories and the Generics Shield
Figure 20.3: Generics intercept dangerous type mismatch exceptions at compile time, eliminating an entire class of runtime failures before code ever reaches deployment.
Defect Category When Detected Typical Cause Role of Generics
Compile-Time Error During javac compilation Passing an Integer where a String was promised Actively triggers this error to prevent bad code from compiling.
Runtime Exception While application executes ClassCastException, NullPointerException Eliminates ClassCastException caused by manual type casting.
Logical Defect During QA or production usage Calculating interest incorrectly, sorting in reverse Outside the type system; requires unit tests and code review.

3.2 Compile-Time Verification in Action

Let's examine what happens when incompatible data is passed to a generic container:

Java (Deliberate Compile-Time Error) CompileCheckDemo.java 
Box<String> studentNames = new Box<>();

studentNames.setItem("Aman"); // Perfectly valid String

// ========================================================
// DELIBERATE COMPILE-TIME ERROR:
// The compiler rejects this line immediately:
// studentNames.setItem(100); 
// ========================================================

If you attempt to compile the line studentNames.setItem(100);, the Java compiler (javac) terminates with an explicit diagnostic:

Javac Compiler Diagnostic 
CompileCheckDemo.java:8: error: incompatible types: int cannot be converted to String
        studentNames.setItem(100);
                             ^
1 error

Syntax & Style

Generic Type Parameter Naming Conventions

By convention, type parameter names are single, uppercase letters. This sharp contrast with ordinary class and interface names (which use PascalCase) makes generic type variables instantly identifiable across any Java codebase.

Figure 20.4 Standard Java Type Parameter Naming Conventions
Figure 20.4: Standard single-letter type parameter naming conventions established in Oracle's Java Language Specification (JLS).

4.1 Convention Breakdown and Standard APIs

Symbol Conventional Meaning Common Context Canonical Java Standard Library Example
T Type (General) Standalone generic classes or primary method arguments Box<T>, Optional<T>, Comparable<T>
E Element Items stored within collections and data structures List<E>, Set<E>, Queue<E>
K Key Lookup keys in associative tables and dictionaries Map<K, V>, Entry<K, V>
V Value Payload values associated with keys in mapping structures Map<K, V>, HashMap<K, V>
N Number Restricted numeric type parameters and math utilities <N extends Number>
R Result / Return Return types in functional interfaces and transformers Function<T, R>, BiFunction<T, U, R>
S, U, V Secondary Types 2nd, 3rd, and 4th arbitrary type parameters when T is taken TriFunction<T, U, V, R>
⚠ Important: Convention vs Keyword
T, E, and K are not Java language keywords. You could technically name a type parameter class Box<MyAwesomeType>, but doing so violates Java community conventions and confuses developers who expect uppercase single letters. Always stick to standard conventions!
05
Object-Oriented Design

Generic Classes: Blueprints for Type-Safe Objects

A generic class is a class that defines one or more type parameters in its header. Once declared, these type parameters can be used anywhere inside the class body as field types, method parameter types, and method return types.

5.1 Declaration Syntax

Java Syntax Generic Class Skeleton 
public class ClassName<T> {
    private T fieldName;

    public void setField(T value) {
        this.fieldName = value;
    }

    public T getField() {
        return this.fieldName;
    }
}
Figure 20.5 Generic Class Anatomy and Diamond Operator Resolution
Figure 20.5: The type parameter <T> is specified on the left-hand variable type, while the diamond operator <> allows the compiler to automatically infer the constructor parameter.

5.2 Multi-Instance Demonstration

Notice how multiple instances of the exact same class definition can coexist in the same application, each enforcing completely different, strict type rules:

Java 21 GenericClassDemo.java 
class Box<T> {
    private T item;

    public void setItem(T item) {
        this.item = item;
    }

    public T getItem() {
        return item;
    }
}

public class GenericClassDemo {
    public static void main(String[] args) {
        // Instance 1: Dedicated to Strings
        Box<String> textBox = new Box<>();
        textBox.setItem("CodeVerse");

        // Instance 2: Dedicated to Integers
        Box<Integer> numberBox = new Box<>();
        numberBox.setItem(100);

        System.out.println("Text Box holds: " + textBox.getItem());
        System.out.println("Number Box holds: " + numberBox.getItem());
    }
}
Expected Console Output 
Text Box holds: CodeVerse
Number Box holds: 100

5.3 Primitive Types vs Wrapper Classes

In Java, type arguments must be reference types. You cannot use primitive types like int, double, or boolean directly:

  • Box<int> box = new Box<>(); → COMPILE ERROR: unexpected type found: int, required: reference
  • Box<Integer> box = new Box<>(); → PERFECT! Java automatically autoboxes primitive int into Integer.
06
Compound Data Structures

Generic Classes with Multiple Type Parameters

A class is not limited to a single type parameter. You can declare multiple comma-separated type parameters inside the angle brackets, creating sophisticated multi-typed data structures such as key-value pairs, tuples, and coordinate maps.

6.1 The Classic Pair<K, V> Implementation

Consider an associative mapping between two distinct domains—such as a student roll number (Integer) and a student name (String), or a product SKU (String) and a price (Double):

Figure 20.6 Multiple Type Parameters: Pair<K, V> Architecture
Figure 20.6: In Pair<K, V>, the key and value types are completely independent. Each field preserves its own compile-time type verification.
Java 21 PairDemo.java 
class Pair<K, V> {
    private final K key;
    private final V value;

    public Pair(K key, V value) {
        this.key = key;
        this.value = value;
    }

    public K getKey() {
        return key;
    }

    public V getValue() {
        return value;
    }

    @Override
    public String toString() {
        return "Pair[" + key + " -> " + value + "]";
    }
}

public class PairDemo {
    public static void main(String[] args) {
        // K = Integer (Roll Number), V = String (Student Name)
        Pair<Integer, String> student = new Pair<>(101, "Riya");

        // K = String (Product Code), V = Double (Price)
        Pair<String, Double> product = new Pair<>("LAPTOP-X1", 1299.99);

        System.out.println("Student: " + student.getKey() + " = " + student.getValue());
        System.out.println("Product: " + product.getKey() + " = $" + product.getValue());
    }
}
Expected Console Output 
Student: 101 = Riya
Product: LAPTOP-X1 = $1299.99

6.2 Why <K, V> Beats Storing Objects

If we had stored both fields as Object, calling student.getKey() would return an Object. We would be forced to write int id = (Integer) student.getKey();. By using <K, V>, the compiler guarantees that getKey() returns an Integer and getValue() returns a String without any casts!

07
Reusable Algorithms

Generic Methods: Algorithms Independent of Enclosing Classes

A generic method is a method that declares its own type parameter(s). A method can be generic even if the enclosing class is completely non-generic! This makes generic methods ideal for utility libraries, converters, and search algorithms.

7.1 Syntax: Placement of the Type Parameter

The most critical rule in generic method declaration is the position of <T>: the type parameter list must appear BEFORE the method return type.

Figure 20.7 Generic Method Anatomy and Argument-Driven Type Inference
Figure 20.7: The type parameter <T> precedes the return type (void). When the method is invoked, the compiler infers T directly from the argument passed.
Java 21 GenericMethodDemo.java 
public class GenericMethodDemo {
    // Generic static method:  placed before void
    public static <T> void display(T value) {
        System.out.println("Value: " + value + " | Inferred Type: " + 
            (value != null ? value.getClass().getSimpleName() : "null"));
    }

    public static void main(String[] args) {
        // 1. Invoking with String: compiler infers T = String
        display("Java");

        // 2. Invoking with int: autoboxed to Integer, compiler infers T = Integer
        display(100);

        // 3. Invoking with double: autoboxed to Double, compiler infers T = Double
        display(3.14);

        // 4. Invoking with boolean: autoboxed to Boolean
        display(true);
    }
}
Expected Console Output 
Value: Java | Inferred Type: String
Value: 100 | Inferred Type: Integer
Value: 3.14 | Inferred Type: Double
Value: true | Inferred Type: Boolean

7.2 Explicit Type Witnesses

In rare situations where the compiler cannot automatically deduce the intended type parameter, you can provide an explicit type witness before the method name: 

// Explicit type witness syntax:
GenericMethodDemo.<String>display("Java");
GenericMethodDemo.<Integer>display(100);

In modern Java (Java 8+), type inference is so robust that explicit type witnesses are almost never required in everyday application code.

08
Method Specialization

Generic Methods with Multiple Parameters

Generic methods can declare multiple type parameters or accept multiple arguments bound to the same type. Understanding how the Java compiler resolves multiple arguments is critical for writing predictable utility functions.

8.1 Homogeneous vs Heterogeneous Generic Methods

Consider the difference between a method that requires both arguments to share a single type T versus a method that permits two completely independent types K and V:

Figure 20.8 Homogeneous vs Heterogeneous Generic Methods
Figure 20.8: <T> printPair(T a, T b) binds both parameters to the same common type, whereas <K, V> printEntry(K key, V val) decouples parameter types completely.

8.2 Code Example: Single <T> vs Dual <K, V>

Java 21 MultiParamMethods.java 
public class MultiParamMethods {

    // Single type parameter T: both arguments must be compatible with T
    public static <T> void printPair(T first, T second) {
        System.out.println(first + " | " + second);
    }

    // Two independent type parameters: K and V can be entirely different types
    public static <K, V> void printEntry(K key, V value) {
        System.out.println(key + " -> " + value);
    }

    public static void main(String[] args) {
        // printPair with identical String types
        printPair("Apple", "Banana");

        // printEntry with Integer key and String value
        printEntry(101, "Riya");

        // printEntry with String key and Double value
        printEntry("ExchangeRate", 83.25);
    }
}
Expected Console Output 
Apple | Banana
101 -> Riya
ExchangeRate -> 83.25
⚠ Compiler Nuance: Least Upper Bound Inference
If you call printPair("Java", 100) with one String and one Integer, the Java compiler will not fail immediately! Instead, it infers T as the least upper bound of both types (which is Object & Serializable & Comparable<?>). However, if your method body attempts to call String-specific methods like first.toUpperCase(), compilation will fail. To allow truly independent types, always declare separate parameters: <K, V>.
09
API Contracts

Generic Interfaces: Designing Extensible Contracts

An interface can declare one or more type parameters, establishing a generic contract for implementors. This pattern forms the bedrock of modern enterprise architectures, such as the Repository Pattern in Spring Data.

9.1 The Two Ways to Implement a Generic Interface

When a class implements a generic interface, it has two architectural options:

  1. Closed / Concrete Implementation: The implementing class specifies a concrete type argument (e.g., implements Repository<String>). The class itself is not generic.
  2. Open / Generic Implementation: The implementing class retains the generic type parameter (e.g., class InMemoryRepo<T> implements Repository<T>).
Figure 20.9 Generic Interface Contract and Implementation Modes
Figure 20.9: Repository<T> implemented either by locking T to String (closed) or by propagating T as a generic parameter (open).
Java 21 GenericInterfaceDemo.java 
// Generic interface contract
interface Repository<T> {
    void save(T item);
    T findById(int id);
}

// Mode 1: Concrete implementation (Locks T to String)
class StudentRepository implements Repository<String> {
    private String studentName;

    @Override
    public void save(String item) {
        this.studentName = item;
    }

    @Override
    public String findById(int id) {
        return this.studentName;
    }
}

// Mode 2: Open generic implementation (Retains T for caller)
class GenericMemoryRepo<T> implements Repository<T> {
    private T cachedItem;

    @Override
    public void save(T item) {
        this.cachedItem = item;
    }

    @Override
    public T findById(int id) {
        return this.cachedItem;
    }
}

public class GenericInterfaceDemo {
    public static void main(String[] args) {
        Repository<String> studentRepo = new StudentRepository();
        studentRepo.save("Aman");
        System.out.println("Student: " + studentRepo.findById(101));

        Repository<Double> scoreRepo = new GenericMemoryRepo<>();
        scoreRepo.save(98.5);
        System.out.println("Score: " + scoreRepo.findById(1));
    }
}
Expected Console Output 
Student: Aman
Score: 98.5

Object Lifecycle

Generic Constructors vs Generic Classes

Students often assume that because a class is generic, its constructor is automatically a "generic constructor." In Java, these are two distinct syntactic concepts with different scoping rules.

10.1 Ordinary Constructor in a Generic Class

An ordinary constructor in a generic class simply consumes the class-level type parameter T. It does not declare its own <...> tag: 

class Box<T> {
    private T item;

    // Ordinary constructor: consumes class-level T
    public Box(T item) {
        this.item = item;
    }
}

10.2 A Genuinely Generic Constructor

A generic constructor is a constructor that declares its own independent type parameter (e.g., <E>) before the constructor name. Genuinely generic constructors can even exist inside non-generic classes!

Figure 20.10 Standard Constructor vs Genuinely Generic Constructor
Figure 20.10: A standard constructor adopts the class's type parameter. A generic constructor declares its own type parameter preceding the constructor identifier.
Java 21 GenericConstructorDemo.java 
// Non-generic class containing a genuinely generic constructor
class Printer {
    // Declares constructor-scoped type parameter 
    public <T> Printer(T value) {
        System.out.println("Constructing Printer for: " + value + 
            " (Type: " + value.getClass().getSimpleName() + ")");
    }
}

public class GenericConstructorDemo {
    public static void main(String[] args) {
        new Printer("Hello Generics"); // T inferred as String
        new Printer(42);               // T inferred as Integer
        new Printer(99.99);            // T inferred as Double
    }
}
Expected Console Output 
Constructing Printer for: Hello Generics (Type: String)
Constructing Printer for: 42 (Type: Integer)
Constructing Printer for: 99.99 (Type: Double)
11
Type Constraints

Bounded Type Parameters: Restricting Types to Gain Power

By default, an unbounded type parameter <T> accepts any reference type. Because T could be anything, the compiler only permits calling methods defined on java.lang.Object (such as toString() and hashCode()). Bounded type parameters restrict the allowed types while unlocking the specific methods of the bound.

11.1 The Calculator Analogy

Imagine you are building a digital calculator method to compute the square of a number. An unbounded <T> could receive a String, a BufferedImage, or a Socket—none of which can be squared! By applying a bound: <T extends Number>, you restrict arguments to numbers (Integer, Double, Float, Long) and gain access to methods like doubleValue().

Figure 20.11 Bounded Type Parameter <T extends Number> Model
Figure 20.11: The bound <T extends Number> acts as a compile-time filter, accepting numeric wrapper classes and rejecting non-numeric types like String.

11.2 The Meaning of `extends` in Type Bounds

📖 Syntactic Rule: extends for Classes and Interfaces
In generic type bounds, the keyword extends is used in a broad, unified sense:
  • If Bound is a class, T extends Bound means T is Bound or a subclass.
  • If Bound is an interface, T extends Bound means T implements the interface.
Java does not use <T implements Comparable>. In generic type parameter bounds, extends is always used for both classes and interfaces!
Java 21 BoundedMethodDemo.java 
public class BoundedMethodDemo {
    // Bounded to java.lang.Number: grants access to .doubleValue()
    public static <T extends Number> double calculateSquare(T number) {
        double val = number.doubleValue();
        return val * val;
    }

    public static void main(String[] args) {
        int intVal = 7;
        double dblVal = 4.5;

        System.out.println("Square of " + intVal + ": " + calculateSquare(intVal));
        System.out.println("Square of " + dblVal + ": " + calculateSquare(dblVal));

        // ========================================================
        // DELIBERATE COMPILE-TIME ERROR:
        // calculateSquare("hello"); // Compile error: String is not within bound!
        // ========================================================
    }
}
Expected Console Output 
Square of 7: 49.0
Square of 4.5: 20.25

Compound Constraints

Multiple Bounds: Combining Classes and Interfaces

A type parameter can be constrained by multiple bounds using the ampersand symbol (&). This allows your generic methods to require that an object inherit from a specific base class and implement one or more specific interfaces.

12.1 Syntax Rules for Multiple Bounds

Java Syntax Multiple Bounds Declaration 
<T extends ClassBound & InterfaceBound1 & InterfaceBound2>
Figure 20.12 Multiple Bounds Architecture (& Operator)
Figure 20.12: A type parameter with multiple bounds: exactly zero or one class (must be placed first) followed by interface bounds.

12.2 Strict Compiler Rules

  • Class Bound Must Be First: If one of the bounds is a class, it must be listed first in the bound declaration. Writing <T extends Comparable<T> & BaseEntity> will trigger a compiler error.
  • At Most One Class Bound: Because Java does not support multiple class inheritance, a type parameter cannot extend more than one class.
  • Multiple Interfaces Allowed: You can append as many interface bounds as required using additional & operators.
Java 21 MultipleBoundsExample.java 
class Entity {
    private final String id;
    public Entity(String id) { this.id = id; }
    public String getId() { return id; }
}

// T must be an Entity AND must implement Comparable
class EntitySorter {
    public static <T extends Entity & Comparable<T>> T getMin(T a, T b) {
        // Access Entity method getId() AND Comparable method compareTo()
        System.out.println("Comparing Entity " + a.getId() + " and " + b.getId());
        return a.compareTo(b) <= 0 ? a : b;
    }
}
13
Flexible Polymorphism

Wildcards: The Question Mark (?) and Unbounded Types

In generic code, the question mark (?) is known as the wildcard. It represents an unknown type. Wildcards are essential for writing flexible methods that operate on collections of different types.

13.1 Why Do We Need Wildcards?

Suppose you want to write a method that prints every element in a list. If you write: 

public static void printList(List<Object> list) { ... }

You might expect to be able to pass a List<String> or a List<Integer> to this method. You cannot! Because generic types are invariant in Java, List<String> is not a subtype of List<Object>. The compiler will reject the call!

To create a method that accepts a list of any type, you use the unbounded wildcard: List<?>.

Figure 20.13 Unbounded Wildcard List<?> Read vs Write Restrictions
Figure 20.13: Reading from List<?> yields Object safely. Writing arbitrary non-null objects to List<?> is prohibited to prevent heap pollution.

13.2 Code Example: Unbounded Wildcard Method

Java 21 UnboundedWildcardDemo.java 
import java.util.List;

public class UnboundedWildcardDemo {
    // Accepts a list containing elements of any unknown type
    public static void printElements(List<?> list) {
        System.out.print("[Size: " + list.size() + "] -> ");
        for (Object item : list) {
            System.out.print(item + " ");
        }
        System.out.println();
    }

    public static void main(String[] args) {
        List<String> names = List.of("Alice", "Bob", "Charlie");
        List<Integer> scores = List.of(95, 88, 92);
        List<Boolean> flags = List.of(true, false, true);

        // Same method handles all list types!
        printElements(names);
        printElements(scores);
        printElements(flags);
    }
}
Expected Console Output 
[Size: 3] -> Alice Bob Charlie 
[Size: 3] -> 95 88 92 
[Size: 3] -> true false true

13.3 The Wildcard Write Restriction

✗ Critical Rule: You Cannot Add Elements to List<?>
You cannot add non-null elements to a collection declared as List<?>: 
public static void addItems(List<?> list) {
    // COMPILE-TIME ERROR:
    // list.add("Hello"); // Error: capture#1 of ? cannot be converted to String
}
Why? Because the compiler has no idea what actual list type was passed. If the caller passed a List<Integer>, allowing list.add("Hello") would corrupt the list! The only value you can add to a List<?> is null.
14
Covariance

Upper-Bounded Wildcards: ? extends T

An upper-bounded wildcard restricts the unknown type to a specific type or a subtype of that type using the syntax <? extends T>. This establishes covariance, allowing you to read elements with a guaranteed common supertype.

14.1 The Summation Problem

Suppose you want to compute the total sum of numbers in a list. You want your method to accept a List<Integer>, a List<Double>, or a List<Long>. By declaring the parameter as List<? extends Number>, all numeric lists become valid arguments!

Figure 20.14 Upper-Bounded Wildcard List<? extends Number> Hierarchy
Figure 20.14: List<? extends Number> establishes an upper bound (ceiling) at Number. Any list whose element type extends Number can be passed into the method.
Java 21 UpperBoundedWildcardDemo.java 
import java.util.List;

public class UpperBoundedWildcardDemo {
    // Accepts any list whose elements are Number or a subclass of Number
    public static double sumNumbers(List<? extends Number> numbers) {
        double total = 0.0;
        for (Number n : numbers) {
            // Safe to extract as Number because Number is the upper bound!
            total += n.doubleValue();
        }
        return total;
    }

    public static void main(String[] args) {
        List<Integer> intList = List.of(10, 20, 30);
        List<Double> doubleList = List.of(2.5, 4.5, 3.0);
        List<Long> longList = List.of(100L, 200L);

        System.out.println("Int Sum: " + sumNumbers(intList));
        System.out.println("Double Sum: " + sumNumbers(doubleList));
        System.out.println("Long Sum: " + sumNumbers(longList));
    }
}
Expected Console Output 
Int Sum: 60.0
Double Sum: 10.0

Contravariance

Lower-Bounded Wildcards: ? super T

While an upper-bounded wildcard restricts the unknown type to a subtype (acting as a read-only producer), a lower-bounded wildcard restricts the unknown type to a supertype of a specified class using the syntax <? super T>. This establishes contravariance, creating a safe destination for writing elements.

15.1 The Destination / Consumer Concept

Suppose you have a method that generates integers and appends them to a list. Where can an Integer safely be placed?

  • Can an Integer be added to a List<Integer>? Yes!
  • Can an Integer be added to a List<Number>? Yes! (Integer is a valid Number).
  • Can an Integer be added to a List<Object>? Yes! (Integer is a valid Object).

By specifying List<? super Integer>, the method can write Integer objects into any of these lists safely!

Figure 20.15 Lower-Bounded Wildcard List<? super Integer> Hierarchy
Figure 20.15: List<? super Integer> accepts Integer and all its superclasses (Number, Object). Writing an Integer into any of these targets is completely type-safe.

15.2 Code Example: Writing Into a Lower-Bounded Wildcard

Java 21 LowerBoundedWildcardDemo.java 
import java.util.ArrayList;
import java.util.List;

public class LowerBoundedWildcardDemo {
    // Consumer method: destination accepts Integer or any supertype of Integer
    public static void addEvenNumbers(List<? super Integer> destination, int count) {
        for (int i = 1; i <= count; i++) {
            destination.add(i * 2); // Perfectly safe!
        }
    }

    public static void main(String[] args) {
        // 1. Target is List
        List<Integer> intList = new ArrayList<>();
        addEvenNumbers(intList, 3);
        System.out.println("Integer List: " + intList);

        // 2. Target is List
        List<Number> numList = new ArrayList<>();
        addEvenNumbers(numList, 4);
        System.out.println("Number List: " + numList);

        // 3. Target is List
