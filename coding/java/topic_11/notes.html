SECTION 01

1. Why Do We Need Encapsulation?

Imagine walking into a commercial bank with an open vault sitting in the middle of the lobby. Any customer could walk up to the cash stacks, grab whatever amount they wanted, write down whatever number they felt like in a notebook, and walk out. Within minutes, the ledger would be completely corrupted, counterfeit cash would be slipped in, and the bank would collapse.

Instead, banks protect their assets using an encapsulated system: cash is locked inside a secure vault (private data), and customers interact through guarded teller windows or automated teller machines (public methods). When you make a deposit or withdrawal, the ATM validates your card, checks your PIN, verifies that you have sufficient funds, and updates your balance according to strict business rules.

💡 Core Definitions

Encapsulation: The fundamental object-oriented programming principle of bundling data (fields) and the operations that act upon that data (methods) together inside a single class, while tightly restricting direct external access to the internal state.

Data Hiding: Concealing an object's internal variables from direct access by other classes so that state modifications can only occur through controlled, validated operations.

Figure 1.1: Direct access allows external code to inject invalid or corrupt data. Encapsulation wraps data inside a protected vault with validated entry methods.

Protecting Valid Object State (Invariants)

In software engineering, an invariant is a condition that must always remain true for an object to be considered valid and healthy. Consider these everyday examples:

  • A Student's exam marks must always fall between 0 and 100.
  • A BankAccount's balance must never drop below 0 (no unauthorized overdraft).
  • A Person's age cannot be negative (e.g., -25).
  • A Product's inventory stock quantity cannot be negative.

Without encapsulation, any rogue or buggy line of code elsewhere in a large enterprise project can directly mutate a field (e.g. student.marks = -500;), corrupting the object's integrity and causing silent crashes downstream. Encapsulation guarantees that the object itself acts as its own gatekeeper.

SECTION 02

2. What Is Encapsulation?

In Java, encapsulation is achieved through two complementary programming practices:

  1. Declaring the fields of a class as private (preventing direct external tampering).
  2. Providing public methods (getters, setters, or action methods) to inspect and modify those fields under controlled validation rules.
Figure 2.1: Encapsulated class structure: private fields are shielded inside the class boundary; external code communicates exclusively through public methods.

A Simple Student Example

Here is an encapsulated Student class where marks is private and protected by a setter validation gate:

Student.java 
public class Student {
    // 1. Private field: inaccessible directly from outside
    private int marks;

    // 2. Public setter: validates value before storing
    public void setMarks(int marks) {
        if (marks >= 0 && marks <= 100) {
            this.marks = marks; // Accepted: valid range
        } else {
            System.out.println("Validation Error: Marks must be between 0 and 100!");
        }
    }

    // 3. Public getter: safely delivers field value to caller
    public int getMarks() {
        return marks;
    }
}
Main.java 
public class Main {
    public static void main(String[] args) {
        Student s = new Student();

        // Valid assignment via public method
        s.setMarks(85);
        System.out.println("Student marks: " + s.getMarks());

        // Invalid assignment attempt: rejected by validation
        s.setMarks(-50);
        System.out.println("Student marks after invalid attempt: " + s.getMarks());
    }
}
🖥 Console Output
Student marks: 85 Validation Error: Marks must be between 0 and 100! Student marks after invalid attempt: 85

Execution Trace: When s.setMarks(85) is called, the condition 85 >= 0 && 85 <= 100 evaluates to true, so this.marks is updated. When s.setMarks(-50) is called, the condition evaluates to false; the setter prints a validation warning and leaves this.marks safely at 85.

SECTION 03

3. What Happens Without Encapsulation?

To truly appreciate encapsulation, let us look at what happens when fields are left public. In naive beginner code, developers often declare everything as public because it seems convenient:

UncontrolledStudent.java 
// DANGEROUS: Uncontrolled public field
public class UncontrolledStudent {
    public int marks; // No protection, no validation!
}
BuggyApp.java 
public class BuggyApp {
    public static void main(String[] args) {
        UncontrolledStudent s = new UncontrolledStudent();
        
        // Any external code can write nonsense values
        s.marks = -50;
        System.out.println("Corrupted Marks: " + s.marks); // Prints -50!
        
        s.marks = 999999;
        System.out.println("Absurd Marks: " + s.marks);   // Prints 999999!
    }
}
🖥 Console Output
Corrupted Marks: -50 Absurd Marks: 999999
Figure 3.1: Side-by-side comparison: Uncontrolled public field allows arbitrary corruption, whereas controlled access halts invalid state changes.
⚠ Key Architectural Insight

The compiler does not stop s.marks = -50 because -50 is a perfectly legal 32-bit signed integer. The problem is semantic corruption: Java's compiler knows data types, but it does not know your application's domain rules! Only encapsulation with validation logic can enforce domain rules.

SECTION 04

4. The private Access Modifier

The private keyword is Java's most restrictive access modifier. It dictates that a member (field, method, or constructor) is accessible only from within the exact body of the class that declares it.

Figure 4.1: The private modifier forms a vault boundary around class fields. Code in any other class is strictly barred from direct access.

Employee Salary Example

Employee.java 
public class Employee {
    private double salary; // PRIVATE: Inaccessible outside Employee class

    public void setSalary(double salary) {
        if (salary >= 0) {
            this.salary = salary;
        }
    }

    public double getSalary() {
        return salary;
    }
}

Now consider what happens if outside code attempts to access salary directly:

✗ ILLEGAL: Direct Private Access
public class Payroll {
    public static void main(String[] args) {
        Employee emp = new Employee();
        // COMPILE-TIME ERROR!
        emp.salary = 65000.0; 
    }
}

Compiler Error: salary has private access in Employee

✓ LEGAL: Access via Public Setter
public class Payroll {
    public static void main(String[] args) {
        Employee emp = new Employee();
        // COMPILES & RUNS PERFECTLY!
        emp.setSalary(65000.0); 
        System.out.println(emp.getSalary());
    }
}

Output: 65000.0

SECTION 05

5. Getters and Setters (Accessor & Mutator Methods)

Because private fields cannot be accessed directly, we provide standardized public methods to read and write them. In Java terminology:

  • Getter (Accessor): A public method that returns the current value of a private field. It takes no parameters and has a return type matching the field.
  • Setter (Mutator): A public method that receives a new value, validates it, and updates the private field. It typically has a void return type (or boolean to indicate success).

Java Bean Naming Conventions

Java follows strict, universally recognized naming conventions for getters and setters:

Field Type & Name Getter Method Name Setter Method Name Notes
String name public String getName() public void setName(String name) Standard camelCase with get / set prefix
int age public int getAge() public void setAge(int age) Standard numeric accessor/mutator
boolean active public boolean isActive() public void setActive(boolean active) Boolean getters conventionally use is instead of get
Figure 5.1: Getter Method Flow: The caller requests a value through the public interface; the method reads the private field and returns a copy.
Figure 5.2: Setter Method Flow: The caller passes an argument; the validation decision gate evaluates it before updating internal state.

Distinguishing Fields with the this Keyword

Notice the common pattern inside setters: this.name = name;. Here, the parameter name shadows the instance variable name. The this keyword explicitly points to the current object instance's field, avoiding the classic bug where a parameter merely assigns to itself!

Person.java 
public class Person {
    private String name;
    private int age;
    private boolean active;

    // Constructor using setters for validation
    public Person(String name, int age, boolean active) {
        this.name = name;
        setAge(age);
        this.active = active;
    }

    public String getName() {
        return name;
    }

    public void setName(String name) {
        this.name = name; // this.name is field; name is parameter
    }

    public int getAge() {
        return age;
    }

    public void setAge(int age) {
        if (age >= 0) {
            this.age = age;
        }
    }

    public boolean isActive() {
        return active;
    }

    public void setActive(boolean active) {
        this.active = active;
    }
}
SECTION 06

6. Validation Through Encapsulation (BankAccount Model)

Let us examine a complete, robust financial domain model: BankAccount. Rather than just exposing raw setters, real-world encapsulation exposes meaningful domain actions such as deposit() and withdraw().

Figure 6.1: BankAccount validation logic: Deposit guards against non-positive sums; withdraw guards against non-positive amounts and overdrafts.
BankAccount.java 
public class BankAccount {
    private int balance; // In whole currency units (e.g. dollars)

    public BankAccount(int initialBalance) {
        if (initialBalance >= 0) {
            this.balance = initialBalance;
        } else {
            this.balance = 0;
        }
    }

    public int getBalance() {
        return balance;
    }

    // Action method: returns true if deposit succeeded, false if rejected
    public boolean deposit(int amount) {
        if (amount <= 0) {
            return false; // Rejected: cannot deposit zero or negative cash
        }
        this.balance += amount;
        return true;
    }

    // Action method: returns true if withdrawal succeeded, false if rejected
    public boolean withdraw(int amount) {
        if (amount <= 0 || amount > this.balance) {
            return false; // Rejected: invalid amount or insufficient funds
        }
        this.balance -= amount;
        return true;
    }
}
BankRunner.java 
public class BankRunner {
    public static void main(String[] args) {
        BankAccount acc = new BankAccount(1000);
        System.out.println("Initial Balance: $" + acc.getBalance());

        // 1. Valid deposit
        boolean d1 = acc.deposit(500);
        System.out.println("Deposit $500 result: " + d1 + " | Balance: $" + acc.getBalance());

        // 2. Invalid negative deposit
        boolean d2 = acc.deposit(-200);
        System.out.println("Deposit -$200 result: " + d2 + " | Balance: $" + acc.getBalance());

        // 3. Valid withdrawal
        boolean w1 = acc.withdraw(300);
        System.out.println("Withdraw $300 result: " + w1 + " | Balance: $" + acc.getBalance());

        // 4. Invalid overdraft withdrawal
        boolean w2 = acc.withdraw(2000);
        System.out.println("Withdraw $2000 result: " + w2 + " | Balance: $" + acc.getBalance());
    }
}
🖥 Console Output
Initial Balance: $1000 Deposit $500 result: true | Balance: $1500 Deposit -$200 result: false | Balance: $1500 Withdraw $300 result: true | Balance: $1200 Withdraw $2000 result: false | Balance: $1200
Figure 6.2: Before-and-after state transitions: Notice how the balance transitions from $1000 to $1500, to $1200, and rejects the $2000 overdraft without corrupting memory.
SECTION 07

7. The Four Java Access Levels

Java provides four distinct visibility levels to regulate which classes can see and invoke specific fields, methods, constructors, and classes. A common misconception among beginners is that there are four access keywords. In truth, there are three keywords (private, protected, public) and one default state (package-private, achieved by writing no keyword at all).

Figure 7.1: The scope boundaries of the four Java access levels, from the narrowest (private) to the broadest (public).
Figure 7.2: Complete Java Access Modifier Visibility Matrix across class, package, subclass, and global scopes.

Detailed Access Level Breakdown

Access Level Keyword Used Visible to Same Class? Visible to Same Package? Visible to Subclass (Diff Pkg)? Visible to Unrelated (Diff Pkg)?
private private ✓ Yes ✗ No ✗ No ✗ No
package-private (default) None (no keyword) ✓ Yes ✓ Yes ✗ No ✗ No
protected protected ✓ Yes ✓ Yes ✓ Yes (via inheritance) ✗ No
public public ✓ Yes ✓ Yes ✓ Yes ✓ Yes
💡 Crucial Protected Qualification

A subclass in a different package can access a protected member only through inheritance (accessing it via this.member, super.member, or inside its own subclass instances). It cannot access the protected member on an arbitrary instance of the superclass! For example, Book b = new Book(); b.isbn; called from an outside package is illegal even inside a subclass.

SECTION 08

8. Understanding Package-Private (Default) Access

When you declare a class member without writing public, private, or protected, Java assigns it package-private access (often colloquially referred to as "default access").

⚠ Common Beginner Mistake: There is No 'default' Keyword for Fields!

Do not write default int score = 10;. In Java, default is a keyword reserved for switch statements and default interface methods. Writing default on an ordinary field or class method will trigger a compile-time syntax error. Package-private access is defined by the absence of any access modifier keyword.

Figure 8.1: Package-private boundary: Classes within package 'school' can freely collaborate; classes in package 'office' are locked out.

Same-Package vs. Cross-Package Code Walkthrough

school/Student.java 
package school;

public class Student {
    // Package-private: NO access modifier written
    String name = "Alex"; 

    void display() {
        System.out.println("Student: " + name);
    }
}
✓ Same Package (school/Teacher.java)
package school;

public class Teacher {
    public void greet(Student s) {
        // LEGAL: in same package 'school'
        System.out.println(s.name);
        s.display();
    }
}

Result: Compiles and runs cleanly.

✗ Different Package (office/Accountant.java)
package office;
import school.Student;

public class Accountant {
    public void audit(Student s) {
        // COMPILE ERROR!
        System.out.println(s.name); 
    }
}

Error: name is not public in Student; cannot be accessed from outside package

SECTION 09

9. Understanding protected Access

The protected access modifier is specifically designed for framework and library inheritance. It provides a hybrid scope:

  1. It behaves like package-private for all classes within the same package.
  2. It extends visibility to subclasses located in different packages, allowing child classes to inherit and use the member.
Figure 9.1: Package and inheritance protected access: Textbook (subclass) inherits protected isbn across packages, while Reader (unrelated) is blocked.

Cross-Package Protected Demonstration

library/Book.java 
package library;

public class Book {
    public String title;
    protected String isbn; // PROTECTED: available to subclasses
    String shelfCode;      // Package-private
    private double cost;   // Private

    public Book(String title, String isbn, String shelfCode, double cost) {
        this.title = title;
        this.isbn = isbn;
        this.shelfCode = shelfCode;
        this.cost = cost;
    }
}
school/Textbook.java (Subclass in Different Package) 
package school;
import library.Book;

// Subclass in another package
public class Textbook extends Book {
    private String subject;

    public Textbook(String title, String isbn, String shelfCode, double cost, String subject) {
        super(title, isbn, shelfCode, cost);
        this.subject = subject;
    }

    public void printDetails() {
        System.out.println("Title: " + title);   // Legal: public
        System.out.println("ISBN:  " + isbn);    // Legal: inherited protected!
        // System.out.println(shelfCode);         // COMPILE ERROR: package-private outside package
        // System.out.println(cost);              // COMPILE ERROR: private to Book
    }
}
SECTION 10

10. Understanding public Access

The public access modifier offers the widest possible visibility. Any class in any package can access a public member, provided the declaring class itself is also accessible.

Figure 10.1: Public API vs. Private Implementation: Public methods serve as the stable steering wheel; private implementation is the hidden engine under the hood.

Why Public Methods Form the Class "Contract"

In software architecture, your public methods form a contract with external developers. When another developer writes code against your class, they rely on your public methods continuing to work consistently. Because your internal fields are private, you are free to refactor, rename, or optimize your data structures without breaking any external software that depends on your class!

Greeting.java 
public class Greeting {
    // Public method: universally accessible entry point
    public void sayHello(String name) {
        System.out.println("Hello, " + name + "! Welcome to CodeVerse Java.");
    }
}
SECTION 11

11. Access Modifiers in Fields, Methods, Constructors & Classes

Access modifiers do not apply solely to variables. They can be placed on four distinct structural elements of Java programs:

Figure 11.1: Complete anatomical skeleton showing where modifiers can be applied to top-level classes, fields, constructors, and methods.

1. Top-Level Classes

A top-level class (a class declared directly in a .java file, not nested inside another class) can only have two access levels:

  • public class MyClass: Accessible from any package. The filename must match the public class name (MyClass.java).
  • class MyClass (no modifier): Package-private. Accessible only within the same package.
  • Rule: A top-level class can never be declared private or protected.

2. Constructors

Constructors have access modifiers just like methods. The constructor's visibility dictates where new instances can be instantiated:

  • public MyClass(): Any class can instantiate this object with new MyClass().
  • protected MyClass(): Can only be called by classes in the same package or subclasses via super().
  • MyClass() (package-private): Can only be instantiated by classes in the same package.
  • private MyClass(): Cannot be instantiated from outside the class at all! (Used in utility classes with static methods, like java.lang.Math, or in the Singleton pattern).
SECTION 12

12. Encapsulation Does Not Mean Automatic Security

One of the most dangerous myths among computer science students is assuming that declaring a field private makes the software "secure" from hackers.

Figure 12.1: Encapsulation provides structural data integrity, not cybersecurity encryption or runtime access control against memory dumps.
🛡 Crucial Security Truths
  • Encapsulation protects against ACCIDENTAL BUGS, not MALICIOUS HACKERS: Access modifiers are enforced by the Java compiler during compilation. At runtime, tools like Java Reflection or memory debuggers can inspect private fields if security managers allow it.
  • The "Naive Getter/Setter" Trap: Mindlessly generating a public getter and public setter for every single private field provides zero encapsulation! If your setter takes any value without validation, it is functionally identical to making the field public.
  • Read-Only Fields: If an object has a unique identifier (like a student ID, transaction timestamp, or UUID), do not write a setter for it! Simply initialize it via the constructor and provide only a getter.

13. Common Mistakes and Debugging Guide

Mastering encapsulation requires learning to spot common compilation failures and logical anti-patterns. Study these 15 frequent pitfalls:

Figure 13.1: Encapsulation debugging triage: recognizing compiler error signatures for private access, field shadowing, and invalid modifier usage.
✗ Mistake 1: Accessing Private Field from Another Class
Employee e = new Employee();
e.salary = 50000; // Direct write

Cause: salary is private to Employee.

Fix: Call e.setSalary(50000);

✓ Correct Public Mutator
Employee e = new Employee();
e.setSalary(50000); // Handled by method

Result: Access permitted through public method contract.

✗ Mistake 2: Assuming Package-Private is Public
// In package school
class Student { String name; }
// In package office
s.name = "Amy"; // Compile Error!

Cause: Omitting modifier creates package-private, not public.

✓ Declare Explicitly Public or Add Getter
// If intended for cross-package use
public class Student {
    public String getName() { return name; }
}

Result: Cross-package callers use public methods.

✗ Mistake 3: Writing 'default' Keyword on Fields
public class Game {
    default int score = 100; // SYNTAX ERROR!
}

Cause: default is not an access modifier keyword for fields.

✓ Simply Omit the Modifier
public class Game {
    int score = 100; // Package-private
}

Result: Valid Java syntax.

✗ Mistake 4: Shadowing Assignment Bug (name = name)
public void setName(String name) {
    name = name; // Parameter assigns to itself!
}

Cause: Parameter shadows field; instance variable never changes.

✓ Qualify with this Keyword
public void setName(String name) {
    this.name = name; // Correct instance update
}

Result: The object's field receives the new value.

✗ Mistake 5: Mindlessly Generating Setters for Invariants
public class Account {
    private final String accountNumber;
    public void setAccountNumber(String acc) {
        this.accountNumber = acc; // DANGEROUS!
    }
}

Cause: Account numbers should never be re-assigned after creation.

✓ Read-Only Design (Omit Setter)
public class Account {
    private final String accountNumber;
    public Account(String num) { this.accountNumber = num; }
    public String getAccountNumber() { return accountNumber; }
}

Result: True immutability and protected integrity.

✗ Mistake 6: Getter Return Type Mismatch
private int age;
public String getAge() {
    return age; // Compile Error: int cannot be converted to String
}

Cause: Getter return type must match the field type.

✓ Matching Return Type
private int age;
public int getAge() {
    return age;
}

Result: Clean compile time type matching.

✗ Mistake 7: Forgetting Return Statement in Getter
public int getScore() {
    // Missing return statement error!
}

Cause: Non-void methods must return a value.

✓ Explicit Return
public int getScore() {
    return this.score;
}

Result: Returns the value to caller.

✗ Mistake 8: Top-Level Class Declared Private
private class MyHelper { ... } // COMPILE ERROR!

Cause: Top-level classes can only be public or package-private.

✓ Use Package-Private Top-Level Class
class MyHelper { ... } // Valid

Result: Top-level class accessible across same package.

✗ Mistake 9: Protected Cross-Package Arbitrary Access
// In package school, inside subclass Textbook
Book b = new Book(...);
System.out.println(b.isbn); // ERROR!

Cause: Protected members must be accessed via inheritance (this.isbn), not on foreign superclass instances.

✓ Access via Inherited Reference
// Inside Textbook subclass
System.out.println(this.isbn); // or super.isbn

Result: Allowed by Java cross-package inheritance rules.

✗ Mistake 10: Faulty Validation Logic
public void setPercentage(double p) {
    if (p >= 0 || p <= 100) { // BUG: Uses || instead of &&
        this.p = p; // Accepts -500 and 9999!
    }
}

Cause: With OR (||), any number satisfies at least one condition.

✓ Logical AND for Range Validation
public void setPercentage(double p) {
    if (p >= 0 && p <= 100) {
        this.p = p;
    }
}

Result: Both bounds strictly enforced.

✗ Mistake 11: Assuming Private Means No Access Inside Class
public class Pair {
    private int x;
    public void copyFrom(Pair other) {
        // Some believe other.x is illegal because x is private!
        this.x = other.x; // TOTALLY LEGAL!
    }
}

Cause: private is per-CLASS, not per-INSTANCE! Any Pair method can access private fields of any Pair instance.

✓ Legal Per-Class Access
// Perfectly legal and standard Java OOP practice
this.x = other.x;

Result: Encapsulation is enforced at the class boundary.

✗ Mistake 12: Assuming Access Modifiers Encrypt Data
// "My private password field cannot be read by anyone"

Cause: Bytecode reflection and debuggers can inspect RAM.

✓ Understand Scope vs. Security
// Encapsulation prevents design errors; 
// Use cryptography for true security.

Result: Accurate software architectural thinking.

✗ Mistake 13: Making All Members Public Lazily
public class Engine {
    public int sparkPlugFiringAngle; // Exposed!
}

Cause: External callers will couple to internal details.

✓ Expose High-Level Operations
public class Engine {
    private int firingAngle;
    public void start() { ... }
}

Result: Clean decoupling and maintainable architecture.

✗ Mistake 14: Confusing Encapsulation with Inheritance
// "Encapsulation means extending a parent class"

Cause: Extending a class is inheritance; bundling and hiding data is encapsulation.

✓ Proper Separation of OOP Concepts
// Encapsulation: private data + public methods
// Inheritance: superclass / subclass relationship

Result: Clear conceptual mastery.

✗ Mistake 15: Silent Failure in Setters Without Feedback
public void setAge(int age) {
    if (age >= 0) this.age = age;
    // If negative, caller never knows it failed!
}

Cause: Silent ignores can make bugs difficult to trace.

✓ Return Boolean or Log Error
public boolean setAge(int age) {
    if (age >= 0) { this.age = age; return true; }
    return false; // Clear feedback to caller
}

Result: Caller can verify if update succeeded.

SECTION 14

14. Real-World Mini Project: Encapsulated Student Record

Let us integrate everything into a complete, self-contained educational console application: Student Record Management System.

Figure 14.1: Real-world mini project class structure: StudentRecord encapsulates id and name as read-only fields, while marks is guarded by a validation update method.

Project Requirements & Invariants

  1. Immutable Fields: id and name must be set during object instantiation via the constructor and have getters, but NO setters.
  2. Guarded Mutable Field: marks must be private, initialized between 0 and 100, and updatable via updateMarks(int newMarks) which returns true on success and false on invalid input.
  3. Reporting: A display method summarizing the student record, letter grade, and status.
StudentRecordApp.java 
public class StudentRecordApp {

    // Encapsulated domain model
    static class StudentRecord {
        private final int id;        // Read-only identifier
        private final String name;   // Read-only name
        private int marks;           // Guarded mutable state

        public StudentRecord(int id, String name, int initialMarks) {
            this.id = id;
            this.name = name;
            if (initialMarks >= 0 && initialMarks <= 100) {
                this.marks = initialMarks;
            } else {
                this.marks = 0; // Safe fallback
            }
        }

        // Read-only accessors
        public int getId() { return id; }
        public String getName() { return name; }
        public int getMarks() { return marks; }

        // Controlled mutator with boolean feedback
        public boolean updateMarks(int newMarks) {
            if (newMarks >= 0 && newMarks <= 100) {
                this.marks = newMarks;
                return true; // Update accepted
            }
            return false; // Rejected: out of bounds
        }

        public void printSummary() {
            String grade = (marks >= 90) ? "A" : (marks >= 75) ? "B" : (marks >= 50) ? "C" : "F";
            System.out.println("ID: " + id + " | Name: " + name + " | Marks: " + marks + " | Grade: " + grade);
        }
    }

    public static void main(String[] args) {
        System.out.println("=== CODEVERSE STUDENT RECORD SYSTEM ===");
        
        // 1. Create a student with initial marks
        StudentRecord student = new StudentRecord(101, "Rohan Sharma", 78);
        student.printSummary();

        // 2. Perform a valid mark update
        System.out.println("\nAttempting valid update: 92 marks...");
        boolean ok1 = student.updateMarks(92);
        System.out.println("Update success? " + ok1);
        student.printSummary();

        // 3. Attempt an invalid mark update (negative)
        System.out.println("\nAttempting invalid update: -15 marks...");
        boolean ok2 = student.updateMarks(-15);
        System.out.println("Update success? " + ok2 + " (Safely rejected!)");
        student.printSummary();

        // 4. Attempt an invalid mark update (exceeding 100)
        System.out.println("\nAttempting invalid update: 125 marks...");
        boolean ok3 = student.updateMarks(125);
        System.out.println("Update success? " + ok3 + " (Safely rejected!)");
        student.printSummary();
    }

Technical Terminology Glossary

Term Definition
Encapsulation Bundling data and methods into a single class while restricting direct external access to maintain integrity.
Data Hiding Concealing internal variables using the private modifier so external code cannot mutate them directly.
Invariant A condition or rule that must always hold true for an object to be valid (e.g. marks >= 0 && marks <= 100).
Accessor (Getter) A public method that returns the current value of a private field without modifying it.
Mutator (Setter) A public method that accepts a new value, validates it against invariants, and updates the field.
Package-Private The default access level in Java when no modifier is written; accessible to any class in the same package.
Protected Access level permitting visibility to the declaring package and to subclasses in other packages via inheritance.
Public API The collection of public methods and constructors that an object exposes to external callers as its contract.
Field Shadowing When a method parameter has the identical name as an instance variable, requiring this.name to distinguish them.
Immutability An object design where fields are set once during construction and never modified (no setters provided).
