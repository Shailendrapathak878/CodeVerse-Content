Section 01

What Is the Java Stream API?

In modern enterprise software, virtually every application processes collections of data: filtering active users, computing total invoice amounts, sorting leaderboard scores, or grouping transactions by currency. Prior to Java 8, developers wrote multi-line imperative for loops and nested if statements with temporary mutable accumulators. The Java Stream API (introduced in Java 8 inside the java.util.stream package) revolutionized Java data processing by introducing a declarative, functional, and composable pipeline architecture.

🏫 Real-Life Analogy: The University Examination Processing Department

Imagine a university registrar's office processing raw semester marks for thousands of students: List<Integer> marks = List.of(35, 80, 45, 90, 25, 70);

In a manual office (imperative style), a clerk pulls student files one-by-one from physical storage, opens a ledger, writes down passing students in pencil, walks across the room to another clerk who sorts them by score, and finally calculates the class average using an adding machine.

In an automated conveyor-belt facility (Stream API style), the raw student file stays securely in the archive. A digital sensor feeds elements onto a high-speed conveyor belt. Specialised inline workstations perform operations on the fly:

  • Workstation 1 (Filter): Rejects any score below 40 marks.
  • Workstation 2 (Sort): Orders qualifying students from highest to lowest.
  • Workstation 3 (Collect): Packages the qualifying scores into a certified digital report.

The original student file is untouched, the workstations can be rearranged effortlessly, and the entire conveyor only moves when the final registrar demands the finished report!

Core Defining Characteristics of Java Streams

🚫 Not a Data Structure

A stream does not store elements. It conveys elements from a source (such as a List, Set, or array) through a computational pipeline.

🔄 Functional in Nature

An operation on a stream produces a result, but does not modify its source. Filtering a List produces a new stream of matching elements; the source list remains intact.

⏳ Lazy Evaluation

Many stream operations (such as filter() and map()) are evaluated lazily. Computation only begins when a terminal operation is invoked.

♻️ Single-Use Only

A stream cannot be reused once a terminal operation has consumed it. Attempting to traverse it again throws an IllegalStateException.

One of the most frequent misconceptions among junior Java developers is treating a Stream as "just an advanced collection". While both deal with sequences of data, their architectural objectives, memory profiles, and execution lifecycles are fundamentally different.

Verifying Source Immutability (Non-Interference)

The following example demonstrates that filtering and transforming a stream leaves the source collection completely unmodified:

CollectionImmutabilityDemo.java Java 17+ 
import java.util.List;

public class CollectionImmutabilityDemo {
    public static void main(String[] args) {
        // Source list remains untouched
        List<String> originalLanguages = List.of("Java", "Kotlin", "Scala", "Groovy");

        // Process through a stream pipeline
        List<String> filteredList = originalLanguages.stream()
            .filter(lang -> lang.startsWith("K") || lang.startsWith("S"))
            .map(String::toUpperCase)
            .toList();

        System.out.println("Original Source List : " + originalLanguages);
        System.out.println("Pipeline Result List : " + filteredList);
    }
}
🖥 Output
Original Source List : [Java, Kotlin, Scala, Groovy]
Pipeline Result List : [KOTLIN, SCALA]
💡 Non-Interference Rule
Stream pipelines must never modify the data source that feeds them while the stream is executing. Modifying the backing collection during stream execution causes ConcurrentModificationException or undefined non-deterministic behaviour.
Section 03

Stream Pipeline Architecture: Source, Intermediate, and Terminal

Every Java stream operation is expressed as a pipeline consisting of exactly three distinct structural stages:

  1. A Stream Source: Generates or provides the input elements (e.g., a Collection, an array, an I/O channel, or a generator function).
  2. Zero or More Intermediate Operations: Transform, filter, sort, or slice the stream into another stream (e.g., filter(), map(), sorted()). These are always lazy.
  3. Exactly One Terminal Operation: Consumes the stream, triggers pipeline execution, and produces a concrete result (e.g., a List, a count, a primitive sum, or an applied side effect).
📊 Visual 3: Three-Stage Pipeline Architecture
Figure 24.3: Anatomy of a stream pipeline. Intermediate operations return a new lazy stream description. The terminal operation initiates the execution pull.

Detailed Pipeline Trace

Consider the following canonical pipeline:

PipelineTraceDemo.java Java 17+ 
import java.util.List;

public class PipelineTraceDemo {
    public static void main(String[] args) {
        List<Integer> result = List.of(10, 15, 20, 25, 30)
            .stream()                 // 1. Source: Stream<Integer>
            .filter(n -> n >= 20)     // 2. Intermediate 1: Stream<Integer> [20, 25, 30]
            .map(n -> n * 2)          // 3. Intermediate 2: Stream<Integer> [40, 50, 60]
            .toList();                // 4. Terminal: List<Integer>

        System.out.println("Result: " + result);
    }
}
🖥 Output
Result: [40, 50, 60]
⚡ Pipeline Fusion & Single-Pass Traversal
Java's stream implementation does not create intermediate temporary lists in memory between filter() and map(). Instead, it fuses the intermediate operations into a single continuous pass. Each individual element travels through the entire pipeline one-by-one!
Section 04

Traditional Loops vs. Stream API

To understand the paradigm shift, let's solve the exact same business requirement using both traditional imperative loops and the declarative Stream API: "Given a list of integers, find all even numbers greater than 10, square each number, and collect the results into a new list."

📊 Visual 4: Imperative Loop vs. Declarative Stream Pipeline
Figure 24.4: Loop vs. Stream comparison. Imperative code mixes traversal, condition checks, mutation, and state management. Streams declare pure functional transformations.
Imperative Style (Pre-Java 8)

Traditional For-Loop with Mutable State

List<Integer> numbers = List.of(2, 8, 12, 15, 20, 7);
List<Integer> result = new ArrayList<>();

for (Integer n : numbers) {
    if (n > 10 && n % 2 == 0) {
        int squared = n * n;
        result.add(squared);
    }
}
System.out.println(result); // [144, 400]
  • How vs What: Dictates exactly how to iterate (index or cursor).
  • State Mutation: Requires an external, mutable ArrayList accumulator.
  • Parallelization: Extremely difficult and bug-prone to parallelize safely.
Declarative Style (Modern Java)

Functional Stream Pipeline

List<Integer> numbers = List.of(2, 8, 12, 15, 20, 7);

List<Integer> result = numbers.stream()
    .filter(n -> n > 10)
    .filter(n -> n % 2 == 0)
    .map(n -> n * n)
    .toList();

System.out.println(result); // [144, 400]
  • What vs How: Declares what transformations are required.
  • Zero Mutation: No intermediate accumulator variables or side effects.
  • Trivial Parallelism: Can switch to numbers.parallelStream() instantly.
⚠ Are Streams Automatically Faster Than Loops?
No! For simple iterations over small in-memory arrays or primitive collections, a standard traditional for loop often has lower abstraction overhead and executes slightly faster. The Stream API's primary advantages are readability, composability, maintainability, and clean parallelization for non-trivial datasets. Always choose clarity first, and benchmark with JMH when micro-optimizations are truly necessary.

Section 07

Filtering Data: filter() Operation

The filter() intermediate operation accepts a Predicate<T> (a functional interface whose abstract method test(T t) returns boolean). For each element flowing through the stream, filter() evaluates the predicate:

  • If the predicate evaluates to true, the element is allowed to flow downstream.
  • If the predicate evaluates to false, the element is immediately discarded from the pipeline.
📊 Visual 10: Step-by-Step Predicate Filtering
Figure 24.10: The filter() sieve. Elements meeting the condition (score ≥ 40) pass through; failing elements are dropped.

University Pass/Fail Threshold Demonstration

Let's filter our sample student marks against an illustrative threshold of 40 marks:

FilterDemo.java Java 17+ 
import java.util.List;

public class FilterDemo {
    public static void main(String[] args) {
        List<Integer> marks = List.of(35, 80, 45, 90, 25, 70);

        List<Integer> passed = marks.stream()
            .filter(mark -> mark >= 40)
            .toList();

        System.out.println("All Marks    : " + marks);
        System.out.println("Passed Marks : " + passed);
    }
}
🖥 Output
All Marks    : [35, 80, 45, 90, 25, 70]
Passed Marks : [80, 45, 90, 70]
Element Value Predicate Evaluation (mark >= 40) Pipeline Action
35 35 >= 40 → false Rejected (Discarded)
80 80 >= 40 → true Passed Downstream
45 45 >= 40 → true Passed Downstream
90 90 >= 40 → true Passed Downstream
25 25 >= 40 → false Rejected (Discarded)

💡 Chaining Multiple Filters
You can chain multiple filter() calls sequentially (e.g., .filter(m -> m >= 40).filter(m -> m <= 80)), which is logically equivalent to a compound boolean expression (.filter(m -> m >= 40 && m <= 80)).

Transforming Data: map() Operation

The map() intermediate operation performs a 1-to-1 transformation. It takes a functional Function<T, R> and applies it to every element in the stream, producing a new Stream<R> where each original element of type T has been transformed into a corresponding value of type R.

📊 Visual 11: 1-to-1 Element Transformation via map()
Figure 24.11: The map() transformation. Every input element produces exactly one transformed output element. Stream length is preserved.
MapDemo.java Java 17+ 
import java.util.List;

public class MapDemo {
    public static void main(String[] args) {
        List<String> names = List.of("aman", "riya", "kabir");

        // Transform lowercase strings to uppercase using a method reference
        List<String> uppercaseNames = names.stream()
            .map(String::toUpperCase)
            .toList();

        System.out.println("Original Names  : " + names);
        System.out.println("Uppercase Names : " + uppercaseNames);
    }
}
🖥 Output
Original Names  : [aman, riya, kabir]
Uppercase Names : [AMAN, RIYA, KABIR]

Common Mapping Transformations

  • Number → Square: n -> n * n (converts 4 to 16).
  • String → Length: String::length (transforms "Java" to 4).
  • Domain Object → Field: Student::getName (extracts String name from Student).
  • Price → Discounted Price: price -> price * 0.90 (applies a 10% discount).

filter()

Cardinality: 0 to N elements (reduces or maintains stream size).

Type: Preserves element type (Stream<T> → Stream<T>).

Function: Evaluates boolean predicate.

map()

Cardinality: Exactly N elements (preserves stream size).

Type: Can change element type (Stream<T> → Stream<R>).

Function: Applies transformation function.

Section 09

Flattening Nested Data: flatMap() Operation

While map() performs a 1-to-1 transformation, flatMap() performs a 1-to-Many transformation followed by flattening. If each element in your stream contains another collection or stream (such as a List<List<String>>), calling map() would result in a nested Stream<Stream<String>>. flatMap() unpacks and combines those inner streams into a single, uniform Stream<String>.

🏫 Analogy: University Classrooms to Master Roll Call

A university building contains several lecture halls (Classrooms). Each classroom holds its own roster of attending students:

Classroom A: ["Aman", "Riya"]
Classroom B: ["Kabir", "Neha"]

If you ask the campus security team for a single list of all students currently on campus, you don't want a "list of lists of names" ([["Aman", "Riya"], ["Kabir", "Neha"]]). You want a single, flat, continuous attendance roster: ["Aman", "Riya", "Kabir", "Neha"]. That flattening operation is precisely what flatMap() performs!

📊 Visual 12: 1-to-N Nested List Flattening
Figure 24.12: The flatMap() operation flattens nested lists of students into a single continuous stream.
FlatMapClassroomDemo.java Java 17+ 
import java.util.List;

public class FlatMapClassroomDemo {
    public static void main(String[] args) {
        List<List<String>> classrooms = List.of(
            List.of("Aman", "Riya"),
            List.of("Kabir", "Neha")
        );

        // Flatten nested student lists into a single master stream
        List<String> allStudents = classrooms.stream()
            .flatMap(classroomList -> classroomList.stream())
            .toList();

        System.out.println("Flattened Student Roster: " + allStudents);
    }
}

Unlike filter() and map() which process elements purely one-by-one, sorted() is a stateful intermediate operation. It must internally buffer all upstream elements before it can emit even the first sorted element. Never call sorted() on an unbounded infinite stream without a preceding limit()!

Lazy Evaluation & Short-Circuiting Mechanics

In Java streams, intermediate operations are lazy: invoking .filter() or .map() does not iterate through the data immediately. Instead, they register processing steps in a pipeline descriptor. Computation only starts when a terminal operation demands results.

📊 Visual 16: Lazy Pull-Based Processing Timeline
Figure 24.16: Elements are pulled one-by-one on demand by the terminal operation.

Demonstrating Laziness with Execution Logging

Watch what happens when we attach logging statements inside intermediate operations:

LazyEvaluationLoggingDemo.java Java 17+ 
import java.util.List;

public class LazyEvaluationLoggingDemo {
    public static void main(String[] args) {
        List<String> names = List.of("Aman", "Riya", "Kabir", "Deepak");

        System.out.println(">>> 1. Building stream pipeline (NO execution yet)...");
        var stream = names.stream()
            .filter(name -> {
                System.out.println("  [filter] evaluating: " + name);
                return name.length() > 4;
            })
            .map(name -> {
                System.out.println("  [map] transforming: " + name);
                return name.toUpperCase();
            });

        System.out.println(">>> 2. Invoking terminal operation (findFirst)...");
        String firstMatch = stream.findFirst().orElse("NONE");

        System.out.println(">>> 3. Result: " + firstMatch);
    }
}
🖥 Output
>>> 1. Building stream pipeline (NO execution yet)...
>>> 2. Invoking terminal operation (findFirst)...
  [filter] evaluating: Aman
  [filter] evaluating: Riya
  [filter] evaluating: Kabir
  [map] transforming: Kabir
>>> 3. Result: KABIR
📊 Visual 17: Short-Circuiting Early Termination
Figure 24.17: Once findFirst() finds a match ("Kabir"), "Deepak" is never touched!
⚡ Key Takeaway: Short-Circuiting Saves Processing
Notice that "Deepak" was never evaluated by the filter or map operations! Because findFirst() is a short-circuiting terminal operation, processing halted as soon as the first satisfying element passed through the pipeline.

Terminal Operations & Predicate Searching

A terminal operation initiates stream consumption and closes the pipeline. Once a terminal operation is called, the stream is spent and cannot be used again:

Consumer Actions: forEach() vs. forEachOrdered()

forEach() applies a consumer action to every element. For sequential streams, encounter order is respected. However, in parallel streams, forEach() executes out-of-order for maximum throughput. Use forEachOrdered() if encounter order must strictly be preserved across threads.

📊 Visual 19: forEach() Action Sink vs. map() Transformation

Searching & Matching Operations

Method Return Type Short-Circuiting? Behavior Description

Defensive Handling with Optional<T>

Search operations (such as findFirst(), findAny(), min(), and max()) return an Optional<T> instead of a raw reference or null. This forces developers to acknowledge that a match might not exist, preventing disastrous NullPointerException crashes.

📊 Visual 28: Optional<T> Type-Safe Null Defense
Figure 24.28: Optional explicitly encapsulates presence vs. absence, enforcing safe fallback strategies.
OptionalStreamsDemo.java Java 17+ 
import java.util.List;
import java.util.Optional;

public class OptionalStreamsDemo {
    public static void main(String[] args) {
        List<Integer> scores = List.of(10, 20, 30);

        // Search for a value greater than 100 (none exists)
        Optional<Integer> match = scores.stream()
            .filter(n -> n > 100)
            .findFirst();

        System.out.println("Is present: " + match.isPresent());

        System.out.println("Value with default: " + valueWithDefault);

        // Safe fallback using orElseGet (supplier called only when empty)
        int valueWithSupplier = match.orElseGet(() -> computeFallback());
        System.out.println("Value with supplier: " + valueWithSupplier);
    }

    private static int computeFallback() {
        return -1;
    }
}

The 3 Critical Mathematical Rules of Reduction

  1. Identity Element: Must satisfy accumulator.apply(identity, x) == x for all x. For addition, identity is 0; for multiplication, identity is 1; for string concatenation, identity is "".

Parallel Streams: Concurrency via Fork/Join

One of the most celebrated features of the Stream API is trivial parallelization. Changing .stream() to .parallelStream() automatically decomposes data across multiple worker threads managed by the JVM's common Fork/Join pool (ForkJoinPool.commonPool()).

📊 Visual 31: Sequential vs. Parallel Fork/Join Architecture
Figure 24.31: Parallel streams partition data into chunks, process them concurrently across worker threads, and combine the results.
Aspect Sequential Stream (.stream()) Parallel Stream (.parallelStream())

Top 20 Stream API Pitfalls & Diagnostic Guide

Because functional stream pipelines operate differently from traditional procedural code, developers frequently encounter subtle traps involving laziness, consumption lifecycles, boxing, and concurrency. Here are the 20 most critical Stream API pitfalls and their solutions:

📊 Visual 34: Stream API Anti-Patterns Diagnostic Map
Figure 24.34: Taxonomy of stream pitfalls: lifecycle bugs, transformation misunderstandings, reduction errors, and parallel race conditions.
Pitfall 01

Forgetting the Terminal Operation (The "Ghost" Pipeline)

The Mistake: Stacking intermediate operations without attaching a terminal operation. Because streams are lazy, zero elements are processed!

✗ Broken Code 
List<String> names = List.of("Aman", "Riya");
// BUG: No terminal operation! Filter never runs!
names.stream().filter(n -> {
    System.out.println("Processing: " + n);
    return n.startsWith("A");
});
// Output: (Silent - Nothing printed at all!)
✓ Corrected Code 
List<String> names = List.of("Aman", "Riya");
// Fixed: toList() triggers execution!
List<String> filtered = names.stream()
    .filter(n -> n.startsWith("A"))
    .toList();
System.out.println(filtered); // [Aman]

Debugging Tip: If your pipeline appears completely dormant, verify that it ends with an eager terminal operation (e.g., .toList(), .count(), .forEach()).

Pitfall 02

Reusing a Consumed Stream (IllegalStateException)

The Mistake: Attempting to call a second terminal operation on an already consumed stream.

✗ Broken Code 
Stream<String> stream = List.of("Java", "Go").stream();
long count = stream.count(); // Stream consumed here!
// CRASH: IllegalStateException: stream has already been operated upon or closed
stream.forEach(System.out::println);
✓ Corrected Code 
List<String> langs = List.of("Java", "Go");
long count = langs.stream().count();
// Fixed: Create a fresh stream from the source collection!
langs.stream().forEach(System.out::println);

Debugging Tip: Streams are single-use disposable conduits. Never store a Stream<T> in a variable for multiple queries; create a new stream from the source collection.

Pitfall 03

Assuming filter() Transforms Elements

The Mistake: Trying to modify elements inside a filter() predicate.

✗ Broken Code 
// BUG: filter() takes Predicate (returns boolean), not transformation!
List<String> res = List.of("aman")
    .stream()
    // .filter(s -> s.toUpperCase()) // COMPILE ERROR: type mismatch
    .toList();
✓ Corrected Code 
// Fixed: Use map() to transform values!
List<String> res = List.of("aman")
    .stream()
    .map(String::toUpperCase)
    .toList();
System.out.println(res); // [AMAN]

Debugging Tip: filter() is a sieve (drops failing elements); map() is a converter (changes element values or types).

Pitfall 04

Assuming map() Filters Elements

The Mistake: Returning null inside map() expecting it to remove items from the stream.

✗ Broken Code 
List<Integer> nums = List.of(1, 2, 3, 4);
List<Integer> evens = nums.stream()
    .map(n -> n % 2 == 0 ? n : null) // Emits [null, 2, null, 4]!
    .toList();
✓ Corrected Code 
List<Integer> nums = List.of(1, 2, 3, 4);
List<Integer> evens = nums.stream()
    .filter(n -> n % 2 == 0) // Properly discards odds
    .toList();
System.out.println(evens); // [2, 4]

Debugging Tip: map() always preserves the stream length 1-to-1. To discard items, use filter().

Pitfall 05

Confusing map() with flatMap()

The Mistake: Calling map() on nested collections, producing a Stream<List<T>> instead of a flat Stream<T>.

✗ Broken Code 
List<List<String>> nested = List.of(List.of("A"), List.of("B"));
var res = nested.stream().map(List::stream).toList();
// res is List<Stream<String>> (Unflattened!)
✓ Corrected Code 
List<List<String>> nested = List.of(List.of("A"), List.of("B"));
List<String> flat = nested.stream()
    .flatMap(List::stream)
    .toList();
System.out.println(flat); // [A, B]

Debugging Tip: If your pipeline ends up with Stream<Stream<T>>, replace map with flatMap.

Pitfall 06

Using forEach() when a Transformed Collection is Desired

The Mistake: Iterating with forEach() to manually append into an external List.

✗ Anti-Pattern Code 
List<String> upper = new ArrayList<>();
List.of("a", "b").stream().forEach(s -> upper.add(s.toUpperCase()));
✓ Idiomatic Code 
List<String> upper = List.of("a", "b").stream()
    .map(String::toUpperCase)
    .toList(); // Clean, functional, zero mutation!

Debugging Tip: Reserve forEach() strictly for terminal side effects like System.out.println() or writing to a socket.

Pitfall 07

Expecting Stream.toList() to Return a Mutable List

The Mistake: Calling .add() or .remove() on the result of Stream.toList().

✗ Broken Code 
List<String> list = List.of("A", "B").stream().toList();
list.add("C"); // CRASH: UnsupportedOperationException!
✓ Corrected Code 
// Fixed: Collect into a mutable ArrayList if mutation is needed
List<String> mutableList = List.of("A", "B").stream()
    .collect(Collectors.toCollection(ArrayList::new));
mutableList.add("C"); // Works perfectly!

Debugging Tip: Stream.toList() returns an unmodifiable list. If you need mutation, collect to new ArrayList<>().

Pitfall 08

Calling Optional.get() Without Checking

The Mistake: Blindly calling .get() on an empty search result.

✗ Broken Code 
Optional<Integer> opt = List.of(1, 2).stream()
    .filter(n -> n > 10).findFirst();
int val = opt.get(); // CRASH: NoSuchElementException: No value present!
✓ Corrected Code 
int val = List.of(1, 2).stream()
    .filter(n -> n > 10)
    .findFirst()
    .orElse(0); // Safe fallback value!

Debugging Tip: Replace raw get() calls with orElse(), orElseGet(), or ifPresent().

Pitfall 09

Using an Incorrect Identity in reduce()

The Mistake: Using an identity that distorts mathematical aggregation.

✗ Broken Code 
// BUG: Identity for multiplication should be 1, not 0!
int product = List.of(2, 3, 4).stream()
    .reduce(0, (a, b) -> a * b); // Returns 0! (0 * 2 * 3 * 4)
✓ Corrected Code 
// Fixed: Identity for multiplication is 1
int product = List.of(2, 3, 4).stream()
    .reduce(1, (a, b) -> a * b); // Returns 24!

Debugging Tip: Identity I must satisfy I op x == x for all values x.

Pitfall 10

Using a Non-Associative Accumulator in Parallel Reduction

The Mistake: Reducing with subtraction or division in parallel streams.

✗ Broken Code 
// BUG: Subtraction is NOT associative: (a - b) - c != a - (b - c)
int diff = List.of(1, 2, 3, 4).parallelStream()
    .reduce(0, (a, b) -> a - b); // Non-deterministic output!
✓ Corrected Code 
// Fixed: Subtraction should be done sequentially or transformed to addition
int sum = List.of(1, 2, 3, 4).parallelStream()
    .reduce(0, Integer::sum); // Associative & deterministic!

Debugging Tip: Parallel reduction operations must strictly satisfy the associative mathematical property.

Pitfall 11

Modifying Shared Mutable State in Parallel Streams

The Mistake: Mutating an unsynchronized ArrayList or primitive counter from concurrent worker threads.

✗ Broken Code 
List<Integer> bad = new ArrayList<>();
IntStream.rangeClosed(1, 1000).parallel().forEach(bad::add);
// Data corruption or ArrayIndexOutOfBoundsException!
✓ Corrected Code 
List<Integer> good = IntStream.rangeClosed(1, 1000)
    .parallel()
    .boxed()
    .toList(); // Thread-safe functional collection!

Debugging Tip: Treat lambdas in stream pipelines as pure mathematical functions without external side-effect mutation.

Pitfall 12

Assuming Parallel Stream Execution Order

The Mistake: Relying on forEach() to preserve encounter order in parallel execution.

✗ Out-of-Order Behavior 
List.of(1, 2, 3, 4).parallelStream()
    .forEach(System.out::print); // Might print 3142 or 2413!
✓ Preserved Order 
List.of(1, 2, 3, 4).parallelStream()
    .forEachOrdered(System.out::print); // Always prints 1234!

Debugging Tip: Use forEachOrdered() when encounter order is non-negotiable across parallel threads.

Pitfall 13

Assuming Intermediate Operations Execute Immediately

The Mistake: Expecting operations to run at the point where they are declared in code.

Correction: Remember laziness: intermediate methods simply configure the pipeline. Execution only happens during terminal consumption.

Pitfall 14

Using peek() for Essential Business Logic

The Mistake: Mutating records or writing to databases inside peek().

Correction: The Javadoc notes the compiler optimizer can omit peek() if terminal output is unaffected. Use peek() exclusively for debugging logs.

Pitfall 15

Sorting When the Result Does Not Require Ordering

The Mistake: Adding .sorted() before .max() or .count().

Correction: .sorted() buffers all items and has O(N log N) complexity. Use .max() directly for O(N) single-pass computation.

Pitfall 16

Creating Unbounded Streams Without a Limit

The Mistake: Calling Stream.generate() or Stream.iterate() without .limit() before calling .toList() or .count().

Correction: Always insert limit(n) or a terminating predicate (takeWhile) to bound infinite streams.

Pitfall 17

Forgetting That count() Returns long

The Mistake: Assigning stream.count() directly to an int without casting.

Correction: Declare the receiving variable as long total = stream.count();.

Pitfall 18

Misusing Primitive-Stream Conversions

The Mistake: Calling .map() instead of .mapToInt() when trying to compute numeric sums or statistics.

Correction: Stream<Integer> does not have .sum(). Use .mapToInt(Integer::intValue).sum().

Pitfall 19

Confusing findFirst() and findAny()

The Mistake: Using findFirst() in parallel streams where any matching element would suffice, incurring significant thread coordination costs.

Correction: In parallel streams, prefer findAny() unless encounter order is strictly necessary.

Pitfall 20

Assuming Streams Automatically Modify the Source Collection

The Mistake: Expecting sourceList.stream().filter(...) to delete non-matching items from sourceList.

Correction: Streams never modify the source collection. To remove elements in-place, use sourceList.removeIf(predicate).
