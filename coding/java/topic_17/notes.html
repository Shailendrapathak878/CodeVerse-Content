Section 01 📁 Namespace & Code Organization

1. What Is a Java Package?

In Java, a package is a named container that groups related classes, interfaces, enumerations, and annotations under a unique namespace. Much like folders on your computer keep documents organized, Java packages organize classes, prevent naming collisions, and establish architectural access boundaries.

📖 Formal Definition

A package is a namespace mechanism used in Java to group related types together, control access permissions across boundaries, and uniquely identify classes via their Fully Qualified Class Name (FQCN).

Real-Life Analogy: College Departments

Imagine a large university campus. The college doesn't throw every student, teacher, classroom, and ledger into a single giant warehouse. Instead, it is partitioned into distinct departments:

  • Computer Science (CSE) manages computer lab schedules, programming syllabi, and CSE student enrollments.
  • Library Services manages catalog books, borrowing checkouts, and overdue fines.
  • Finance & Accounts manages tuition billing, payment receipts, and fee audits.

Java packages work identically. We group CSE code into college.cse, library code into college.library, and financial code into college.accounts.

Visual 1: College Application Namespace Architecture

Figure 1.1: Visual representation of how packages create distinct architectural domains for related Java classes.

Introductory Code Example: Defining a Package

To declare that a class belongs to a package, write the package keyword followed by the package identifier as the very first non-comment statement in your .java file.

src/college/cse/Student.java Java 
package college.cse;

public class Student {
    public void display() {
        System.out.println("CSE Student");
    }
}
Expected Output When Invoked from Main:
CSE Student

Why Do We Need Packages in Java?

1. Eliminating Naming Collisions

In a large enterprise project with hundreds of engineers, two developers might independently create a class named Student (e.g., an academic student in CSE vs. an art student in Fine Arts). Packages ensure both can coexist peacefully because their Fully Qualified Class Names are distinct: college.cse.Student versus college.arts.Student.

2. Establishing Access Boundaries

Packages aren't just cosmetic folders; they form an active access-control boundary. Java allows package members to share package-private methods and variables that remain completely invisible and shielded from the outside world.

3. Discoverability & Maintainability

Finding a utility class among 10,000 files in a single folder is impossible. With packages, you immediately know where to look: networking code lives in com.app.net, database models live in com.app.model, and UI components live in com.app.ui.

4. Enterprise Modular Distribution

Packages allow third-party libraries (like Spring, Google Guava, and Jackson JSON) to bundle their classes into JAR files without polluting your application's global namespace.

Section 02 📁 File System & Classpath

2. Packages and Directory Structure

In standard Java development, there is an exact, 1-to-1 relationship between the package declaration in your source file and the folder hierarchy on your disk.

The Golden Rule of Java Package Mapping

Each period (.) in a package name represents a subdirectory in the file system: 

package college.cse;
// MUST be saved in: src/college/cse/Student.java
Visual 3: Directory Tree to Package Declaration Mirroring

Figure 2.1: The package declaration in Java source mirrors the folder path on disk.

Conventional Project Layout

Professional Java projects (whether managed by Maven, Gradle, IntelliJ IDEA, Eclipse, or VS Code) separate human-editable source files (.java) from compiler-generated bytecode (.class): 

project/
├── src/                          <-- Source Root (-sourcepath)
│   └── college/
│       ├── cse/
│       │   └── Student.java       <-- package college.cse;
│       └── app/
│           └── Main.java          <-- package college.app;
└── bin/                          <-- Bytecode Output (-d)
    └── college/
        ├── cse/Student.class
        └── app/Main.class

Compiling and Running from the Terminal

Understanding how the compiler and runtime locate packaged classes from the command line demystifies the magic performed by IDEs:

Terminal Command Line Workflow Bash / PowerShell 
# Step 1: Navigate to the project root directory
cd project

# Step 2: Compile with the -d (destination directory) flag
# The compiler automatically creates the subfolders inside bin/
javac -d bin src/college/cse/Student.java src/college/app/Main.java

# Step 3: Run using the -cp (classpath) flag, specifying the Fully Qualified Class Name
java -cp bin college.app.Main
Visual 4: Compilation (-d) and Execution (-cp) Lifecycle

Figure 2.2: How javac -d translates source paths into structured bytecode folders and how java -cp resolves the FQCN.

⚠ Critical Command-Line Mistake

When executing a packaged class with java, never append .class and never use folder slashes (/). You must pass the Fully Qualified Class Name using dots:

✗ WRONG java -cp bin college/app/Main.class
✓ CORRECT java -cp bin college.app.Main

💡 Packages Are Namespaces, Not Security Sandboxes

A common student misconception is believing that creating a package named secure.vault somehow encrypts or cryptographically isolates the code inside. Packages are purely logical namespaces and compilation access boundaries, not hardware sandboxes.

Section 04 🔍 Type Resolution & Static Imports

4. Import Statements

When a class needs to use a type declared in another package, you have two choices: write out the complete Fully Qualified Class Name every time, or write an import statement at the top of your file to use its simple name.

The Four Ways to Access External Classes

Approach A: Single Type Import (Recommended)

Imports exactly one specific class into the file's namespace:

import java.util.ArrayList;

public class Demo {
    ArrayList<String> list = new ArrayList<>();
}

Approach B: Wildcard Import on Demand (*)

Imports all accessible public types in the target package:

import java.util.*;

public class Demo {
    Scanner sc = new Scanner(System.in);
    ArrayList<Integer> nums = new ArrayList<>();
}

Note: The wildcard * has zero performance cost at runtime! It only tells the compiler where to search during compilation. However, it does not import subpackages (e.g. java.util.* does not import java.util.regex.*).

Approach C: Fully Qualified Class Name (FQCN)

Bypasses imports entirely by writing the complete package path inline:

public class Demo {
    java.time.LocalDate date = java.time.LocalDate.now();
}

This approach is essential when two imported packages contain classes with the identical simple name (e.g., java.util.Date versus java.sql.Date).

Approach D: Static Import

Introduced in Java 5, a static import allows static fields and methods to be referenced directly without qualifying them with their owning class name:

StaticImportDemo.java Java 
import static java.lang.Math.PI;
import static java.lang.Math.sqrt;

public class StaticImportDemo {
    public static void main(String[] args) {
        // Accessing static members directly without 'Math.'
        System.out.println(PI);
        System.out.println(sqrt(25));
    }
}
Exact Output:
3.141592653589793
5.0

Section 05 🏠 Unnamed Package & Limitations

5. The Default (Unnamed) Package

When a .java file omits the package statement entirely, the Java compiler automatically assigns all classes within that file to an unnamed package, commonly referred to as the default package.

Hello.java (No package header) Java 
// Notice: No package declaration here!
public class Hello {
    public static void main(String[] args) {
        System.out.println("Hello Java");
    }
}
Expected Output:
Hello Java

Why Does the Default Package Exist?

The default package exists solely for beginner convenience and rapid prototyping. When a student writes their very first HelloWorld.java, Java does not force them to understand package trees, directory structures, or classpath flags on day one.

⚠ The Fatal Limitation of the Default Package

Classes in a named package CANNOT import or use classes from the default package!

Because the default package has no name identifier, it is impossible to write an import statement pointing to it. If you have package college.cse;, you can never access a class in the unnamed package.

Section 06 🔒 Encapsulation & Shielding

6. What Is Access Control?

In software engineering, access control defines the rules governing which classes, methods, and variables can be seen and invoked by other parts of the codebase. It is the practical language mechanism that powers Object-Oriented Encapsulation.

Real-Life Analogy: College Information Classification

  • Public (Notice Board): The college campus map, calendar holidays, and exam timetable are posted on the front gate notice board. Anyone can view them.
  • Protected (Department Sub-Units): Department equipment (like oscilloscope hardware) is accessible to CSE professors and their specialized research scholars.
  • Package-Private (Internal Office): Teacher meeting minutes and draft exam papers are accessible only to staff inside the CSE department office. External visitors cannot see them.
  • Private (Principal's Personal Safe): Sealed exam question keys and master system passwords reside in the principal's locked safe. No one outside that room can touch them directly.
Visual 9: The 4 Expanding Spheres of Java Visibility

Figure 6.1: Concentric boundaries of Java visibility from the restrictive private core to the universal public realm.

Why Unrestricted Access Destroys Codebases

Imagine if every variable in a 100,000-line bank application was marked public. Any junior developer could write: 

account.balance = -9999999; // Corrupted state! No validation!

By restricting access to fields and requiring external callers to pass through validated public methods, we protect the structural integrity of our data models.

Section 08 🌎 Universal Exposure

8. The public Access Modifier

Members marked public have unrestricted visibility across the entire Java program, provided their containing class is also accessible. Public methods define the public contract (API) of your software modules.

Visual 11: Public Access Across Package Boundaries

Figure 8.1: A public class and its public methods can be imported and executed from any foreign package.

Code Walkthrough: Multi-Package Public Invocation

src/college/cse/Student.java Java 
package college.cse;

public class Student {
    public String name = "Aman";

    public void displayName() {
        System.out.println(name);
    }
}
src/college/app/PublicMain.java Java 
package college.app;

import college.cse.Student; // Importing the public class

public class PublicMain {
    public static void main(String[] args) {
        Student s = new Student();
        s.displayName(); // Accessing the public method
    }
}
Exact Output:
Aman
⚠ Architectural Best Practice: Avoid Public Mutable Fields

While public String name = "Aman"; compiles cleanly, making mutable fields public violates OOP encapsulation. Anyone could reassign s.name = null;. Keep fields private and provide public getter/setter methods with validation instead.

Section 09 📦 Default Package Boundary

9. Package-Private (Default) Access

When you declare a class member without writing public, protected, or private, Java applies package-private access. The member is visible to every class in the same package, but strictly invisible to all classes outside.

Visual 12: Package-Private Boundary Enforcement

Figure 9.1: Package-private members are freely shared within their package home, but compiler-shielded from external packages.

Code Example: Package-Private Member Declaration

src/college/cse/Student.java Java 
package college.cse;

public class Student {
    // No access modifier keyword = package-private
    String department = "CSE";

    void showDepartment() {
        System.out.println(department);
    }
}
src/college/cse/DepartmentPeer.java (Same Package) Java 
package college.cse;

public class DepartmentPeer {
    public static void main(String[] args) {
        Student s = new Student();
        // ✓ ALLOWED: Same package access works seamlessly
        System.out.println(s.department);
        s.showDepartment();
    }
}
✗ External Package Access (Compiles with Error)
package college.app;
import college.cse.Student;

public class ExternalCaller {
    void test() {
        Student s = new Student();
        s.showDepartment(); // COMPILER ERROR!
    }
}
✓ Correct Design (Expose Safe Public API)
package college.cse;

public class Student {
    String department = "CSE";

    // Public method provides controlled external access
    public void printPublicDept() {
        showDepartment();
    }
}
Compiler Error Diagnostic When Accessing from Another Package:

        s.showDepartment();

Section 10 🔒 Ultimate Encapsulation

10. The private Access Modifier

The private modifier is the most restrictive access level in Java. A private member can only be accessed within the exact body of its declaring top-level class (including its own nested member classes). It is invisible to subclasses, peers in the same package, and foreign packages alike.

Visual 13: Private Encapsulation & Public Access Gateway

Figure 10.1: External callers interact strictly through verified public methods; the private field remains safely encapsulated.

Code Example: BankAccount State Shielding

BankDemo.java Java 
class BankAccount {
    // Encapsulated state: invisible to any outside class
    private double balance;

    // Public mutation gateway with business validation
    public void deposit(double amount) {
        if (amount > 0) {
            balance += amount;
        }
    }

    // Public read-only accessor
    public double getBalance() {
        return balance;
    }
}

public class BankDemo {
    public static void main(String[] args) {
        BankAccount acc = new BankAccount();
        acc.deposit(500.0);
        System.out.println(acc.getBalance());

        // The following line would fail to compile!
        // acc.balance = 10000; // ERROR: balance has private access in BankAccount
    }
}
Exact Output:
500.0
📖 The Three Pillars of Encapsulation
  1. Data Hiding: Hide internal representations (e.g. keeping balance private).
  2. Input Validation: Prevent corrupted or invalid states (e.g., rejecting negative deposit amounts).
  3. Implementation Independence: You can later change balance to a BigDecimal internally without breaking any external callers calling getBalance().
Section 11 🔑 Subclass Inheritance & Package Scope

11. The protected Access Modifier

The protected modifier is designed specifically for inheritance relationships. It provides a unique dual-behavior that is often misunderstood by beginners.

Case A: Same Package

Within the same package, protected behaves exactly like package-private. Any class in the package can access the protected member directly, even without inheriting from it!

Case B: Different Package

Across package boundaries, a protected member is accessible only to subclasses through inheritance (via this or super).

Visual 14: Protected Access Within the Same Package

Figure 11.1: Protected members are openly accessible to non-subclass peer classes residing in the same package.

The Critical Cross-Package Reference Restriction

Here is the most critical rule in the entire Java access control specification:

⚠ The Java Language Specification Protected Rule (JLS §6.6.2)

In a foreign package, a subclass can access an inherited protected member only through its own instance (or an instance of its own subclass). It CANNOT access the protected member through a reference typed as the superclass!

Visual 15: Cross-Package Protected Access: Subclass vs. Reference Rule

Figure 11.2: A subclass can access protected members through inheritance (this), but cannot access them via an arbitrary parent reference.

Complete Code Demonstration of Protected Inheritance

src/college/people/Person.java Java 
package college.people;

public class Person {
    // Protected field: accessible in college.people & subclasses worldwide
    protected String departmentCode = "CSE-DEP";

    protected void showDepartment() {
        System.out.println("Department: " + departmentCode);
    }
}
src/college/staff/Teacher.java (Subclass in Different Package) Java 
package college.staff;

import college.people.Person;

public class Teacher extends Person {
    public void printInfo() {
        // ✓ VALID: Accessing inherited protected member via 'this'
        System.out.println("Teacher Dept: " + departmentCode);
        showDepartment(); // ✓ VALID: Inherited protected method

        // ✗ INVALID: Trying to access through an arbitrary Person instance!
        // Person p = new Person();
        // System.out.println(p.departmentCode); // COMPILER ERROR!
    }

    public static void main(String[] args) {
        Teacher t = new Teacher();
        t.printInfo();
    }
}
Exact Output:
Teacher Dept: CSE-DEP
Department: CSE-DEP
Section 12 🔨 Instantiation Control

12. Access Control and Constructors

Constructors support the exact same four access modifiers as regular methods. Controlling constructor visibility allows architects to dictate who can instantiate an object and enforce design patterns such as Factory and Singleton.

Visual 16: Constructor Accessibility & Object Instantiation Boundaries

Figure 12.1: How constructor access modifiers govern where new ClassName() can be executed.

Constructor Modifier Instantiation Scope Common Architectural Use Case
public Universal (any class anywhere can call new) Standard domain models, DTOs, and public API utility classes.
(default / pkg-private) Same package only Subsystem implementations that should only be created by an internal factory.
protected Package + Subclasses (via super()) Abstract parent classes designed exclusively for subclass extension.
private Declaring class only Utility classes (e.g., Math) or Singleton instances via getInstance().

Example: Private Constructor for Utility Classes

Classes that contain only static utility methods (like java.lang.Math) should not be instantiated. Adding a private constructor enforces this at compile time: 

public class MathUtils {
    // Private constructor prevents external instantiation
    private MathUtils() {
        throw new UnsupportedOperationException("Utility class; cannot be instantiated");
    }

    public static int add(int a, int b) {
        return a + b;
    }
}
Section 13 📄 Top-Level vs. Nested Visibility

13. Access Modifiers for Classes

In Java, the rules governing class declarations differ sharply depending on whether the class is a top-level class (directly in a .java file) or a nested class (defined inside another class).

Visual 17: Class-Level Access Modifiers: Top-Level vs. Nested

Figure 13.1: Top-level classes permit only two access levels; nested member classes permit all four.

Top-Level Class Rule

A top-level class can only be declared with:

  • public: Visible to all packages. The file name must match the class name (e.g., public class Student in Student.java).
  • Package-Private (No modifier): Visible only within its package. Multiple package-private classes can live in a single source file.

⚠ A top-level class CANNOT be marked private or protected. Doing so triggers: modifier private/protected not allowed here.

Nested Classes Support All Four Modifiers

Because nested classes are members of an enclosing class, they can be marked private, protected, package-private, or public:

NestedAccessDemo.java Java 
public class NestedAccessDemo {
    // Private nested class: accessible strictly inside NestedAccessDemo
    private static class InternalHelper {
        static void help() {
            System.out.println("Internal helper");
        }
    }

    public static void main(String[] args) {
        // Enclosing class can access its own private nested class
        InternalHelper.help();
    }
}
Exact Output:
Internal helper
Section 14 🛠 Unified Architecture

14. Package and Access Control Together

Real-world Java applications organize code by functional layer (Model-Service-Application pattern). Here is a complete multi-package project demonstrating packages and access control working in harmony.

Visual 18: Multi-Package Architecture: Model-Service-App Decoupling

Figure 14.1: Decoupled three-tier architecture: model holds data state, service executes business rules, and app coordinates execution.

Project Directory Layout

StudentManagement/
└── src/
    └── college/
        ├── model/
        │   └── Student.java
        ├── service/
        │   └── StudentService.java
        └── app/

src/college/model/Student.java Java 
package college.model;

public class Student {
    // Encapsulated private state
    private int id;
    private String name;
    private double marks;

    // Package-private helper field: accessible only within college.model
    String recordTag = "AUDIT_OK";

    public Student(int id, String name, double marks) {
        this.id = id;
        this.name = name;
        this.marks = marks;
    }

    // Public getters and setters
    public int getId() { return id; }
    public String getName() { return name; }
    public double getMarks() { return marks; }

    public void setMarks(double marks) {
        if (marks >= 0 && marks <= 100) {
            this.marks = marks;
        }
    }
}
src/college/service/StudentService.java Java 
package college.service;

import college.model.Student;

public class StudentService {
    public String evaluateResult(Student s) {
        if (s.getMarks() >= 40) {
            return "Pass";
        }
        return "Fail";
    }

    public void printReport(Student s) {
        System.out.println("Student: " + s.getName());
        System.out.println("Marks: " + (int) s.getMarks());
        System.out.println("Result: " + evaluateResult(s));
    }
}
src/college/app/Main.java Java 
package college.app;

import college.model.Student;
import college.service.StudentService;

public class Main {
    public static void main(String[] args) {
        Student s = new Student(101, "Aman Sharma", 88.0);
        StudentService service = new StudentService();
        service.printReport(s);
    }
}
Exact Output:
Student: Aman Sharma
Marks: 88
Result: Pass

Section 15 🐞 Compiler Errors & Diagnosis

15. Import Errors and Package Debugging (12 Scenarios)

Package declarations and access modifiers introduce specific compilation errors. Master these 12 debugging scenarios to troubleshoot compiler diagnostics quickly.

Visual 19: Package Statement vs. File Directory Mismatch

Figure 15.1: The source directory path must match the declared package statement tokens exactly.

Visual 20: Ambiguous Import Collision Resolution

Figure 15.2: Resolving colliding class names between wildcard packages using explicit single-type imports or FQCNs.

Error 1: Package Statement & Directory Mismatch

Declared package a.b; but saved file in src/c/

// In file: src/Student.java
package college.cse; // ERROR!
// Move file to:
src/college/cse/Student.java

Compiler Message: package college.cse does not match directory path

Fix: Ensure the file's folder structure precisely mirrors the package statement.

Error 2: Missing Import Statement

Using a class from another package without importing it

package college.app;
Student s = new Student(); // cannot find symbol
package college.app;
import college.cse.Student;
Student s = new Student();

Compiler Message: cannot find symbol: class Student

Fix: Add import package.name.ClassName; at the top of the file.

Error 3: Attempting to Access a Private Member

Directly referencing private fields or methods from outside the class

BankAccount a = new BankAccount();
a.balance = 500; // ERROR
BankAccount a = new BankAccount();
a.deposit(500); // Call public method

Compiler Message: balance has private access in BankAccount

Fix: Provide a public method (getter/setter) for controlled access.

Error 4: Package-Private Member Accessed from Outside

Omitting access modifier and attempting cross-package access

// In college.app
student.showDepartment(); // ERROR
// In college.cse.Student
public void showDepartment() { ... }

Compiler Message: showDepartment() is not public in Student; cannot be accessed from outside package

Fix: Mark the member public if cross-package access is intended.

Error 5: Invalid Cross-Package Protected Access

Subclass in another package accessing protected member via parent reference

Person p = new Person();
System.out.println(p.deptCode); // ERROR
// Access via inherited 'this':
System.out.println(this.deptCode);

Compiler Message: deptCode has protected access in Person

Fix: Access inherited protected members through this or a subclass reference.

Error 6: Top-Level Class Declared Private or Protected

Attempting to declare an outer class private

private class TopLevel { ... } // ERROR!
public class TopLevel { ... }
// OR: class TopLevel { ... }

Compiler Message: modifier private not allowed here

Fix: Top-level classes can only be public or package-private.

Error 7: Importing from Default Package into Named Package

Named package trying to import unnamed package class

package mypkg;
import MyHelper; // ERROR!
// Put MyHelper into a named package:
package mypkg.util;
public class MyHelper { ... }

Compiler Message: cannot find symbol: class MyHelper

Fix: Move all reusable classes into named packages.

Error 8: Ambiguous Import Collision

Importing two packages with identically named classes

import java.util.*;
import java.sql.*;
Date d = new Date(); // Ambiguous!
import java.util.Date; // Explicit
// OR: java.sql.Date d = ...

Compiler Message: reference to Date is ambiguous

Fix: Use an explicit single-type import or fully qualified name.

Error 9: Public Top-Level Class Name Mismatch

Public class name does not match the .java file name

// In file: StudentRecord.java
public class Student { ... }
// Rename file to Student.java
public class Student { ... }

Compiler Message: class Student is public, should be declared in a file named Student.java

Fix: Ensure the file name exactly matches the public class name (case-sensitive!).

Error 10: Forgetting to Make an Externally Used Class Public

Class has package-private access and cannot be imported by another package

package college.cse;
class Student { ... } // Not public!
package college.cse;
public class Student { ... }

Compiler Message: college.cse.Student is not public in college.cse; cannot be accessed from outside package

Fix: Add the public keyword to the class declaration.

Error 11: Assuming Wildcard Imports Are Recursive

Assuming import java.util.* imports java.util.concurrent.*

import java.util.*;
ConcurrentHashMap map = ... // Fails!
import java.util.concurrent.ConcurrentHashMap;
// OR: import java.util.concurrent.*;

Compiler Message: cannot find symbol: class ConcurrentHashMap

Fix: Wildcard imports apply to one package level only. Import subpackages explicitly.

Error 12: Executing with File Path Instead of FQCN

Running java bin/college/app/Main.class from terminal

java -cp bin college/app/Main.class
java -cp bin college.app.Main

Runtime Message: Could not find or load main class ... Caused by: NoClassDefFoundError

Fix: Use dotted FQCN without .class extension.

Section 16 💡 Facts vs. Myths

16. Common Misconceptions vs. Facts

Clear up 12 pervasive myths about Java packages and access control.

Visual 21: Wildcard Imports Are NOT Recursive

Figure 16.1: Wildcard imports do not cascade into child subpackages.

Common Misconception The Java Specification Fact
"Every class must be declared public." False. Package-private classes are ideal for internal implementation helpers that should never be exposed to consumers.
"Package-private is the same as protected." False. Package-private is strictly limited to the package; protected extends visibility to subclasses worldwide.
"Protected members are accessible to any subclass anywhere via any reference." False. Subclasses in other packages can only access protected members through inheritance (via this), not via arbitrary parent references.
"Private members cannot be used by nested classes." False. An outer class and its inner member classes can freely access each other's private fields and methods.
"Importing a class gives access to its private fields." False. Imports only make names convenient; they never bypass access modifiers.
"Wildcard import a.b.* also imports subpackages." False. Java packages are flat namespaces. java.util.* does not import java.util.regex.*.
"Java packages provide runtime hardware security." False. Packages are logical namespaces and compile-time boundaries, not cryptographic sandboxes.
"A top-level class can be marked private." False. Top-level classes can only be public or package-private.
"A private constructor means the class can never create objects." False. The class can instantiate itself inside static factory methods (e.g., Singleton pattern).
"The package name acts like a password." False. Any developer can declare a class in your package unless modules (Java 9+ JPMS) restrict it.
"Making every field public is harmless in small apps." False. Public fields destroy encapsulation, bypass validation, and create rigid, fragile code.
"A public method can return a package-private type without issues." Warning: While legal, callers outside the package cannot name or use the returned type easily!
