Section 01 ⚠ Runtime Reliability

1. What Is Exception Handling?

In Java, an exception is an abnormal event or condition that occurs during program execution and disrupts the normal flow of instructions. Rather than crashing abruptly, Java wraps the failure into an exception object that can be detected, intercepted, handled, and recovered from.

📖 Formal Definition

An exception is an object representing a runtime error condition that interrupts standard instruction execution. Exception handling is the architectural mechanism used to intercept exception objects, execute compensatory logic, preserve diagnostic logs, and prevent application termination.

Real-Life Failure Analogies

  • Food Delivery App: You order dinner, but the restaurant experiences a sudden internet disconnection. The app doesn't crash to your phone's home screen; it catches the timeout and presents a polite message: "Network connection lost. Retrying order..."
  • ATM Withdrawal: You request $500, but your account only holds $300. The ATM doesn't power down or freeze; it rejects the transaction cleanly, prints an explanation receipt, and returns your card safely.
  • Document Reader: An application attempts to open receipt.pdf, but the file was deleted by the user. The app informs the user rather than terminating silently.

Introductory Code Example: The Uncaught ArithmeticException

Consider what happens when Java attempts integer division by zero without any error handling:

Main.java (No Exception Handling) Java 
public class Main {
    public static void main(String[] args) {
        int result = 10 / 0; // Triggers ArithmeticException!
        System.out.println(result);
        System.out.println("Program completed"); // Never reached!
    }
}
Illustrative Console Output (Abrupt JVM Crash):
Exception in thread "main" java.lang.ArithmeticException: / by zero
    at Main.main(Main.java:3)

Because integer division by zero is mathematically undefined, the JVM creates an ArithmeticException object. Because no handler caught it, the program terminated immediately, and "Program completed" was never printed.

Section 02 🧪 Problem Classification

2. Errors, Exceptions, and Other Problems

Not all software defects are exceptions. In Java, program failures are categorized into four distinct classes: syntax errors, compile-time type errors, runtime exceptions, and fatal JVM errors.

Visual 2: Taxonomy of Java Program Failures

Figure 2.1: The four classes of programming errors and their respective detection stages.

1. Syntax Errors

Violations of Java language grammar rules (e.g. int x = ; or missing semicolons). Detected by javac; prevents bytecode generation.

2. Compile-Time Type Errors

Violations of Java's static typing (e.g. int n = "Hello";). The compiler catches these before the program ever runs.

3. Runtime Exceptions

Valid syntax and types that encounter unexpected conditions during execution (e.g. 10 / 0 or parsing "abc" to an integer). These can and should be handled.

4. Fatal JVM Errors

Severe hardware or JVM exhaustion issues (e.g. OutOfMemoryError or StackOverflowError). Applications should generally not attempt recovery.

Figure 2.2: java.lang.Throwable sits at the apex of all reportable Java conditions, dividing into Error and Exception.

Section 03 🛡 Robustness & Graceful Degradation

3. Why Exception Handling Is Needed

Without exception handling, any minor runtime anomaly causes an abrupt process crash, leaving files unclosed, database connections dangling, and users facing confusing stack traces.

Visual 4: Banking ATM Withdrawal Decision Tree

Figure 3.1: Separating standard business flow from failure compensation ensures predictable software behavior.

The 5 Core Benefits of Java Exception Handling

  1. Graceful Degradation: Prevents catastrophic termination; the application remains responsive and logs the incident.
  2. Separation of Concerns: Normal business logic is kept clean in the try block, while error-handling logic is centralized in catch blocks.
  3. Propagation Across Call Stacks: A deep utility method doesn't need to know how the UI wants to show errors; it simply propagates the exception to a layer with sufficient context.
  4. Resource Cleanup Guarantees: Ensures external resources (files, sockets, database locks) are reliably released even during failure.
  5. Preservation of Diagnostic Trails: Stack traces record the exact method call chain, file name, and line number where the problem originated.
Section 04 🌳 Object-Oriented Taxonomy

4. The Java Exception Hierarchy

Exceptions in Java are ordinary classes adhering to standard object-oriented inheritance. Every exception class descends from java.lang.Throwable.

Visual 5: Comprehensive Java Exception Hierarchy Blueprint

Figure 4.1: Comprehensive tree showing Throwable, Error, Exception, RuntimeException, and representative subclasses.

Inheritance Rules in Exception Handling

  • Polymorphic Catching: A catch (Exception e) block can catch an instance of ArithmeticException because ArithmeticException is an Exception.
  • Catch Ordering: Because catch blocks are evaluated sequentially from top to bottom, subclasses must always be placed before superclasses.

Section 06 🛡 Protected Execution Zone

6. The try Block

The try block designates a protected statement block where exceptions may arise. When an exception occurs inside a try block, execution of remaining statements inside the block is halted immediately, and control transfers to the matching catch handler.

Visual 7: The try Block Execution and Exception Interception Flow

Figure 6.1: How the JVM intercepts an exception and branches to the appropriate handler.

TryCatchDemo.java Java 
public class TryCatchDemo {
    public static void main(String[] args) {
        try {
            int result = 10 / 0; // Triggers ArithmeticException
            System.out.println(result); // Skipped!
        } catch (ArithmeticException e) {
            System.out.println("Cannot divide by zero.");
        }

        System.out.println("Program continues.");
    }
}
Exact Output:
Cannot divide by zero.
Program continues.
💡 Try Cannot Stand Alone

A standard try block must be followed by at least one catch block, a finally block, or both. Writing try { ... } alone triggers a compilation error.

Section 07 🪣 Interception & Diagnosis

7. The catch Block

The catch block is the exception handler. Its parameter acts like a method parameter, receiving a reference to the active exception object created by the JVM.

Visual 8: Exception Object Instantiation & Catch Parameter Binding

Figure 7.1: The JVM creates an exception object on the heap and binds it to the catch parameter variable e.

Code Example: Catching NumberFormatException

NumberFormatDemo.java Java 
public class NumberFormatDemo {
    public static void main(String[] args) {
        try {
            int number = Integer.parseInt("abc");
            System.out.println(number);
        } catch (NumberFormatException e) {
            System.out.println("Please enter a valid whole number.");
        }
    }
}
Exact Output:
Please enter a valid whole number.

User-Facing Messages vs. Diagnostic Stack Traces

  • User Message: Friendly, actionable guidance (e.g., "Please enter a valid whole number."). Never show raw Java exceptions to end users.
  • Diagnostic Message (e.getMessage()): Concise internal explanation (e.g., For input string: "abc") suitable for developer logging.
  • Stack Trace (e.printStackTrace()): Complete call chain used during local development and debugging.
Section 08 🔀 Multi-Branch Handling

8. Multiple Catch Blocks

A single try block can throw different types of exceptions. Java allows multiple sequential catch blocks to handle each specific problem with tailored recovery logic.

Visual 9: Multiple Catch Ordering: Specific Subclass Before Broad Superclass

Figure 8.1: Sequential evaluation: the first matching catch block executes; broader handlers act as fallbacks.

MultipleCatchDemo.java Java 
public class MultipleCatchDemo {
    public static void main(String[] args) {
        try {
            int[] numbers = {10, 20, 30};
            System.out.println(numbers[5]); // Triggers ArrayIndexOutOfBoundsException
        } catch (ArithmeticException e) {
            System.out.println("Arithmetic problem.");
        } catch (ArrayIndexOutOfBoundsException e) {
            System.out.println("Invalid array index.");
        } catch (Exception e) {
            System.out.println("Unexpected problem.");
        }
    }
}
Exact Output:
Invalid array index.
⚠ The Catch Ordering Compilation Rule

Always arrange catch blocks from most specific to most general. If you place catch (Exception e) at the top, the compiler will reject the subsequent subclass catch blocks with: 

error: exception ArrayIndexOutOfBoundsException has already been caught
Section 09 🔗 Java 7+ Code Condensation

9. Multi-Catch (Java 7+)

When multiple distinct exception types require identical handling logic, Java 7's multi-catch syntax allows you to combine them into a single catch clause using the pipe (|) operator.

Visual 10: Java 7 Multi-Catch: Disjoint Exception Unions

Figure 9.1: Combining disjoint exception types reduces duplicated boilerplate code.

MultiCatchDemo.java Java 
public class MultiCatchDemo {
    public static void main(String[] args) {
        try {
            int number = Integer.parseInt("abc");
            System.out.println(number);
        } catch (NumberFormatException | NullPointerException e) {
            System.out.println("Input could not be processed.");
        }
    }
}
Exact Output:
Input could not be processed.

Two Vital Multi-Catch Rules

  1. Disjoint Types Only: The combined exception classes cannot be related by inheritance. For example, catch (FileNotFoundException | IOException e) is illegal because FileNotFoundException is already a subclass of IOException.
  2. Implicitly Final Parameter: The exception variable e in a multi-catch is implicitly final. You cannot reassign e = new Exception();.
Section 10 🔒 Guaranteed Cleanup

10. The finally Block

The finally block represents Java's guarantee for cleanup operations. It executes regardless of whether an exception occurred, whether an exception was successfully caught, or whether the try block executed normally without any issue.

Real-Life Analogy: Returning Borrowed Equipment

Imagine you borrow specialized power tools from a community workshop to repair a chair:

  • Scenario A (Success): You finish repairing the chair smoothly. You return the power tools to the rack.
  • Scenario B (Failure): The chair leg snaps completely in half. You stop the repair, but you still return the power tools to the rack.
  • Scenario C (Unexpected Emergency): A fire alarm rings in the workshop. Even while exiting, safety procedures mandate shutting down the power switch before departure.

In programming, returning tools is analogous to closing open database connections, releasing socket channels, and freeing system resources.

Visual 11: The Finally Execution Guarantee

Figure 10.1: Three distinct execution paths all converge through the mandatory finally block.

Code Example: Demonstrating the Finally Block

FinallyDemo.java Java 
public class FinallyDemo {
    public static void main(String[] args) {
        try {
            System.out.println("Task started");
            int result = 10 / 2;
            System.out.println(result);
        } catch (ArithmeticException e) {
            System.out.println("Calculation failed");
        } finally {
            System.out.println("Cleanup step");
        }

        System.out.println("Program finished");
    }
}
Exact Output:
Task started
5
Cleanup step
Program finished

Detailed Step-by-Step Execution Traces

Execution Stage Trace 1: No Exception (10 / 2) Trace 2: Caught Exception (10 / 0) Trace 3: Uncaught Exception (e.g. NullPointer)
1. Enter Try Prints "Task started" Prints "Task started" Prints "Task started"
2. Statement Evaluates 10 / 2 = 5; prints 5 Division throws ArithmeticException Invokes method on null reference
3. Catch Evaluation Bypassed (no exception thrown) Matched: prints "Calculation failed" No match: propagation queued
4. Finally Block Executes: prints "Cleanup step" Executes: prints "Cleanup step" Executes: prints "Cleanup step"
5. Subsequent Code Prints "Program finished" Prints "Program finished" Not reached; thread terminates with stack trace
⚠ Critical Anti-Pattern: Never Return from Finally

If you place a return statement inside a finally block, it will swallow and suppress any exception thrown in the try or catch blocks, as well as override any return value computed earlier. Similarly, throwing an exception inside finally discards any prior pending exception. Keep finally clean and strictly limited to resource release.

When Does Finally NOT Execute?

While finally is guaranteed under all normal and exceptional Java control flows, it will not run if:

  1. System.exit(status) is invoked, which terminates the Java Virtual Machine immediately.
  2. The underlying operating system abruptly terminates the JVM process (kill -9 or Task Manager end-process).
  3. The host machine suffers a catastrophic hardware power failure or kernel panic.
  4. An infinite loop or thread deadlock permanently halts progress inside the preceding try block.

11. Try, Catch, and Finally Together

Understanding the full life cycle of a try-catch-finally construct allows you to predict program control flow under all operational conditions.

Scenario 1: Normal Clean Execution

try {

    int val = 100 / 10;

} catch (ArithmeticException e) {
    System.out.println("3. Caught");

System.out.println("5. After construct");

2. Value: 10
4. Finally cleanup
5. After construct

Scenario 2: Handled Exception

    int val = 100 / 0;
    System.out.println("2. Value: " + val); // Skipped
} catch (ArithmeticException e) {
    System.out.println("3. Caught arithmetic error");
} finally {
    System.out.println("4. Finally cleanup");

System.out.println("5. After construct");

1. Try start
3. Caught arithmetic error
4. Finally cleanup
5. After construct

Scenario 3: Uncaught Propagating Exception

// Main with unhandled NullPointerException

    System.out.println("1. Try start");
    String text = null;
    int len = text.length(); // Throws NullPointerException
} catch (ArithmeticException e) {

Scenario 4: Exception Thrown Inside Catch Block

If an exception occurs inside the catch handler itself, control jumps immediately to the finally block, executes the cleanup statements, and then propagates the new exception upward to the caller.

Section 12 📈 Call Stack Unwinding

12. Exception Propagation and the Call Stack

When an exception occurs inside a method that does not possess an internal try-catch handler, Java does not abandon the process immediately. Instead, it drops through the call stack in a process known as exception propagation (or stack unwinding).

Real-Life Analogy: Support Escalation

A customer calls a software company with a complex billing dispute:

  1. The junior support clerk cannot authorize a refund. They escalate the problem to their team lead.
  2. The team lead cannot authorize amounts over $500. They escalate to the regional finance manager.
  3. The regional manager possesses the exact authority required, reviews the case, authorizes the refund, and resolves the issue smoothly.

If no one in the company possessed the authority, the request would hit the executive office and ultimately be rejected. In Java, methods propagate exceptions upward until a caller at the appropriate architectural layer catches and resolves it.

Visual 13: Call Stack Exception Propagation & Unwinding

Figure 12.1: The exception propagates down the call stack until main catches it.

Code Example: Method Call Chain

PropagationDemo.java Java 
public class PropagationDemo {
    static void methodC() {
        int result = 10 / 0; // ArithmeticException created here
    }

    static void methodB() {
        methodC(); // No try-catch: propagates up to caller
    }

    static void methodA() {
        methodB(); // No try-catch: propagates up to caller
    }

    public static void main(String[] args) {
        try {
            methodA();
        } catch (ArithmeticException e) {
            System.out.println("Exception handled in main.");
        }
    }
}
Exact Output:
Exception handled in main.

Why Catch at the Right Abstraction Level?

Low-level methods (such as a database driver or JSON parser) should rarely display UI dialogs or decide business recovery policies. Instead, they let technical exceptions propagate up to service or controller layers that understand the full user workflow.

Section 13 🚀 Explicit Exception Triggering

13. The throw Keyword

While the JVM automatically throws exceptions when low-level hardware or arithmetic operations fail, Java provides the throw keyword to allow developers to explicitly trigger an exception whenever a domain rule or contractual precondition is violated.

📖 The throw Statement

Syntax: throw exceptionObject;
The operand must be an instance of Throwable or any of its subclasses (usually created with new ExceptionType("message")).

Visual 14: The Throw Keyword Validation Pipeline
throw is an executable command statement. • Followed by an exception object (created with new).

Figure 13.1: Explicit exception creation and execution halt upon contract violation.

Code Example: Validating Voter Eligibility

ThrowDemo.java Java 
public class ThrowDemo {
    static void checkAge(int age) {
        if (age < 18) {
            throw new IllegalArgumentException(
                "Age must be at least 18."
            );
        }

        System.out.println("Access allowed.");
    }

    public static void main(String[] args) {
        try {
            checkAge(16);
        } catch (IllegalArgumentException e) {
            System.out.println(e.getMessage());
        }
    }
}
Exact Output:
Age must be at least 18.

When to Throw Exceptions vs Returning Status Values

  • Throw an Exception: When the condition prevents the method from fulfilling its fundamental contract (e.g., negative balance in an account creation, missing database connection, corrupt encrypted token).
  • Return a Status / Optional: For expected, routine outcomes (e.g., userNotFound during search query, password mismatch during standard login attempt). Exceptions are heavy objects because building their stack trace incurs CPU overhead.
Section 14 📣 Method Signature Declaration

14. The throws Keyword

The throws keyword is part of a method's contractual signature. It informs the compiler and any caller methods that this method might propagate specific checked exception types during execution.

Visual 15: The Throws Signature Contract
throws appears in the method declaration header. • Warns the caller: "Handle IOException or propagate further!"

Figure 14.1: The method declaration communicates potential checked exceptions to calling methods.

Code Example: Reading Files with Throws

ThrowsDemo.java Java 
import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;

public class ThrowsDemo {
    // Declares that this method does not handle IOException internally
    static String readFile(Path path) throws IOException {
        return Files.readString(path);
    }

    public static void main(String[] args) {
        try {
            String content = readFile(Path.of("notes.txt"));
            System.out.println(content);
        } catch (IOException e) {
            System.out.println("Unable to read the file.");
        }
    }
}
Output (When notes.txt is Missing):
Unable to read the file.

Note: If notes.txt exists in the current directory, the method prints the file contents instead.

Key Insights on throws

  • Mandatory for Checked Exceptions: If a method invokes code that can throw checked exceptions without handling them in a local try-catch, it must declare them using throws.
  • Optional for Unchecked Exceptions: You may document unchecked exceptions like throws IllegalArgumentException in the signature, but the compiler does not enforce it.
  • Multiple Exceptions: Multiple exception types can be declared separated by commas: void process() throws IOException, SQLException.
Section 15 ⚖ Comparison & Contrast

15. throw Versus throws

Beginner Java developers frequently confuse throw and throws due to their similar names. However, they serve completely different roles in syntax and program architecture.

Visual 16: Throw vs Throws Architectural Comparison
object instance throw new IllegalArgumentException(); • Initiates immediate exceptional interruption ✓ Can only throw one object at a time throws (Declaration Clause) • Used in METHOD SIGNATURE header • Followed by exception class names void read() throws IOException, SQLException • Delegates handling responsibility to caller ⚠ Can declare multiple comma-separated types

Figure 15.1: Action in code body vs contract declaration in method signature.

Feature throw Keyword throws Keyword
Primary Purpose Explicitly creates and initiates an exception object Declares potential exceptions a method may propagate
Syntactic Location Inside a method, constructor, or code block In the method signature header
Operand / Suffix Followed by an instance (e.g. new IOException()) Followed by class names (e.g. IOException)
Quantity Can only throw one exception object at a time Can declare multiple comma-separated exception types
Execution Effect Immediately halts sequential execution Does not execute code; merely informs the compiler
⚠ The Classic Beginner Syntax Blunder

Incorrect Code: 

void readData() {
    throw IOException; // COMPILE ERROR: cannot find symbol / not an instance
}

Explanation: throw requires an instantiated object expression, not a type name. Furthermore, IOException is a checked exception, so the method must either handle it or declare it.

Correct Alternative A (Throwing an instance): 

void readData() throws IOException {
    throw new IOException("Disk error"); // Instantiates object and throws
}

Correct Alternative B (Declaring propagation): 

void readData() throws IOException {
    Files.readString(Path.of("data.txt")); // Passes responsibility to caller
}
Section 16 📁 Practical File I/O Reliability

16. Checked Exception Handling in File Operations

File operations provide the quintessential real-world demonstration of checked exceptions in Java. When an application communicates with the host operating system's file system, things outside Java's control can fail: files can be missing, permissions can be revoked, or disks can run out of space.

Visual 17: File I/O Checked Exception Architecture

Figure 16.1: Handling file I/O failures vs propagating them across application layers.

Two Strategies for Checked File Operations

When reading files with Files.readString(Path.of("config.txt")), the Java compiler enforces the catch-or-declare contract for IOException.

Strategy 1: Local Handling (UI/Service Layer) Java 
import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.NoSuchFileException;
import java.nio.file.Path;

public class LocalFileHandler {
    public static void loadConfig(String fileName) {
        try {
            Path path = Path.of(fileName);
            String content = Files.readString(path);
            System.out.println("Config loaded: " + content);
        } catch (NoSuchFileException e) {
            System.out.println("Error: Configuration file '" + fileName + "' was not found.");
        } catch (IOException e) {
            System.out.println("Error: Unable to read file due to an I/O issue.");
        }
    }
}
Strategy 2: Declaring Throws (Data/Utility Layer) Java 
import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;

public class FileUtil {
    // Utility library passes raw exception upward so caller can decide recovery
    public static String readRawData(String fileName) throws IOException {
        Path path = Path.of(fileName);
        return Files.readString(path);
    }
}

Architectural Rule of Thumb

Never catch an exception at a low-level layer if all you can do is print a generic message to the console and continue blindly. Allow checked exceptions to propagate to a layer that possesses the contextual authority to prompt the user, choose a default fallback file, or abort the workflow cleanly.

Section 17 ♻ AutoCloseable Management

17. Try-With-Resources (Java 7+)

Prior to Java 7, closing external system resources (such as streams, readers, and database connections) required verbose, error-prone finally blocks with nested try-catch statements. Java 7 introduced try-with-resources, which automates safe, guaranteed resource closing.

Visual 18: Try-With-Resources Lifecycle & AutoCloseable

Figure 17.1: Automatic resource closure occurs before catch and finally blocks execute.

📖 The AutoCloseable Contract

Any object whose class implements the java.lang.AutoCloseable (or java.io.Closeable) interface can be opened inside the parenthesis of a try (...) statement. Java guarantees that its close() method will be invoked automatically as control exits the block, even if an exception occurs!

Code Example: Modern File Reading

TryWithResourcesDemo.java Java 
import java.io.BufferedReader;
import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;

public class TryWithResourcesDemo {
    public static void main(String[] args) {
        Path path = Path.of("notes.txt");

        // reader is automatically closed when try block exits
        try (BufferedReader reader = Files.newBufferedReader(path)) {
            String line = reader.readLine();
            System.out.println("First line: " + line);
        } catch (IOException e) {
            System.out.println("Could not read the file.");
        }
    }
}
Sample Output (When notes.txt is not found):
Could not read the file.

Key Advantages of Try-With-Resources

  1. Zero Resource Leaks: Prevents operating system file descriptor exhaustion.
  2. Eliminates Boilerplate: No need for null checks or nested try { reader.close(); } catch (...) inside finally.
  3. Suppressed Exceptions: If both the try block and the close() method throw an exception, Java preserves the primary exception from the try block and attaches the closing failure as a suppressed exception (accessible via e.getSuppressed()).
Section 18 🎨 Domain-Specific Error Architecture

18. Custom Exceptions

While Java provides dozens of built-in exceptions, enterprise applications require domain-specific error types that clearly reflect business concepts (e.g., InsufficientBalanceException, SeatAlreadyBookedException, InvalidTokenException).

Designing the Custom Exception

InsufficientBalanceException.java Java 
// Custom checked exception extending Exception
public class InsufficientBalanceException extends Exception {
    public InsufficientBalanceException(String message) {
        super(message);
    }
}

Complete Banking Account Implementation

CustomExceptionDemo.java Java 
class BankAccount {
    private double balance;

    public BankAccount(double initialBalance) {
        this.balance = initialBalance;
    }

    public void withdraw(double amount) throws InsufficientBalanceException {
        if (amount > balance) {
            throw new InsufficientBalanceException(
                "Withdrawal of $" + amount + " exceeds balance of $" + balance
            );
        }
        balance -= amount;
        System.out.println("Withdrawal successful! Remaining balance: $" + balance);
    }

    public double getBalance() {
        return balance;
    }
}

public class CustomExceptionDemo {
    public static void main(String[] args) {
        BankAccount account = new BankAccount(500.0);

        try {
            System.out.println("Attempting to withdraw $200...");
            account.withdraw(200.0);

            System.out.println("Attempting to withdraw $400...");
            account.withdraw(400.0); // Will throw InsufficientBalanceException
        } catch (InsufficientBalanceException e) {
            System.out.println("Transaction Rejected: " + e.getMessage());
        }

        System.out.println("Final Account Balance: $" + account.getBalance());
    }
}

Section 19 🔍 Diagnostic Autopsy

19. Reading and Deconstructing Stack Traces

When an unhandled exception terminates a thread, the Java Virtual Machine prints a stack trace to the standard error stream. A stack trace is not random computer noise—it is an exact, reverse chronological snapshot of every method call active at the exact instant of failure.

Visual 20: Anatomy of a Java Stack Trace

Representative Illustrative Stack Trace

Development vs Production Stack Trace Discipline

Section 21 ⚠ Anti-Patterns & Traps

21. Sixteen Common Exception-Handling Mistakes & Anti-Patterns

Writing robust exception handling requires avoiding deceptive traps that give the illusion of safety while concealing catastrophic failures.

Visual 22: The "Swallowed Exception" Black Hole Anti-Pattern

Figure 21.1: Catching exceptions with empty blocks creates silent, un-debuggable production disasters.

Catalog of Major Mistakes and Professional Remedies

  1. Swallowing Exceptions Silently: 
    // INCORRECT: The "Black Hole"
try {
    processPayment();
} catch (Exception e) {
    // Empty: complete silence!
}

// CORRECT: Log or handle meaningfully
try {
    processPayment();
} catch (PaymentException e) {
    logger.error("Payment failed for user", e);
    notifyUserOfFailure();
}
  2. Catching Exception or Throwable Too Broadly: Catching Exception indiscriminately masks unexpected bugs like NullPointerException that should be investigated and fixed.
  3. Incorrect Catch Block Ordering: Placing catch (Exception e) ahead of catch (IOException e) causes an unreachable code compiler error.
  4. Confusing throw with throws: throw is an action on an object; throws is a clause in a method declaration.
  5. Returning from Inside a finally Block: Overwrites any return value or pending exception from the try block.
  6. Throwing Exceptions from finally: Completely masks the original root cause that triggered the cleanup.
  7. Using Exceptions for Standard Control Flow: Using a try-catch to terminate an array loop instead of checking bounds creates massive CPU overhead because creating stack traces is expensive.
  8. Log-and-Throw Duplication: Logging an exception in a low-level method and then immediately re-throwing it causes identical stack traces to flood logs multiple times across architectural tiers. Either log it OR re-throw it!
  9. Exposing Raw Traces to Users: Direct security vulnerability exposing system internals.
  10. Forgetting Resource Closure: Failing to use try-with-resources causes file descriptor and socket leaks.
  11. Unchecked Exception Declared in throws as Substitute for Handling: Adding throws RuntimeException doesn't resolve a logic error.
  12. Assuming All Exceptions Are Recoverable: Attempting to recover from severe memory or thread deadlocks leads to corrupt state.
  13. Destructive Wrapping: Re-throwing a new exception without chaining the original cause: throw new MyException("failed") instead of throw new MyException("failed", originalCause).
  14. Overly Broad Custom Exceptions: Creating one single AppException for 50 completely unrelated domain failures.
  15. Throwing Generic new Exception(): Forces callers into clumsy, broad catch blocks.
  16. Ignoring InterruptedException: Swallowing thread interruptions without restoring the interrupt flag with Thread.currentThread().interrupt().

Project Requirements

  2. Safely parse numeric marks, guarding against non-numeric entries (NumberFormatException).
  3. Enforce the domain rule that marks must fall within the range [0, 100] using custom InvalidMarksException.

StudentResultApp.java Java 
// 1. Custom Domain Exception
class InvalidMarksException extends Exception {
    public InvalidMarksException(String message) {
        super(message);
    }
}

// 2. Student Evaluation Engine
public class StudentResultApp {

    // Validates that mark falls between 0 and 100
    public static int validateMark(String subjectName, String markStr) 
            throws InvalidMarksException, NumberFormatException {
        int mark = Integer.parseInt(markStr.trim());
        if (mark < 0 || mark > 100) {
            throw new InvalidMarksException(
                subjectName + " marks (" + mark + ") must be between 0 and 100."
            );
        }
        return mark;
    }

    // Calculates and displays student evaluation report
    public static void evaluateStudent(String name, String mathStr, String sciStr, String engStr) {
        System.out.println("----------------------------------------------");
        System.out.println("Evaluating Results for Student: " + name);
        try {
            int math = validateMark("Mathematics", mathStr);
            int sci = validateMark("Science", sciStr);
            int eng = validateMark("English", engStr);

            int total = math + sci + eng;
            double avg = total / 3.0;

            String grade;
            if (avg >= 90) grade = "A+";
            else if (avg >= 75) grade = "A";
            else if (avg >= 60) grade = "B";
            else if (avg >= 50) grade = "C";
            else grade = "F";

            System.out.println("Math: " + math + " | Science: " + sci + " | English: " + eng);
            System.out.println("Total Marks: " + total + " / 300");
            System.out.printf("Average Percentage: %.2f%%%n", avg);
            System.out.println("Final Grade: " + grade);
            System.out.println("Status: PASSED VALIDATION");

        } catch (NumberFormatException e) {
            System.out.println("Validation Error: Marks must be valid whole numbers.");
        } catch (InvalidMarksException e) {
            System.out.println("Domain Rule Error: " + e.getMessage());
        } finally {
            System.out.println("Audit: Evaluation cycle complete for " + name + ".");
        }
    }

    public static void main(String[] args) {
        // Test Case 1: Valid Student
        evaluateStudent("Sarah Connor", "85", "92", "78");

        // Test Case 2: Non-numeric String
        evaluateStudent("John Doe", "85", "ninety", "78");

        // Test Case 3: Out-of-bounds Mark (> 100)
        evaluateStudent("Alex Murphy", "85", "105", "78");
    }
}

Summary of Core Tenets

  • Throwable: Root of all errors and exceptions. Has two direct subclasses: Error and Exception.
  • Error: Serious JVM failure (OutOfMemoryError, StackOverflowError); applications should not attempt recovery.
  • Checked Exceptions: Subclasses of Exception (excluding RuntimeException). Enforced by compiler catch-or-declare rule.
  • Unchecked Exceptions: Subclasses of RuntimeException. Not enforced by compiler; represent logic bugs and invalid preconditions.
  • try: Encloses risky code that might throw an exception.
  • catch: Intercepts and handles specific exception objects. Must be ordered specific-to-general.
  • multi-catch: Combines disjoint exception types: catch (A | B e); parameter e is final.
  • finally: Guaranteed cleanup block; always runs (unless System.exit() called).
  • throw: Explicitly triggers an exception instance: throw new MyException();.
  • throws: Declares potential checked exceptions in method header: void f() throws IOException.
  • try-with-resources: Automatically closes any AutoCloseable object when block exits.
