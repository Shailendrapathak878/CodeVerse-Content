What Is a Process? The Operating System Container

Every time you double-click an application icon on your computer — whether launching Google Chrome, Spotify, IntelliJ IDEA, or running java Main in your terminal — the operating system creates an isolated execution environment known as a Process.

🏛 Real-Life Analogy: The University Campus Departments

Imagine a large university campus consisting of multiple independent academic departments: the Computer Science department, the School of Medicine, and the Department of Physics.

  • Autonomous Workspace: Each department occupies its own secured building. The Medical School cannot accidentally spill liquid nitrogen onto the CS department's servers because a physical security gate isolates them.
  • Dedicated Resources: Each department receives its own budget, electrical meters, and private library room.
  • People Working Inside: Inside the Computer Science building, several professors, researchers, and students move around concurrently collaborating on different project assignments.

In computer science, each department building represents an OS Process. The people working collaboratively inside that building represent Threads!

  • Shared Region: Contains the JVM Heap and Metaspace where class definitions, static variables, and instantiated objects reside. Accessible by all threads in the process.
  • Thread Lanes: Thread 1 (Main), Thread 2 (Worker), and Thread 3 (I/O). Each thread possesses its own private Call Stack, local variables, and Program Counter (PC).

Core Characteristics of an Operating System Process

🔒 Memory Isolation

Processes cannot directly read or write to another process's memory space. If your web browser crashes, your code editor remains completely unharmed because their memory spaces are strictly segregated by the operating system kernel.

💻 Heavyweight Allocation

Creating a new OS process requires substantial overhead: allocating virtual memory page tables, file descriptor tables, and system security credentials. Inter-process communication (IPC) requires sockets or shared pipes.

What Is a Thread? Lightweight Execution Paths

A Thread (often described as a lightweight process) is the smallest sequential unit of CPU execution scheduled by an operating system. A process provides the physical resources (memory, file handles, network sockets), while threads perform the actual computations within that space.

🍳 Real-Life Analogy: The Busy Restaurant Kitchen

Consider a bustling restaurant kitchen preparing orders for hundreds of dinner guests:

  • The Kitchen (Process): The entire kitchen space, gas lines, refrigerators, and ventilation hoods constitute the process environment.
  • The Line Cooks (Threads): Cook A boils pasta, Cook B grills salmon, and Cook C whips chocolate soufflé. Each cook moves around independently and rapidly.
  • Personal Utensils (Private Call Stack): Each cook holds their own chef's knife, tasting spoon, and notepad in their pocket. Cook A's knife cannot accidentally cut Cook B's finger.
  • The Shared Prep Table (Shared Heap Memory): In the center of the kitchen sits a large marble cutting board with seasoning bowls (salt, pepper, olive oil). All cooks reach for this shared table simultaneously!

Section 04

Concurrency vs. Parallelism: The Precise Distinction

In casual technical conversation, software developers often mix up the words concurrency and parallelism as if they were synonyms. In systems engineering, they represent two fundamentally different concepts. As computer scientist Rob Pike famously stated: "Concurrency is about dealing with lots of things at once. Parallelism is about doing lots of things at once."

🕑 Concurrency (Structure)

The architectural ability to structure a program into discrete tasks that make progress over overlapping periods of time. Concurrency can happen on a single single-core processor through rapid time-slicing (interleaving).

⚡ Parallelism (Execution)

The physical hardware capability to execute multiple distinct computational tasks at the exact same physical instant. Parallelism requires multiple physical CPU cores or multiple processors.

💡 Does Multithreading Always Mean Faster Execution?

No! If you take a CPU-bound math problem (such as calculating prime numbers) and spawn 1,000 threads on a 4-core laptop, your program will run significantly slower than running just 4 threads! Why? Because the CPU spends more time performing expensive operating-system context switches (swapping thread memory and register registers) than executing actual math!

public class ConcurrentDemo {
    public static void main(String[] args) throws InterruptedException {
        Thread threadA = new Thread(() -> {
            for (int i = 1; i <= 3; i++) {
                System.out.println("[Thread-A] Step " + i);
            }
        }, "Worker-A");

        Thread threadB = new Thread(() -> {
            for (int i = 1; i <= 3; i++) {
                System.out.println("[Thread-B] Step " + i);
            }
        }, "Worker-B");

        System.out.println("Launching threads concurrently...");
        threadA.start();
        threadB.start();

        // Wait for both threads to finish before printing completion
        threadA.join();
        threadB.join();
        System.out.println("All concurrent tasks finished.");
    }
}

💡 Why Did the Output Interleave?

Because both threads were marked as RUNNABLE simultaneously! The operating system's thread scheduler allotted short microsecond time-slices to Worker-A, then paused it and allotted slices to Worker-B. Rerunning this exact program 5 times will likely yield 5 slightly different interleavings!

Creating Threads with Thread: Inheritance Approach

In Java, the most fundamental representation of a thread is the class java.lang.Thread. The first historical way to create a thread (dating back to Java 1.0) is to declare a custom class that extends Thread and overrides its run() method.

Visual 7: Thread Creation Flow — Object Instantiation to OS Binding
Figure 7.1: Calling new MyThread() merely allocates a standard Java object. Calling .start() prompts the JVM to create a real OS thread and execute run() asynchronously.
Diagram Fallback (Text Summary):

Three-step lifecycle of creating a thread by extension:

  1. DownloadThread t = new DownloadThread(); → State is NEW. Java heap object created, but no operating system thread exists yet.
  2. t.start(); → Transitions to RUNNABLE. JVM requests the OS kernel to allocate a native thread stack.
  3. JVM invokes run() on the new thread stack. Main thread continues without waiting!
ExtendThreadDemo.java Verified on JDK 21 LTS 
// Step 1: Extend java.lang.Thread
class DownloadThread extends Thread {
    // Step 2: Override the run() method to define the thread's work
    @Override
    public void run() {
        System.out.println("DownloadThread is running inside: " + Thread.currentThread().getName());
    }
}

public class ExtendThreadDemo {
    public static void main(String[] args) throws InterruptedException {
        System.out.println("Main thread starting: " + Thread.currentThread().getName());

        // Step 3: Instantiate the custom thread object
        DownloadThread worker = new DownloadThread();
        worker.setName("Worker-Download");

        // Step 4: Call start() to spawn the new OS thread
        worker.start();

        // Wait for worker to finish
        worker.join();
        System.out.println("Main completed.");
    }
}
Terminal Output

Main completed.
⚠ The Major Drawback of Extending Thread

Java enforces single class inheritance. If your class already extends Thread, it can never extend any other useful base class (such as BaseService, JPanel, or HttpRequestHandler)! Furthermore, it tightly couples your business logic with low-level thread lifecycle controls. For this reason, professional Java development overwhelmingly prefers implementing Runnable.

Creating Threads with Runnable: Separation of Concerns

The preferred and architecturally clean way to define concurrent work in Java is implementing the java.lang.Runnable interface. Runnable is a single-method functional interface that encapsulates pure work, completely separated from the mechanism that executes it.

start() vs. run(): The Most Common Beginner Trap

Every Java learner makes this mistake at least once: they write a multithreaded class, call worker.run(), and are baffled when their application still freezes or runs completely sequentially! Understanding the mechanical difference between start() and run() is vital.

Visual 9: Execution Lanes — Direct run() vs. start() Spawning
Figure 9.1: Calling run() directly executes code synchronously on the caller's thread lane. Calling start() asks the OS to allocate a brand new execution lane.
Diagram Fallback (Text Summary):

Execution differences:

  • Direct task.run(): Stays on the main thread lane! No new thread is spawned. Main blocks until run() returns.
  • worker.start(): Spawns a dedicated new OS thread lane! The new thread runs run() concurrently while the main thread keeps moving.
StartVsRunDemo.java Verified on JDK 21 LTS 
public class StartVsRunDemo {
    public static void main(String[] args) throws InterruptedException {
        Runnable task = () -> {
            System.out.println("Executed by thread: " + Thread.currentThread().getName());
        };

        // MISTAKE: Calling run() directly
        System.out.println("--- 1. Calling run() directly ---");
        task.run(); // Runs on 'main' thread! Zero multithreading!

        // CORRECT: Calling start()
        System.out.println("
--- 2. Calling start() on a Thread ---");
        Thread worker = new Thread(task, "Dedicated-Worker");
        worker.start(); // Spawns a new OS thread!
        worker.join();
    }
}
Terminal Output

--- 2. Calling start() on a Thread ---

❌ Can You Restart a Terminated Thread?

No! In Java, a Thread instance has a one-way lifecycle. Once a thread starts and completes its run() method (entering the TERMINATED state), calling start() on it a second time will immediately throw an IllegalThreadStateException! If you need to perform the task again, you must instantiate a fresh new Thread(task).

Section 10

Thread Lifecycle and States: The Official State Machine

At any given moment during JVM execution, every Java thread resides in exactly one official state defined by the java.lang.Thread.State enum. Understanding these state transitions is crucial for diagnosing deadlocks, thread starvation, and application stalls.

Visual 11: Java Thread Lifecycle State Machine (The 6 Official States)
Figure 11.1: Official Java thread lifecycle state machine illustrating state transitions between NEW, RUNNABLE, BLOCKED, WAITING, TIMED_WAITING, and TERMINATED.
Diagram Fallback (Text Summary):

The 6 official states of Thread.State:

  1. NEW: The thread object has been created via new Thread(), but start() has not yet been invoked.
  2. RUNNABLE: The thread is either actively executing instructions on a CPU core or is ready and waiting in the OS scheduler queue. (Note: Java does NOT have a separate official "RUNNING" state!)
  3. BLOCKED: The thread is temporarily suspended waiting to acquire an intrinsic monitor lock held by another thread.
  4. WAITING: The thread is waiting indefinitely for another thread to perform a specific action (e.g. via join() or wait() without a timeout).
  5. TIMED_WAITING: The thread is paused for a specified duration (e.g. via Thread.sleep(ms), join(ms), or wait(ms)).
  6. TERMINATED: The thread has completed executing its run() method or was terminated due to an uncaught exception.

Detailed State Inspection Table

Thread.State What Is the Thread Doing? How Does It Enter This State? How Does It Leave?
NEW Allocated in RAM as a Java object only. new Thread(...) Calls .start()
RUNNABLE Executing on CPU or queued for a time slice. start() or awakened from wait/sleep. Lock contention, sleep, wait, or exits run().
BLOCKED Waiting to enter a synchronized block/method. Attempts to acquire an intrinsic lock held by another thread. The lock owner leaves the synchronized block.
WAITING Waiting indefinitely for another thread's signal. join() without timeout, wait(), LockSupport.park() Target thread terminates or notify() is called.
TIMED_WAITING Waiting for a specified duration of clock time. Thread.sleep(ms), join(ms), wait(ms) Time period expires or thread is interrupted.
TERMINATED Dead. Stack frame and execution registers destroyed. Finished run() logic or threw uncaught fatal exception. Cannot leave! Re-starting throws IllegalThreadStateException.
💡 What Is thread.getState() Used For?

Calling thread.getState() returns a momentary point-in-time snapshot of the thread's state. It is primarily designed for monitoring, health checks, and thread-dump diagnostics — never use getState() as a program synchronization tool!

Section 11

Thread.sleep(): Pausing Current Execution Safely

The static method Thread.sleep(long millis) pauses the currently executing thread for a specified duration of real-world milliseconds. It does not pause other threads in your application.

Visual 12: Thread.sleep() Timeline & The Intrinsic Lock Warning
Figure 12.1: Thread.sleep() moves the calling thread into TIMED_WAITING. Crucially: sleep() does NOT release any intrinsic monitor locks the thread currently holds!
Diagram Fallback (Text Summary):

Timeline mechanics of Thread.sleep():

  • Running Code (0-120ms) → Calls Thread.sleep(500) → Enters TIMED_WAITING (120-400ms) → Wakes up and resumes.
  • Critical Warning: If thread A enters a synchronized block, grabs lock L, and sleeps for 10 seconds, thread B trying to acquire lock L remains completely frozen for all 10 seconds!
ThreadSleepDemo.java Verified on JDK 21 LTS 
public class ThreadSleepDemo {
    public static void main(String[] args) {
        System.out.println("Starting countdown timer on: " + Thread.currentThread().getName());

        try {
            for (int i = 3; i >= 1; i--) {
                System.out.println("Countdown: " + i);
                // Pauses execution of the main thread for 500 milliseconds
                Thread.sleep(500);
            }
            System.out.println("Liftoff! Timer completed cleanly.");

        } catch (InterruptedException e) {
            // Always handle InterruptedException properly!
            System.err.println("Thread was interrupted while sleeping!");
            Thread.currentThread().interrupt(); // Restore interrupted status
        }
    }
}

❌ Anti-Pattern: Never Use sleep() to Coordinate Thread Order!

A common beginner mistake is writing Thread.sleep(2000) in the main thread in the hopes that a background worker will finish in under 2 seconds. What if the computer is under heavy load and the worker takes 2.1 seconds? Your program reads incomplete data and crashes! What if the worker finishes in 5 milliseconds? Your program wastes 1.995 seconds doing nothing! Always use join(), CountDownLatch, or Future.get() for coordination!

Section 12

Thread.join(): Coordinating Dependent Tasks

When an application spawns worker threads to perform independent calculations (such as parsing a data chunk or calculating a mathematical sum), the spawning thread frequently needs to wait until those workers finish before combining their results. The join() method allows one thread to pause and wait for the target thread to die.

🎓 Real-Life Analogy: The College Group Presentation

Imagine you and your classmate Kabir are presenting a semester project. You are responsible for delivering the final slide conclusions, while Kabir is calculating the experimental test statistics.

You cannot stand up in front of your professor and present the final conclusion slide until Kabir finishes his calculation! You sit patiently in your chair (calling kabir.join()). The moment Kabir finishes and hands you his finalized data sheet, you stand up and present the results!

Section 13

Thread Scheduling & Nondeterminism: The Unpredictable OS

In traditional single-threaded programming, execution is strictly deterministic: line 10 always runs after line 9, and the output sequence is 100% reproducible every time you run the program. In multithreading, thread execution is governed by the operating system kernel's Preemptive Thread Scheduler, which makes scheduling order fundamentally nondeterministic.

Visual 14: Thread Scheduling Nondeterminism — Multiple Valid Output Orders
Figure 14.1: Two executions of the exact same concurrent code yield completely different output interleavings due to operating system scheduling time slices.
Diagram Fallback (Text Summary):

Demonstration of nondeterministic runs:

  • Run #1: Thread-A Step 1 → Thread-A Step 2 → Thread-B Step 1 → Thread-A Step 3 → Thread-B Step 2.
  • Run #2: Thread-B Step 1 → Thread-A Step 1 → Thread-B Step 2 → Thread-B Step 3 → Thread-A Step 2.
  • Both outputs are completely correct and valid! A concurrent program must never rely on a specific interleaving order without explicit synchronization locks.
📌 Why Thread Priorities Are Unreliable

Java provides thread.setPriority(Thread.MAX_PRIORITY) (values from 1 to 10). However, the JVM merely passes these as informal hints to the underlying host OS. Windows, Linux, and macOS map Java priorities differently, and many modern OS schedulers completely ignore them to prevent thread starvation. Never rely on thread priorities for program correctness!

Section 14

Shared Data and Race Conditions: When Concurrency Breaks

A Race Condition occurs when two or more concurrent threads access shared mutable data simultaneously, and the final outcome of the program depends unpredictably on the exact microsecond timing of how their machine instructions interleave.

🏷️ Real-Life Analogy: Selling the Last Concert Ticket

Imagine an arena concert has exactly 1 ticket remaining.

  1. Clerk Alice looks at her screen: it says Remaining Tickets = 1.
  2. At the exact same microsecond, Clerk Bob looks at his screen: it also says Remaining Tickets = 1.
  3. Alice swipes her customer's credit card and confirms the sale (calculating 1 - 1 = 0).
  4. Bob swipes his customer's credit card and confirms the sale (calculating 1 - 1 = 0).

Both customers walk away with printed tickets for Seat #14! Two people show up at the stadium for the exact same seat. That is a race condition!

Visual 15: Race Condition Anatomy — Why count++ Loses Updates
Figure 15.1: count++ is not a single atomic step. It breaks into three distinct CPU instructions: Read, Modify, Write. Interleaving causes lost updates.
Diagram Fallback (Text Summary):

Step-by-step breakdown of how count++ loses an increment:

  1. Initial state in RAM: count = 0.
  2. Thread 1 reads count (value = 0).
  3. Thread 2 reads count (value = 0) before Thread 1 writes back!
  4. Thread 1 computes 0 + 1 = 1 and writes 1 to RAM.
  5. Thread 2 computes 0 + 1 = 1 and writes 1 to RAM, overwriting Thread 1's work!
  6. Outcome: Two increments occurred, but the final value in RAM is 1 instead of 2!

Reproducing the Race Condition in Code

UnsafeCounterDemo.java Verified on JDK 21 LTS 
class UnsafeCounter {
    private int count = 0;

    // NOT thread-safe: count++ is a read-modify-write compound operation!
    public void increment() {
        count++;
    }

    public int getCount() {
        return count;
    }
}

public class UnsafeCounterDemo {
    public static void main(String[] args) throws InterruptedException {
        UnsafeCounter counter = new UnsafeCounter();

        // 2 threads, each incrementing 5,000 times. Expected total = 10,000!
        Thread t1 = new Thread(() -> {
            for (int i = 0; i < 5000; i++) counter.increment();

The volatile Keyword: Cross-Core Memory Visibility

Modern computer CPUs do not read and write directly to main system RAM on every instruction; doing so would be hundreds of times too slow. Instead, each physical CPU core maintains ultra-fast local hardware memory: L1, L2, and L3 Caches. Without special instructions, a write by Core 1 lingers in Core 1's local cache and remains completely invisible to Core 2!

Diagram Fallback (Text Summary):

Atomic Classes: Lock-Free Hardware Compare-And-Swap (CAS)

While the synchronized keyword guarantees mutual exclusion, it relies on operating system monitor locks. When threads compete heavily for a monitor lock, the OS kernel must repeatedly suspend (block) and awaken threads, causing measurable context-switch overhead. In java.util.concurrent.atomic, Java provides Atomic Classes (like AtomicInteger, AtomicLong, and AtomicBoolean) that achieve thread safety without locks.

Visual 21: AtomicInteger Hardware Compare-And-Swap (CAS) Loop
Figure 21.1: Atomic classes utilize low-level hardware CPU instructions (e.g. cmpxchg on x86/ARM) to update variables atomically. If another thread intervened, the loop automatically retries instantly without OS thread blocking!
Diagram Fallback (Text Summary):

The 3-stage Compare-And-Swap (CAS) cycle:

  1. Read current value into local register (e.g. expected = 5, desired = 6).
  2. Execute single atomic CPU instruction: CAS(address, expected, desired).

    • If another thread altered memory to 7 → Return false (do not overwrite).
  3. On failure, loop around, read the new value (7), and retry instantly in user-space. Zero OS thread suspension!

Thread-Safe Collections: Modern Concurrent Data Structures

In Topic 19, you mastered standard Java collections like ArrayList and HashMap. Figure 22.1: Modern concurrent collections segregated by workload: ConcurrentHashMap (lock-free read caches), BlockingQueue (work queues), and CopyOnWriteArrayList (infrequent write listeners).

Why ConcurrentHashMap Is Faster Than Collections.synchronizedMap()

In legacy Java, developers wrapped maps with Collections.synchronizedMap(map). This placed a single, monolithic lock around the entire map: if Thread 1 was reading key "userA", Thread 2 trying to update key "userZ" was completely blocked!

Modern ConcurrentHashMap uses fine-grained bucket-level synchronization:

  • Reads (get()) are 100% lock-free! Thousands of threads can read simultaneously at maximum CPU bus speed.
  • Writes synchronize only on the single head node of the specific hash bucket being updated, allowing concurrent writes to different buckets without blocking each other.
⚠ The "Check-Then-Act" Compound Operation Trap

Just because a collection is thread-safe does not mean multiple method calls are automatically atomic! Consider this anti-pattern: 

// BUGGY CHECK-THEN-ACT RACE CONDITION!

    concurrentMap.put(key, computeValue());
}

Deadlocks: The Fatal Circular Wait Trap

A Deadlock is a catastrophic state where two or more threads are permanently blocked, each waiting for a lock that is held by the other thread. Neither thread can proceed, CPU usage drops to 0%, and the application freezes indefinitely until killed.

🔒 Real-Life Analogy: The Standoff Over Keys

Imagine two bank security guards, Officer Alice and Officer Bob, opening a high-security vault that requires two physical keys: Key A and Key B.

  • Alice grabs Key A from the cabinet and refuses to let go of it until she gets Key B.
  • At the exact same instant, Bob grabs Key B from the cabinet and refuses to let go of it until he gets Key A.

Both guards stand in the hallway staring at each other for eternity. That is a deadlock!

Visual 27: Deadlock — The Fatal Circular Wait Condition
Figure 27.1: Deadlock graph: Thread 1 holds Lock A and requests Lock B; Thread 2 holds Lock B and requests Lock A. Neither thread can proceed.
Visual 28: Deadlock Prevention — Global Lock Ordering Rule
Figure 28.1: Breaking circular wait by enforcing a strict global lock acquisition order. If both threads always acquire Lock A before Lock B, deadlocks are mathematically impossible!

The Four Coffman Conditions for Deadlock

A deadlock can occur only if all four of the following conditions are simultaneously met:

  1. Mutual Exclusion: The resources involved cannot be shared; only one thread holds a lock at a time.
  2. Hold and Wait: A thread currently holding at least one resource is actively waiting to acquire additional resources.
  3. No Preemption: Resources cannot be forcibly confiscated from a thread while it is holding them.
  4. Circular Wait: A closed chain of threads exists such that each thread holds a resource requested by the next thread.

15 Deadlock Circular Wait Application freezes with 0% CPU consumption. Thread 1 holds A and wants B; Thread 2 holds B and wants A. Enforce strict global lock acquisition ordering (always acquire A before B).
16 Using Ordinary Collections Concurrently ConcurrentModificationException / Data corruption. Accessing ArrayList or HashMap from multiple threads without locks. Use ConcurrentHashMap, CopyOnWriteArrayList, or BlockingQueue.
17 Compound Operations on Concurrent Collections Check-then-act race conditions (e.g. duplicate inserts). Assuming two separate thread-safe method calls behave as one atomic unit. Use atomic composite methods like map.computeIfAbsent() or putIfAbsent().
18 Busy-Waiting in Tight Loops 100% CPU fan spin while thread waits for a condition. Writing while(!ready) {} without pausing or yielding. Use BlockingQueue, CountDownLatch, or wait()/notify().
19 Unreleased ReentrantLock Permanent thread lockup after an exception. Called lock.lock() without putting lock.unlock() in a finally block. Always follow the pattern: lock.lock(); try { ... } finally { lock.unlock(); }.
20 Virtual Threads for CPU-Bound Math Zero performance gain; false architectural expectations. Assuming virtual threads add extra physical CPU cores to the silicon. Use virtual threads for high-volume I/O; use parallel streams/thread pools for CPU math.

        this.success = false;

    }

class FileCounterTask implements Callable<FileAnalysisResult> {
    private final Path filePath;

    public FileCounterTask(Path filePath) {
        this.filePath = filePath;
    }

    @Override
    public FileAnalysisResult call() {
        long lines = 0;
        long words = 0;
        try (BufferedReader reader = Files.newBufferedReader(filePath)) {
            String line;
            while ((line = reader.readLine()) != null) {
                lines++;
                String trimmed = line.trim();
                if (!trimmed.isEmpty()) {
                    String[] tokens = trimmed.split("\\s+");
                    words += tokens.length;
                }
            }
            return new FileAnalysisResult(filePath.getFileName().toString(), lines, words);
        } catch (NoSuchFileException e) {
            return new FileAnalysisResult(filePath.getFileName().toString(), "File not found on disk");
        } catch (IOException e) {
            return new FileAnalysisResult(filePath.getFileName().toString(), "I/O Read Error: " + e.getMessage());
        }
    }
}
