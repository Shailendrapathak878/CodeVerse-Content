Master non-blocking asynchronous programming in modern JavaScript. Explore the event loop, callback mechanisms and callback hell, promise states (pending, fulfilled, rejected), promise chaining with .then(), .catch(), and .finally(), sequential vs. parallel coordination with Promise.all(), clean async workflows with async/await, robust error handling with try...catch, and production API requests using fetch().

⏱ Introduction: Why Does JavaScript Work Asynchronously?

Imagine a student logs into the CodeVerse Learning Portal and clicks a button to view their final certification exam results. The server is located 5,000 miles away and needs 1.5 seconds to query the database, calculate the GPA score, and respond.

If JavaScript were strictly synchronous and blocking:

  • The entire browser tab would completely freeze for 1.5 seconds.
  • Animations would stutter and stop.
  • Typing into text fields or clicking navigation menus would fail to respond.
  • The operating system might show an ugly "Page Unresponsive" warning dialog.

To prevent this freezing, JavaScript is fundamentally non-blocking and asynchronous. When an operation requires time (such as fetching data over the network, waiting for a timer, reading files, or polling hardware), JavaScript schedules the task in the background and immediately continues executing other code!

🍕 The Restaurant Food-Ordering Analogy

Consider ordering food at a modern cafe:

  1. Synchronous Blocking (Terrible Experience): You place your order. The cashier halts the entire line, walks back into the kitchen, watches the pizza bake for 15 minutes, returns, hands it to you, and only then serves customer #2.
  2. Asynchronous Non-Blocking (JavaScript Way): You order. The cashier hands you a token/buzzer (a Promise) and immediately takes the next customer's order. While the kitchen prepares your food in the background, you sit and chat. When the food is ready, the buzzer alerts you (the Callback) to collect your meal!

1 Synchronous vs. Asynchronous JavaScript

JavaScript is inherently single-threaded: it has one Call Stack and can execute only one instruction at any single moment.

  • Synchronous Code: Each statement executes strictly in order. The runtime must wait for the current line to complete before proceeding to the next.
  • Asynchronous Code: Tasks that require waiting (such as timers or network calls) are handed off to the browser's Web APIs or Node.js runtime. JavaScript continues running the rest of the script immediately, and processes the callback later when the main stack clears via the Event Loop.
Example 1.1: Synchronous Execution Order JavaScript 
console.log("Start");
console.log("Learning JavaScript");
console.log("End");
Expected Console Output
Start Learning JavaScript End

Now observe what happens when we introduce a timer via setTimeout():

Example 1.2: Asynchronous Scheduling with setTimeout JavaScript 
console.log("Start");

// Hand off a 1000ms delay to the browser's timer engine:
setTimeout(() => {
  console.log("Timer finished");
}, 1000);

console.log("End");
Expected Console Output Order
Start End Timer finished
🕑 Execution Timeline: Why "End" Logs Before "Timer finished"
[T=0ms] • console.log("Start") runs immediately on Call Stack.
[T=1ms] • setTimeout(..., 1000) is called. Web API starts a 1000ms timer in the background.
[T=2ms] • console.log("End") executes immediately! Main script completes.
[T=1000ms+] • Timer expires → callback is placed on Task Queue → Event Loop pushes it to Call Stack → console.log("Timer finished") runs!
Important Timing Clarification: The second argument in setTimeout(fn, 1000) specifies the minimum delay before the callback is queued, NOT a hard real-time guarantee. If heavy synchronous work is occupying the main thread at 1,000ms, the callback will wait until the stack is completely clear!

2 What Is a Callback?

In JavaScript, functions are first-class citizens: you can assign them to variables, store them in arrays, and pass them as arguments to other functions.

A callback function is simply a function passed as an argument to another function, intended to be called ("called back") at an appropriate moment.

  • Synchronous Callback: Executes immediately during the execution of the higher-order function (e.g. Array.prototype.forEach or Array.prototype.map).
  • Asynchronous Callback: Executes at a future time after an asynchronous task (timer, network fetch, file I/O) has finished.
Example 2.1: A Synchronous Callback Function JavaScript 
function greetStudent(name, callback) {
  console.log(`Hello, ${name}!`);
  callback(); // Invokes the passed function immediately
}

function showCourse() {
  console.log("Welcome to JavaScript.");
}

// Pass function reference without parentheses:
greetStudent("Aarav", showCourse);
Expected Console Output
Hello, Aarav! Welcome to JavaScript.
Example 2.2: An Asynchronous Callback JavaScript 
console.log("Preparing lesson...");

setTimeout(() => {
  console.log("Lesson is ready!");
}, 1000);

console.log("You can continue exploring.");
Expected Console Output Order
Preparing lesson... You can continue exploring. Lesson is ready!

3 Callbacks with Realistic Tasks & Error-First Conventions

In asynchronous operations, a function cannot simply use a return statement because the caller has already moved on before the background task finishes. Instead, the asynchronous function receives the data and passes it into a callback.

Example 3.1: Simulated Asynchronous Data Loading with Callbacks JavaScript 
function loadStudent(callback) {
  setTimeout(() => {
    const student = {
      name: "Aarav",
      course: "JavaScript"
    };
    callback(student);
  }, 1000);
}

loadStudent((student) => {
  console.log("Loaded Student:", student.name);
  console.log("Course:", student.course);
});
Expected Console Output (After 1000ms Delay)
Loaded Student: Aarav Course: JavaScript

To handle potential failures (e.g. server downtime or missing records), Node.js and classical JavaScript established the Error-First Callback Pattern:

The Error-First Convention: callback(error, data)
• If an error occurred, the first parameter contains an Error object, and the second is null.
• If successful, the first parameter is null, and the second parameter carries the loaded data.
Example 3.2: Error-First Callback Implementation JavaScript 
function getMarks(callback) {
  setTimeout(() => {
    const hasError = false;

    if (hasError) {
      callback(new Error("Marks unavailable."), null);
      return;
    }

    callback(null, 85);
  }, 500);
}

getMarks((error, marks) => {
  if (error) {
    console.error("Failed to load marks:", error.message);
    return;
  }

  console.log("Marks:", marks);
});
Expected Console Output
Marks: 85

4 The Problem of Callback Hell

Callbacks work fine for a single asynchronous step. But what happens when an application needs four consecutive operations where each step depends on data from the previous one?

For example: 1. Login User → 2. Fetch User Profile → 3. Fetch Enrolled Courses → 4. Fetch Exam Grades.

Nesting callbacks inside callbacks creates a deeply indented pyramid structure known as Callback Hell (or the "Pyramid of Doom"):

Example 4.1: A Nested Callback Pyramid (Callback Hell) JavaScript 
setTimeout(() => {
  console.log("Step 1: Login complete");

  setTimeout(() => {
    console.log("Step 2: Profile loaded");

    setTimeout(() => {
      console.log("Step 3: Dashboard ready");
    }, 500);
  }, 500);
}, 500);

Why is Callback Hell dangerous?

  • Terrible Readability: Code expands horizontally across the screen rather than reading cleanly top-to-bottom.
  • Duplicated Error Handling: Every single nested level requires repetitive if (err) { ... } checks.
  • Fragile Refactoring: Moving or reordering a step requires rewriting nested parameter blocks.
Example 4.2: Mitigating Nesting by Extracting Named Functions JavaScript 
function showDashboard() {
  console.log("Step 3: Dashboard ready");
}

function loadProfile() {
  console.log("Step 2: Profile loaded");
  setTimeout(showDashboard, 500);
}

function login() {
  console.log("Step 1: Login complete");
  setTimeout(loadProfile, 500);
}

setTimeout(login, 500);
Expected Console Output
Step 1: Login complete Step 2: Profile loaded Step 3: Dashboard ready

5 What Is a Promise?

To solve Callback Hell, ES6 (ECMAScript 2015) introduced the Promise object.

A Promise is a JavaScript object that serves as a placeholder for a value that is not known right now, but will be resolved at some point in the future.

🖈 The Three States of a Promise
1. Pending
Initial state. The operation is currently running in the background.
⟶
2. Fulfilled
Success! resolve(value) was invoked. Handled via .then().
OR
3. Rejected
Failed! reject(error) was invoked. Handled via .catch().
Settled State Immutability: Once a Promise settles (transitions from pending to either fulfilled or rejected), it is permanently locked. It can never transition again or change its resolved value!
Example 5.1: Creating and Consuming a Resolved Promise JavaScript 
const resultPromise = new Promise((resolve, reject) => {
  // Simulate successful operation
  resolve("Lesson completed!");
});

resultPromise.then((message) => {
  console.log("Fulfillment Result:", message);
});
Expected Console Output
Fulfillment Result: Lesson completed!
Example 5.2: Creating and Consuming a Rejected Promise JavaScript 
const failedPromise = new Promise((resolve, reject) => {
  // Simulate failure
  reject(new Error("Lesson could not be loaded."));
});

failedPromise.catch((error) => {
  console.error("Rejection Caught:", error.message);
});
Expected Console Output
Rejection Caught: Lesson could not be loaded.

6 Promise Methods: then, catch, and finally

Promises expose three primary instance methods to attach handlers:

  • .then(onFulfilled): Executes when the promise fulfills successfully. Receives the resolved value.
  • .catch(onRejected): Executes if the promise rejects or an error is thrown anywhere in the chain.
  • .finally(onSettled): Guaranteed to execute when the promise settles (regardless of whether it succeeded or failed). Used for cleanup tasks like hiding loading spinners.
Example 6.1: Handling Success and Transforming Values JavaScript 
Promise.resolve(80)
  .then((marks) => {
    console.log("Initial Marks:", marks);
    return marks + 5; // Returned value feeds into the next .then()
  })
  .then((updatedMarks) => {
    console.log("Updated Marks:", updatedMarks);
  });
Expected Console Output
Initial Marks: 80 Updated Marks: 85
Example 6.2: Handling Failure and Guaranteed Cleanup with finally JavaScript 
let isLoading = true;
console.log("Loading indicator:", isLoading);

Promise.reject(new Error("Unable to load results."))
  .catch((error) => {
    console.log("Error Handled:", error.message);
  })
  .finally(() => {
    isLoading = false;
    console.log("Cleanup completed. Loading indicator:", isLoading);
  });
Expected Console Output
Loading indicator: true Error Handled: Unable to load results. Cleanup completed. Loading indicator: false

7 Promise Chaining

Every call to .then() returns a brand new Promise. This powerful feature allows you to chain multiple asynchronous steps sequentially, transforming Callback Hell into a flat, readable sequence:

Example 7.1: Chaining Sequential Mathematical Operations JavaScript 
Promise.resolve(10)
  .then((number) => {
    return number * 2; // 20
  })
  .then((number) => {
    return number + 5; // 25
  })
  .then((result) => {
    console.log("Final Calculation Result:", result);
  });
Expected Console Output
Final Calculation Result: 25
Example 7.2: Chaining Dependent Asynchronous Operations JavaScript 
function getStudent() {
  return Promise.resolve({
    id: 101,
    name: "Aarav"
  });
}

function getStudentMarks(studentId) {
  return Promise.resolve({
    studentId: studentId,
    marks: 90
  });
}

getStudent()
  .then((student) => {
    console.log("Step 1: Loaded Student", student.name);
    // Returning a Promise makes the NEXT .then() wait for it:
    return getStudentMarks(student.id);
  })
  .then((result) => {
    console.log("Step 2: Loaded Marks", result.marks);
  })
  .catch((error) => {
    console.error("Chain Failure:", error.message);
  });
Expected Console Output
Step 1: Loaded Student Aarav Step 2: Loaded Marks 90

8 Error Handling in Promise Chains

One of the biggest advantages of promises over callbacks is Error Propagation. In a promise chain, you don't need to check for errors at each individual step. A single .catch() placed at the end will intercept any error that occurs anywhere in the preceding chain!

Example 8.1: Catching a Rejected Promise in a Pipeline JavaScript 
function loadMarks() {
  return Promise.reject(new Error("Marks service unavailable."));
}

loadMarks()
  .then((marks) => {
    console.log("This line will NEVER run because the promise rejected!", marks);
  })
  .catch((error) => {
    console.log("Caught In Chain:", error.message);
  });
Expected Console Output
Caught In Chain: Marks service unavailable.
Example 8.2: Intercepting Errors Thrown Inside a .then() Block JavaScript 
Promise.resolve(10)
  .then((value) => {
    if (value < 20) {
      throw new Error("Value is too small. Minimum required is 20.");
    }
    return value * 2;
  })
  .then((value) => {
    console.log("Accepted:", value);
  })
  .catch((error) => {
    console.log("Validation failed:", error.message);
  });
Expected Console Output
Validation failed: Value is too small. Minimum required is 20.

9 What Are async Functions?

Introduced in ES2017 (ES8), the async keyword can be placed before any function declaration. It establishes two fundamental guarantees:

  1. Guaranteed Promise Return: An async function always returns a Promise. Even if you return a plain string or number like return 42;, JavaScript automatically wraps it inside Promise.resolve(42).
  2. Throws Equal Rejections: Any uncaught throw statement inside an async function causes the returned Promise to reject with that error.
Example 9.1: An Async Function Automatically Wraps Returned Values in a Promise JavaScript 
async function getCourse() {
  return "JavaScript";
}

// Notice we consume it using .then() because it returned a Promise!
getCourse().then((course) => {
  console.log("Course:", course);
});
Expected Console Output
Course: JavaScript
Example 9.2: Throwing Inside an Async Function Rejects the Returned Promise JavaScript 
async function loadCourse() {
  throw new Error("Course database offline.");
}

loadCourse().catch((error) => {
  console.log("Async Throw Caught:", error.message);
});
Expected Console Output
Async Throw Caught: Course database offline.

10 The await Keyword

The await keyword can only be used inside an async function (or at the top level of modern ES Modules).

When JavaScript encounters await somePromise:

  • It pauses the execution of that specific async function until the promise settles.
  • It does NOT freeze the browser tab or other background processes. Other event listeners and scripts continue executing normally.
  • If the promise fulfills, await unwraps and returns the resolved value directly.
  • If the promise rejects, await throws the rejection error, allowing you to catch it with a standard try...catch block!
Example 10.1: Awaiting a Resolved Promise JavaScript 
function getMarks() {
  return Promise.resolve(85);
}

async function showMarks() {
  const marks = await getMarks();
  console.log("Marks:", marks);
}

showMarks();
Expected Console Output
Marks: 85
Example 10.2: Awaiting a Rejected Promise Inside try...catch JavaScript 
function getFailedMarks() {
  return Promise.reject(new Error("Marks unavailable from server."));
}

async function showFailedMarks() {
  try {
    const marks = await getFailedMarks();
    console.log("Marks:", marks);
  } catch (error) {
    console.log("Caught Await Error:", error.message);
  }
}

showFailedMarks();
Expected Console Output
Caught Await Error: Marks unavailable from server.

11 Robust Error Handling with try...catch in async Functions

Building on what we learned in Topic 16 (Error Handling), combining try...catch...finally with async/await gives you the cleanest error-handling architecture in modern JavaScript.

Example 11.1: Recovering from an Expected Failure with a Fallback Default JavaScript 
async function loadProfile() {
  try {
    const profile = await Promise.reject(new Error("Profile service unavailable."));
    return profile;
  } catch (error) {
    console.log("Unable to load profile:", error.message);
    return null; // Explicit graceful recovery fallback
  }
}

loadProfile().then((profile) => {
  console.log("Profile Result:", profile);
});
Expected Console Output
Unable to load profile: Profile service unavailable. Profile Result: null
Example 11.2: Multiple Dependent Operations with Error Rethrow JavaScript 
async function loadDashboard() {
  try {
    const student = await Promise.resolve({ id: 101, name: "Aarav" });
    const marks = await Promise.resolve(92);

    return {
      name: student.name,
      marks: marks
    };
  } catch (error) {
    console.error("Dashboard loading failed:", error.message);
    throw error; // Re-throw so caller can display UI alert banner
  }
}

loadDashboard()
  .then((dashboard) => console.log("Dashboard Data:", dashboard))
  .catch(() => console.log("Please try again later."));
Expected Console Output
Dashboard Data: { name: 'Aarav', marks: 92 }

12 Sequential vs. Parallel Asynchronous Operations (Promise.all)

A frequent performance mistake among junior developers is writing sequential await calls for independent tasks that have no dependency on each other:

Example 12.1: Sequential Execution (Total Duration: 500ms + 500ms = 1000ms) JavaScript 
function taskA() {
  return new Promise((res) => setTimeout(() => res("Task A complete"), 500));
}
function taskB() {
  return new Promise((res) => setTimeout(() => res("Task B complete"), 500));
}

async function runSequentially() {
  // taskB does NOT start until taskA finishes!
  const a = await taskA();
  const b = await taskB();
  console.log(a);
  console.log(b);
}

runSequentially();

Because taskA and taskB are completely independent, they should run simultaneously in parallel! We can trigger them both at once using Promise.all():

Example 12.2: Parallel Coordination with Promise.all() (Total Duration: 500ms) JavaScript 
async function runTogether() {
  // Both tasks start immediately; Promise.all waits for both to settle:
  const [a, b] = await Promise.all([taskA(), taskB()]);
  console.log("Parallel Output:", a, "&", b);
}

runTogether();
Expected Console Output
Parallel Output: Task A complete & Task B complete
⏱ Execution Timeline: Sequential vs. Parallel
Sequential: |--- Task A (500ms) ---|--- Task B (500ms) ---| → Total: 1000ms
Parallel: |--- Task A (500ms) ---|
           |--- Task B (500ms) ---| → Total: 500ms (2x Faster!)
Promise.all Fail-Fast Warning: If any single promise in Promise.all([p1, p2, p3]) rejects, the entire Promise.all immediately rejects, discarding successful results. If you need all outcomes regardless of failure, use Promise.allSettled() instead!

13 Real API Requests with fetch()

An API (Application Programming Interface) allows client-side JavaScript to request data from external web servers.

The native fetch() function performs HTTP requests asynchronously and returns a Promise. However, using fetch() requires understanding two critical facts:

  1. Two-Step Asynchronous Process: First, you await the HTTP Response headers (await fetch()). Second, you must await the body parsing (e.g. await response.json()).
  2. HTTP Errors Do NOT Automatically Reject: fetch() only rejects on physical network failures (e.g. user offline or DNS failure). If the server returns an HTTP 404 Not Found or 500 Server Error, the promise resolves normally! You must check if (!response.ok) manually!
Example 13.1: Fetching Post Data with Status Code Verification JavaScript 
async function loadPost() {
  try {
    const response = await fetch("https://jsonplaceholder.typicode.com/posts/1");

    if (!response.ok) {
      throw new Error(`HTTP error: ${response.status}`);
    }

    const post = await response.json();
    console.log("Post Title:", post.title);
  } catch (error) {
    console.error("Could not load post:", error.message);
  }
}

loadPost();
Example 13.2: Fetching User Data and Handling Simulated Failures JavaScript 
async function loadUser() {
  try {
    const response = await fetch("https://jsonplaceholder.typicode.com/users/1");

    if (!response.ok) {
      throw new Error(`HTTP status: ${response.status}`);
    }

    const user = await response.json();
    console.log("User Name:", user.name);
    console.log("Email:", user.email);
  } catch (error) {
    console.error("Unable to load user information:", error.message);
  }
}

loadUser();

fetch(url) → 1. Loading State Activated → 2. Network Response Arrives → 3. Check response.ok → 4. Parse response.json() → 5. Render Success UI or Friendly Error Banner

14 Common Asynchronous Mistakes & Best Practices

❌ Mistake 1: Invoking a Callback Immediately Instead of Passing Its Reference
// INCORRECT: greet() executes immediately at runtime!
setTimeout(greet(), 1000);
✔ Corrected Code: Pass the function reference without parentheses: setTimeout(greet, 1000);
❌ Mistake 2: Forgetting to Return in a Promise Chain
// INCORRECT: The next .then() receives 'undefined' because return was omitted!
Promise.resolve(10)
  .then(n => { n * 2; }) // Missing return!
  .then(res => console.log(res)); // logs: undefined
✔ Corrected Code: .then(n => n * 2) or .then(n => { return n * 2; })
❌ Mistake 3: Forgetting the await Keyword
// INCORRECT: Assigns the pending Promise object instead of the resolved data!
const data = fetchData();
console.log(data.title); // undefined! data is Promise { <pending> }
✔ Corrected Code: const data = await fetchData();
❌ Mistake 4: Assuming fetch() Rejects on HTTP 404 / 500
// INCORRECT: fetch only rejects on physical network failures!
try {
  const res = await fetch("/missing-file"); // HTTP 404 does NOT throw!
} catch (e) { ... }
✔ Corrected Code: Always verify: if (!res.ok) throw new Error(`HTTP ${res.status}`);
❌ Mistake 5: Using Synchronous try...catch Around a Promise Without await
// INCORRECT: The rejection happens later in the microtask queue after try/catch exits!
try {
  Promise.reject(new Error("Boom!"));
} catch (e) { // NEVER CATCHES! UnhandledPromiseRejection! }
✔ Corrected Code: Add await: await Promise.reject(new Error("Boom!"));
❌ Mistake 6: Awaiting Independent Tasks Sequentially in a Loop
// INCORRECT: Unnecessarily runs 5 requests one after another (e.g. 5 x 500ms = 2500ms)
for (const id of ids) {
  await fetchUser(id);
}
✔ Corrected Code: Run in parallel: await Promise.all(ids.map(fetchUser));
❌ Mistake 7: Empty Catch Blocks (Silent Failure)
// INCORRECT: Hides the failure and leaves developers blind during debugging!
try { await loadData(); } catch (e) {}
✔ Corrected Code: Log diagnostic details and alert the user: console.error(e); setError("Failed to load");
❌ Mistake 8: Assuming setTimeout(fn, 1000) Guarantees Exact 1-Second Timing

A timer represents a minimum scheduling threshold. If the main thread is busy with long calculations, the callback will wait until the thread is idle.

✔ Best Practice: Never rely on setTimeout for precise cryptographic or financial timestamp deadlines.

Part A: 8 Output Prediction Challenges

Challenge 1: Zero-Delay setTimeout Execution Order

What is logged by this script?

console.log("A");
setTimeout(() => console.log("B"), 0);
console.log("C");

Answer: A, then C, then B.

Explanation: Even with a 0ms delay, setTimeout queues the callback on the Task Queue. It cannot run until the synchronous call stack is completely empty.

Challenge 2: Microtask vs. Macrotask Priority

Does a resolved Promise run before or after a 0ms timer?

setTimeout(() => console.log("Timer"), 0);
Promise.resolve().then(() => console.log("Promise"));

Answer: Promise, then Timer.

Explanation: Promises schedule Microtasks, whereas timers schedule Macrotasks. The event loop always empties the microtask queue before executing the next macrotask!

Challenge 3: Return Value of an Async Function

What does calling an async function that returns 100 produce?

async function getVal() { return 100; }
console.log(getVal());

Answer: Promise { <fulfilled>: 100 }

Explanation: Async functions always wrap their return value in a Promise. To read 100, you must use await getVal() or getVal().then(...).

Challenge 4: Forgetting Return in a Promise Chain

What is logged by the second .then() handler below?

Promise.resolve(5)
  .then((num) => {
    num * 2;
  })
  .then((res) => {
    console.log(res);
  });

Answer: undefined

Explanation: Because curly braces { ... } were used without an explicit return keyword, the handler returns undefined.

Challenge 5: Error Propagation Skipping Subsequent Then Blocks

What is logged below?

Promise.reject("Initial Error")
  .then(() => console.log("Step 1"))
  .then(() => console.log("Step 2"))
  .catch((e) => console.log("Caught:", e));

Answer: Caught: Initial Error

Explanation: Rejection immediately skips all intervening .then() fulfillment handlers until it reaches the first matching .catch().

Challenge 6: Promise.all Rejection Behavior

What happens if one promise in Promise.all rejects?

Promise.all([
  Promise.resolve(10),
  Promise.reject("Failure"),
  Promise.resolve(30)
]).then(console.log).catch((e) => console.log("All Caught:", e));

Answer: All Caught: Failure

Explanation: Promise.all() implements fail-fast semantics: if any single promise rejects, the entire combined promise rejects immediately.

Challenge 7: The finally() Callback Argument

Does .finally((val) => console.log(val)) receive the resolved value?

Answer: Value: undefined

Explanation: The callback supplied to .finally() receives no arguments because cleanup routines should run identically regardless of success or failure.

Challenge 8: Await Inside Synchronous forEach

Does [1, 2].forEach(async (n) => await delay(n)) wait sequentially?

Answer: NO! forEach does not wait for async callbacks.

Explanation: Array.prototype.forEach is synchronous and ignores promises returned by its callback. Use a modern for...of loop or Promise.all() instead!

Exercise 6: Automatic Retry Function

Task: Write retryAsync(fn, retries = 3) that retries calling an async function up to 3 times before finally throwing.

View Solution 
async function retryAsync(fn, retries = 3) {
  for (let attempt = 1; attempt <= retries; attempt++) {
    try {
      return await fn();
    } catch (err) {
      if (attempt === retries) throw err;
    }
  }
}
