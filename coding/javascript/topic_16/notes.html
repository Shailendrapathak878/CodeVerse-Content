⚠ Lesson Introduction: Why Error Handling Matters

Imagine you deploy a new user registration portal. A user enters their name, but accidentally leaves the email field blank. If your JavaScript assumes the email string always exists and immediately calls email.toLowerCase(), the browser encounters an unhandled TypeError: Cannot read properties of undefined. The script crashes, the submit button remains frozen in a disabled state, and the user stares at a broken screen wondering if their account was created.

Errors are not an embarrassment; they are an inevitable reality of computer programming. Real-world software constantly interacts with unpredictable human inputs, spotty cellular networks, corrupted API payloads, and unexpected hardware conditions:

  • A financial calculator receives text (e.g. "twenty") instead of a numeric digit.
  • A mobile banking app attempts to read an account balance from a server that is temporarily offline.
  • An e-commerce checkout tries to parse invalid or truncated JSON received from a web service.
  • A function attempts to divide by an unexpected value of zero.

1 What Is an Error?

In JavaScript, an error is an abnormal condition that occurs during code parsing or execution, disrupting the normal flow of instructions. When an error occurs, the JavaScript engine creates and throws an Error object containing detailed diagnostics.

To debug effectively, programmers distinguish between three related terms:

  • Bug: A flaw or defect in your source code logic written by the developer (e.g. subtracting instead of adding).
  • Exception: An exceptional runtime condition that disrupts normal program execution (e.g. attempting to parse malformed JSON). Exceptions can be “caught” and handled.
  • Error Object: The built-in JavaScript object (e.g. Error, TypeError) that records what went wrong and where.

The Three Major Error Categories

Error Category When Does It Occur? Can try...catch Catch It? How to Fix It
1. Syntax Error During the parsing/compilation phase before execution begins. Code violates language grammar rules. No (in the same script block) Correct the invalid syntax (matching quotes, brackets, keywords) in your code editor.
2. Runtime Error While the script is actively running (e.g. accessing properties on null, calling undefined variables). Yes Use input validation and wrap risky operations in try...catch blocks.
3. Logical Error The code runs completely without crashing, but computes or displays the wrong result. No (no exception is thrown) Rethink the algorithm, review math formulas, and write automated unit tests.

The JavaScript engine parses code into an Abstract Syntax Tree (AST) before running a single line. If syntax is malformed, the parser aborts immediately. Not even a surrounding try...catch block in the same script tag can intercept a syntax error!

3 Prevent Errors with Validation

The most effective error-handling strategy is preventing errors before they happen. Validating incoming data using guard clauses stops bad values at the door before they reach critical calculations or database operations.

Example 3.1: Validating Numeric Inputs with Number.isNaN JavaScript 
function doubleNumber(input) {
  // 1. Guard against empty string or whitespace-only inputs
  if (typeof input !== "string" || input.trim() === "") {
    return "Please enter a valid number.";
  }

  // 2. Attempt numeric conversion
  const number = Number(input);

  // 3. Verify the conversion produced a valid finite number
  if (Number.isNaN(number) || !Number.isFinite(number)) {
    return "Please enter a valid number.";
  }

  return number * 2;
}

console.log(doubleNumber("12"));    // 24
console.log(doubleNumber("hello")); // "Please enter a valid number."
console.log(doubleNumber("   "));   // "Please enter a valid number."
Expected Console Output
24 Please enter a valid number. Please enter a valid number.
Example 3.2: Multi-Criteria Age Boundary Validation JavaScript 
function checkAge(age) {
  // Type & finiteness check
  if (typeof age !== "number" || !Number.isFinite(age)) {
    return "Age must be a valid number.";
  }

  // Reasonable range boundary checks
  if (age < 0 || age > 120) {
    return "Age must be between 0 and 120.";
  }

  return "Age accepted.";
}

console.log(checkAge(20));    // "Age accepted."
console.log(checkAge(-5));    // "Age must be between 0 and 120."
console.log(checkAge("20"));  // "Age must be a valid number."
Expected Console Output
Age accepted. Age must be between 0 and 120. Age must be a valid number.

4 The try...catch Statement

When an operation cannot be completely guaranteed by validation alone (such as parsing external JSON or interacting with storage devices), JavaScript provides the try...catch statement.

  • try block: Encloses risky code that might throw an exception.
  • catch block: Executes only if an exception is thrown inside the try block. It receives the caught error object as a parameter.
Example 4.1: Intercepting a Runtime Exception JavaScript 
try {
  const student = null;
  // This line throws a TypeError
  console.log(student.name);
} catch (error) {
  console.log("Something went wrong.");
  console.log("Error category:", error.name);
}

console.log("Program execution continues smoothly!");
Expected Output (Script Keeps Running Without Crashing)
Something went wrong. Error category: TypeError Program execution continues smoothly!
Example 4.2: Safely Parsing JSON Strings JavaScript 
function parseUserData(jsonString) {
  try {
    const data = JSON.parse(jsonString);
    return `Loaded user: ${data.name}`;
  } catch (error) {
    return "Invalid JSON format. Could not parse data.";
  }
}

// 1. Valid JSON
console.log(parseUserData('{"name":"Aarav","course":"JavaScript"}'));

// 2. Invalid JSON (illegal trailing comma)
console.log(parseUserData('{"name": "Aarav",}'));
Expected Output
Loaded user: Aarav Invalid JSON format. Could not parse data.

5 Understanding the Error Object

The caught error object contains standard properties designed to assist developers in diagnostics:

  • error.name: The classification name of the error (e.g. "SyntaxError", "TypeError").
  • error.message: A human-readable description of what failed.
  • error.stack: A detailed call stack trace listing the exact files, functions, and line numbers where the exception originated.
Example 5.1: Inspecting Core Error Properties JavaScript 
try {
  JSON.parse("{invalid}");
} catch (error) {
  console.log("Name:", error.name);
  console.log("Message:", error.message);
  console.log("Stack available:", Boolean(error.stack));
}
Expected Console Diagnostic Output
Name: SyntaxError Message: Expected property name or '}' in JSON at position 1 Stack available: true
Example 5.2: Separating Developer Diagnostics from User-Facing Messages JavaScript 
function handleUserAction() {
  try {
    // Simulating an unexpected runtime failure
    JSON.parse("<bad-xml>");
  } catch (error) {
    // 1. Developer Diagnostic (sent to internal logging or console)
    console.error("[Internal Diagnostic]", error.name, error.message);

    // 2. User-Facing Feedback (safe, friendly, non-technical)
    return "We couldn't process your request right now. Please try again.";
  }
}

const userFeedback = handleUserAction();
console.log("User Banner:", userFeedback);
❌ Bad: Raw Internal Stack Trace Shown to User

✔ Good: Friendly User-Facing Recovery Banner

6 The finally Block

The optional finally block executes guaranteed, 100% of the time after the try and catch blocks finish, regardless of whether an error was thrown, caught, or even if an early return statement was encountered.

finally is the ideal home for cleanup tasks:

  • Stopping a loading spinner so the UI doesn't freeze permanently.
  • Closing file streams or database connection pools.
  • Re-enabling disabled submit buttons.
Example 6.1: Guaranteed Execution Order JavaScript 
try {
  console.log("1. Starting operation");
  throw new Error("Something failed");
} catch (error) {
  console.log("2. Handled error:", error.message);
} finally {
  console.log("3. Cleanup completed in finally block");
}
Expected Output
1. Starting operation 2. Handled error: Something failed 3. Cleanup completed in finally block
Example 6.2: Guaranteed Loading State Teardown JavaScript 
let isLoading = true;

try {
  console.log("Loading data... (isLoading = true)");
  // Simulating a data processing failure
  throw new Error("Data unavailable");
} catch (error) {
  console.log("Error caught:", error.message);
} finally {
  // ALWAYS runs whether try succeeded or failed!
  isLoading = false;
  console.log("Spinner dismissed! (isLoading = false)");
}
Expected Output
Loading data... (isLoading = true) Error caught: Data unavailable Spinner dismissed! (isLoading = false)

7 Throwing Custom Errors with throw

JavaScript allows developers to generate and signal their own exceptions using the throw keyword combined with the standard new Error("description") constructor.

💡 Always Throw an Error Object, Not a Plain String

While JavaScript technically allows writing throw "Invalid input", doing so is considered bad practice because string literals lack .stack traces and .name metadata. Always write throw new Error("Invalid input").

Example 7.1: Validating a Banking Withdrawal JavaScript 
function withdraw(balance, amount) {
  if (!Number.isFinite(amount) || amount <= 0) {
    throw new Error("Withdrawal amount must be a positive number.");
  }

  if (amount > balance) {
    throw new Error("Insufficient funds in account balance.");
  }

  return balance - amount;
}

try {
  console.log("Remaining:", withdraw(1000, 300)); // 700
  withdraw(1000, 1500); // Triggers exception!
} catch (error) {
  console.log("Transaction rejected:", error.message);
}
Expected Console Output
Remaining: 700 Transaction rejected: Insufficient funds in account balance.
Example 7.2: Catching a Custom Student Registration Validation Error JavaScript 
function registerStudent(name) {
  if (typeof name !== "string" || name.trim() === "") {
    throw new Error("Student name is required and cannot be blank.");
  }

  return `Registered: ${name.trim()}`;
}

try {
  console.log(registerStudent("   "));
} catch (error) {
  console.log("Registration failed:", error.message);
}
Expected Output
Registration failed: Student name is required and cannot be blank.

8 try...catch with Asynchronous Code

A frequent source of bugs among developers is assuming that a synchronous try...catch can catch errors thrown inside asynchronous callbacks like setTimeout or unawaited Promises.

⚠ Synchronous try...catch Cannot Intercept Future Callbacks!

If you wrap a setTimeout(() => { throw new Error(); }, 1000) inside a synchronous try...catch, the try block finishes executing in milliseconds. When the timer callback fires 1 second later on the event loop, the try...catch is long gone! To catch errors in asynchronous code, use async/await with try...catch or .catch() on Promises.

Example 8.1: Catching Async Function Rejections with await JavaScript 
async function loadStudent() {
  // Simulating a rejected asynchronous operation
  throw new Error("Student profile data unavailable from database.");
}

async function main() {
  try {
    // The await keyword unwraps the rejection into a catchable exception
    const student = await loadStudent();
    console.log(student);
  } catch (error) {
    console.log("Handled async error:", error.message);
  }
}

main();
Expected Console Output
Handled async error: Student profile data unavailable from database.
Example 8.2: Safe Network Requests with fetch & response.ok Check JavaScript 
async function loadPost(postId) {
  try {
    const response = await fetch(`https://jsonplaceholder.typicode.com/posts/${postId}`);

    // CRUCIAL: fetch() DOES NOT REJECT on HTTP 404 or 500! Must check response.ok
    if (!response.ok) {
      throw new Error(`HTTP Server returned status: ${response.status}`);
    }

    const post = await response.json();
    console.log("Loaded Post Title:", post.title);
  } catch (error) {
    console.log("Unable to load the post:", error.message);
  }
}

loadPost(1);
Expected Console Output (When Online)
Loaded Post Title: sunt aut facere repellat provident occaecati excepturi optio reprehenderit

9 Errors in Event Handlers and Forms

In modern client-side JavaScript, event listeners are the frontline where user interactions meet business logic. An uncaught exception inside a button click listener halts that specific handler and clutters the console with errors.

⚠ The Division-By-Zero Trap in JavaScript

In many languages (like Python or Java), dividing a number by zero immediately raises a ZeroDivisionError exception. JavaScript does NOT throw an exception for division by zero! Instead, it silently returns Infinity or -Infinity. Therefore, you cannot rely on try...catch alone to catch division by zero; you must explicitly check if (divisor === 0)!

Example 9.1: Why try...catch Alone Does Not Catch Division By Zero JavaScript 
try {
  const total = 100 / 0;
  // Does NOT enter the catch block! total is Infinity
  console.log("Result is:", total);
} catch (error) {
  console.log("This line will NEVER run for division by zero!");
}
Actual Browser Output
Result is: Infinity
Example 9.2: Correct Division with Explicit Zero Validation JavaScript 
function divide(a, b) {
  if (!Number.isFinite(a) || !Number.isFinite(b)) {
    throw new Error("Both values must be valid finite numbers.");
  }

  if (b === 0) {
    throw new Error("Cannot divide by zero. Divisor must be non-zero.");
  }

  return a / b;
}

try {
  console.log("10 / 2 =", divide(10, 2));
  console.log("10 / 0 =", divide(10, 0));
} catch (error) {
  console.log("Caught division error:", error.message);
}
Expected Console Output
10 / 2 = 5 Caught division error: Cannot divide by zero. Divisor must be non-zero.

10 Debugging and Reading Console Errors

Every browser (Chrome, Firefox, Edge, Safari) includes built-in Developer Tools (press F12 or Ctrl+Shift+I). When an error occurs, the Console panel acts as your primary investigative dashboard.

👀 The Senior Engineer's 7-Step Debugging Checklist
  1. 1. Read the full error name & message: Don’t guess. Does it say ReferenceError or TypeError?
  2. 2. Identify file name & line number: Look at the right-hand side of the error stack in the console (e.g. app.js:42).
  3. 3. Inspect variable values: What exact data is held in memory at that line? Is a variable unexpectedly null or undefined?
  4. 4. Identify the root cause: Did an API return an empty array? Did an input fail conversion?
  5. 5. Apply the smallest appropriate fix: Add a guard clause, fix a typo, or wrap an unvalidated parser.
  6. 6. Rerun the test suite: Verify that the normal success path still functions correctly.
  7. 7. Deliberately test the failing edge case: Ensure the bug cannot silently regress in the future.

11 Common Mistakes and Best Practices

Review these 12 classic error-handling blunders before writing production software:

❌ Mistake 1: Silently Swallowing Exceptions (The Empty Catch Block)
// INCORRECT: The error is completely ignored
try {
  saveUserData();
} catch (e) {} // Silence! Bugs become completely invisible!
✔ Corrected Code: At minimum, log the error for developers: catch (err) { console.error("Save failed:", err); showUserAlert("Could not save data."); }
❌ Mistake 2: Using try...catch for Simple Input Validation
// INCORRECT: Abusing exceptions for normal program control flow
try {
  if (name === "") throw "empty";
} catch (e) { ... }
✔ Corrected Code: Use simple if guard clauses: if (!name.trim()) return "Name is required";
❌ Mistake 3: Assuming fetch() Rejects on HTTP 404 or 500
// INCORRECT: fetch only rejects on network disconnection, NOT HTTP 404!
const res = await fetch("/missing-file");
const data = await res.json(); // Fails trying to parse HTML error page!
✔ Corrected Code: Always check: if (!res.ok) throw new Error(`HTTP ${res.status}`);
❌ Mistake 4: Forgetting await Inside try...catch
// INCORRECT: Missing await means the promise rejection occurs AFTER try/catch exits!
try {
  fetchData(); // Returns pending promise; try/catch exits immediately!
} catch (err) { ... }
✔ Corrected Code: Add await: await fetchData();
❌ Mistake 5: Assuming try...catch Catches Errors in setTimeout
// INCORRECT: The timer callback executes on a future event loop tick
try {
  setTimeout(() => { throw new Error("Boom!"); }, 100);
} catch (e) { // Never catches the error! }
✔ Corrected Code: Put the try...catch inside the callback function.
❌ Mistake 6: Throwing Raw Strings Instead of Error Objects
// INCORRECT: No stack trace or line number metadata
throw "Invalid age";
✔ Corrected Code: throw new Error("Invalid age");
❌ Mistake 7: Confusing Logical Errors with Thrown Exceptions
// INCORRECT: Believing try/catch will detect wrong formulas
try {
  const area = width + height; // Supposed to be width * height
} catch (e) { ... } // No exception is thrown!
✔ Corrected Code: Use automated test assertions to verify mathematical outputs.
❌ Mistake 8: Assuming Division By Zero Throws an Exception
// INCORRECT: 10 / 0 returns Infinity without throwing
try {
  const ans = 10 / 0;
} catch (e) { ... }
✔ Corrected Code: Explicitly check if (divisor === 0) throw new Error("Cannot divide by zero");
❌ Mistake 9: Exposing Sensitive Database Stack Traces to End Users
// INCORRECT: Security vulnerability & poor UX
uiElement.textContent = error.stack;
✔ Corrected Code: Show clean feedback: "Could not connect to service. Please try again."
❌ Mistake 10: Returning Fake Success Objects After Failures
// INCORRECT: Hides the failure and corrupts downstream application state
catch (e) { return { status: "success", data: [] }; }
✔ Corrected Code: Return explicit failure descriptors: return { status: "error", error: e.message };
❌ Mistake 11: Forgetting Cleanup on Error Paths
// INCORRECT: If save() throws, spinner never turns off!
spinner.show();
save();
spinner.hide();
✔ Corrected Code: Put spinner.hide() in a finally block.
❌ Mistake 12: Failing to Test Edge Cases & Error Paths

Only testing happy paths leaves edge cases unverified until real users encounter them in production.

✔ Corrected Code: Write automated tests deliberately passing negative numbers, zero, null, empty strings, and simulated server outages.

Part A: 8 Output Prediction Challenges

Challenge 1: The finally Block Execution Order

What is printed to the console when the following code executes?

try {
  console.log("A");
  throw new Error("B");
} catch (e) {
  console.log(e.message);
} finally {
  console.log("C");
}
console.log("D");

Answer:

A B C D

Explanation: "A" logs before the throw. The catch block catches the error and prints its message ("B"). The finally block is guaranteed to run ("C"). Finally, normal program execution proceeds ("D").

Challenge 2: Division by Zero Without Validation

Does the catch block run below?

try {
  const result = 50 / 0;
  console.log("Result:", result);
} catch (error) {
  console.log("Caught:", error.message);
}

Answer: NO! The catch block does not run.

Result: Infinity

Explanation: JavaScript evaluates 50 / 0 to Infinity rather than throwing an exception. Without an explicit guard clause, it stays inside the try block.

Challenge 3: Return in try vs. finally

What does this function return?

function test() {
  try {
    return 1;
  } finally {
    return 2;
  }
}
console.log(test());

Answer: 2

Explanation: A return statement in a finally block overrides any pending return value from the preceding try or catch blocks.

Challenge 4: Error Thrown Inside Catch Block

What happens when an error is thrown inside a catch block?

try {
  throw new Error("Initial failure");
} catch (e) {
  console.log("Caught 1");
  throw new Error("Secondary failure");
} finally {
  console.log("Finally cleanup");
}

Answer: Logs "Caught 1", then "Finally cleanup", and then the program halts with an uncaught Error: Secondary failure.

Explanation: An exception thrown inside catch will not be re-caught by that same block; it bubbles up to any outer caller, but finally is still guaranteed to execute first.

Challenge 5: Throwing a Plain String

What is logged by e.stack below?

try {
  throw "Access Denied";
} catch (e) {
  console.log(typeof e);
  console.log(e.stack);
}

Answer:

string undefined

Explanation: Because a primitive string was thrown instead of new Error(), e has no .stack or .name properties.

Challenge 6: Synchronous try...catch Around setTimeout

Will the catch block intercept the timer error?

try {
  setTimeout(() => {
    throw new Error("Timer Boom");
  }, 100);
} catch (e) {
  console.log("Caught timer error!");
}

Answer: NO! The catch block will NOT catch it.

Explanation: setTimeout schedules the callback for a future turn of the event loop. The try...catch statement completes execution immediately, so the callback runs in an unhandled global context.

Challenge 7: fetch() 404 Status Behavior

Does fetch() enter the catch block if the server returns HTTP 404 Not Found?

try {
  const res = await fetch("https://example.com/nonexistent-endpoint");
  console.log("Success flag:", res.ok);
} catch (err) {
  console.log("Caught network failure");
}

Answer: It does NOT enter the catch block! It logs: Success flag: false.

Explanation: fetch() resolves its promise normally for any valid HTTP response from the server, even 404 or 500. Only physical network disconnections cause rejection.

Challenge 8: Optional Chaining with Nullish Coalescing

What is the output when student is null?

const student = null;
const grade = student?.grades?.math ?? "No grade recorded";
console.log(grade);

Answer: "No grade recorded"

Explanation: Optional chaining safely returns undefined without throwing a TypeError, and the nullish coalescing operator (??) supplies the fallback string.
