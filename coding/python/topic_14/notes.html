Introduction to Errors & Their Categories

📌 What is an Error?

In computer programming, an error is an abnormal condition or flaw in a program that prevents it from executing successfully or causes it to produce incorrect output. In Python, not all errors are created equal. They fall into three distinct categories:

Error Category When It Occurs Representative Example Can Program Start? Typical Solution
1. Syntax Error Parsing phase (before bytecode compilation) if True
    print("Hi") (missing colon)		 ❌ No. Python halts before running line 1. Fix syntax to comply with Python grammatical rules.
2. Runtime Exception Execution phase (while code is actively running) number = 10 / 0 (ZeroDivisionError) ✅ Yes. Runs until the faulty statement is evaluated. Handle gracefully with try-except blocks.
3. Logical Error Execution phase (runs completely without crashing) area = length + width (intended *) ✅ Yes. Runs to finish, but answers are wrong. Fix algorithmic logic and mathematical formulas.
🚫 Everyday Language vs. Python Terminology

In everyday speech, people loosely call any software defect a "bug" or "error". In Python, however, a SyntaxError is a structural grammatical violation that prevents parsing, whereas an Exception is a special object created dynamically at runtime when an exceptional event disrupts normal execution.

✅ The Goal of Exception Handling

You cannot prevent external issues like a user typing letters into a number prompt, a network timeout, or a missing disk file. But with exception handling, your program detects these events and responds gracefully instead of abruptly crashing!

02

What Is an Exception?

⚡ Definition of an Exception

An exception is an object representing an unexpected runtime disruption. When Python encounters an illegal operation (e.g., dividing by zero or indexing an empty list), it halts normal sequential flow and raises an exception object containing diagnostic details about the failure.

Once raised, an exception begins propagating backwards through the call stack looking for an enclosing try-except handler. If no handler is found, Python halts the process and outputs a standard traceback to the console.

Exception Lifecycle & Propagation Flowchart
Normal Execution
Statements run top-down
→
Disruption Occurs
e.g., invalid conversion
→
Exception Raised
Object created
↓
Branch A: Matching Handler Found
Python executes the except block. Execution recovers and continues smoothly past the handler.
Branch B: No Handler Found (Unhandled)
Exception propagates up the call stack. Program halts with non-zero exit code and dumps a full traceback.
☝ Critical Mindset: Handling ≠ Fixing

Catching an exception does not magically repair corrupted data or find a missing file. Handling means your program safely decides what to do next — informing the user, retrying, falling back to a safe default, or logging the incident — rather than dying abruptly.

03

Anatomy of an Exception and Traceback

When an unhandled exception occurs, Python prints a traceback (stack trace). Learning to read a traceback is one of the most vital debugging skills in software development.

PYTHON: Code That Triggers a Nested Call Traceback
def calculate_ratio(a, b):
    return a / b

def process_data():
    calculate_ratio(10, 0)

process_data()
► UNHANDLED PYTHON TRACEBACK (CONSOLE)
Traceback (most recent call last): File "demo.py", line 7, in <module> process_data() File "demo.py", line 5, in process_data calculate_ratio(10, 0) File "demo.py", line 2, in calculate_ratio return a / b ZeroDivisionError: division by zero
🔍 How to Read a Traceback Like an Expert
  1. Step 1: Look at the Very Last Line First: It states the Exception Type (ZeroDivisionError) and the Exception Message (division by zero).
  2. Step 2: Read Upwards: The line directly above the error shows the exact line of code that triggered the failure (return a / b).
  3. Step 3: Trace the Call Stack: Each File "...", line ..., in ... block represents an active stack frame, showing which function called which to reach the point of failure.

The try and except Blocks

🛡️ Basic try-except Syntax
try:
    # Protected code that might raise an exception
except TargetException:
    # Recovery code executed only if TargetException occurs
PYTHON: Intercepting a ZeroDivisionError
try:
    print("Step 1: Attempting division...")
    result = 10 / 0
    print("Step 2: This line will NOT execute!")
except ZeroDivisionError:
    print("Step 3: Caught division by zero! Assigning fallback.")
    result = 0.0

print(f"Program continues safely. Result = {result}")
► OUTPUT
Step 1: Attempting division... Step 3: Caught division by zero! Assigning fallback. Program continues safely. Result = 0.0
☝ Golden Rule: Keep try Blocks Tight

Never wrap 200 lines of business logic inside a single giant try block! Only enclose the specific 1–3 lines that perform risky I/O, user conversions, or mathematical divisions. Overly broad try blocks mask bugs in unrelated statements.

05

Multiple except Blocks

A single protected operation might fail for multiple independent reasons. Python allows attaching multiple dedicated except handlers to a single try block.

PYTHON: Multiple Dedicated Handlers
def calculate_share(raw_input_value):
    try:
        number = int(raw_input_value)
        share = 100 / number
        print(f"Share calculated: {share}")
    except ValueError:
        print("❌ ValueError: Please provide a valid integer string.")
    except ZeroDivisionError:
        print("❌ ZeroDivisionError: Share cannot be divided among 0 recipients.")

# Case 1: Valid input
calculate_share("5")

# Case 2: Zero divisor
calculate_share("0")

# Case 3: Non-numeric input
calculate_share("hello")
► OUTPUT
Share calculated: 20.0 ❌ ZeroDivisionError: Share cannot be divided among 0 recipients. ❌ ValueError: Please provide a valid integer string.
06

Catching Multiple Exception Types in a Single Handler

When multiple distinct exception types require identical recovery logic, you can group them into a tuple passed to a single except statement:

PYTHON: Grouping Exceptions in a Tuple
def safe_parse_and_divide(val_str):
    try:
        result = 100 / int(val_str)
        print(f"Result: {result}")
    except (ValueError, ZeroDivisionError) as err:
        # Both exceptions trigger this exact same fallback
        print(f"Math/parsing fault encountered: {type(err).__name__} → {err}")

safe_parse_and_divide("0")
safe_parse_and_divide("xyz")
► OUTPUT
Math/parsing fault encountered: ZeroDivisionError → division by zero Math/parsing fault encountered: ValueError → invalid literal for int() with base 10: 'xyz'
07

Exception Handling Order (Subclasses First)

Python evaluates except clauses sequentially from top to bottom. The first handler whose exception type matches or is a parent class of the raised exception executes. All subsequent handlers are skipped!

❌ Dead Code Anti-Pattern
try:
    int("abc")
except Exception:  # Catches EVERYTHING!
    print("General error")
except ValueError: # DEAD CODE! Never runs!
    print("Specific value error")
✅ Correct Specific-to-Broad Order
try:
    int("abc")
except ValueError: # Specific first!
    print("Specific value error")
except Exception:  # Broad safety net last
    print("Unexpected general error")
Part C • Else, Finally, and Cleanup

The else Block

✅ The else Clause

The else block executes if and only if the try block runs to completion without raising any exceptions.

PYTHON: The else Block in Action
def convert_age(text):
    try:
        age = int(text)
    except ValueError:
        print("Failed to convert age: non-numeric string.")
    else:
        # Runs ONLY if conversion succeeded
        print(f"Conversion success! Registered age in months: {age * 12}")

convert_age("25")
convert_age("twenty")
► OUTPUT
Conversion success! Registered age in months: 300 Failed to convert age: non-numeric string.
🤔 Why not just put the code at the end of try?

Placing success actions inside else keeps your try block small and prevents accidentally catching exceptions raised by the success-handling code itself!

09

The finally Block

🔒 Guaranteed Cleanup with finally

The finally block is guaranteed to execute before leaving the try statement, regardless of whether:

  • The try block finished normally.
  • An exception occurred and was caught by an except handler.
  • An exception occurred and was not caught (executes before propagating!).
  • A return, break, or continue statement was encountered!
PYTHON: Demonstrating finally Execution
def divide_test(x, y):
    print(f"\n--- Testing {x} / {y} ---")
    try:
        print("1. Inside try block")
        res = x / y
        print(f"2. Calculation succeeded: {res}")
    except ZeroDivisionError:
        print("2. Caught ZeroDivisionError in except block")
    finally:
        print("3. FINALLY block runs: Releasing resources & flushing logs.")

divide_test(10, 2)
divide_test(10, 0)
► OUTPUT
--- Testing 10 / 2 --- 1. Inside try block 2. Calculation succeeded: 5.0 3. FINALLY block runs: Releasing resources & flushing logs. --- Testing 10 / 0 --- 1. Inside try block 2. Caught ZeroDivisionError in except block 3. FINALLY block runs: Releasing resources & flushing logs.

The Python Exception Hierarchy

👑 Inheritance in Exceptions

All Python exceptions are standard Python classes organized into a strict single-inheritance tree rooted at BaseException. When you write except LookupError, it catches both IndexError and KeyError because they are subclasses of LookupError!

BaseException ├── SystemExit ← Inherits directly; not caught by except Exception ├── KeyboardInterrupt ← Ctrl+C interrupts; not caught by except Exception ├── GeneratorExit └── Exception ← Root for ALL application-level exceptions! ├── ArithmeticError │ ├── ZeroDivisionError │ └── OverflowError ├── LookupError │ ├── IndexError │ └── KeyError ├── ValueError │ └── UnicodeDecodeError ├── TypeError ├── NameError │ └── UnboundLocalError ├── AttributeError ├── OSError │ ├── FileNotFoundError │ ├── FileExistsError │ ├── PermissionError │ └── IsADirectoryError └── RuntimeError └── RecursionError
☝ Why You Should Catch Exception, NOT BaseException

If you write except BaseException:, your program will intercept KeyboardInterrupt (when the user presses Ctrl+C to quit) and SystemExit (when the program calls sys.exit()). This makes your script impossible to terminate from the terminal! Always catch Exception at application boundaries.

The raise Statement

Programmers use the raise statement to trigger an exception intentionally when input or business constraints are violated.

PYTHON: Raising Built-in Exceptions Defensively
def calculate_bank_interest(principal, rate, years):
    if principal <= 0:
        raise ValueError(f"Principal must be strictly positive. Received: {principal}")
    if not (0 <= rate <= 100):
        raise ValueError(f"Rate must be between 0% and 100%. Received: {rate}")
        
    return (principal * rate * years) / 100

try:
    interest = calculate_bank_interest(-5000, 7.5, 2)
except ValueError as err:
    print(f"⚠️ Validation Rejected: {err}")
► OUTPUT
⚠️ Validation Rejected: Principal must be strictly positive. Received: -5000
14

Re-Raising an Exception (Bare raise)

Sometimes an intermediate function needs to log an incident or perform partial recovery, but still wants the exception to propagate to the caller. A bare raise inside an except block re-raises the active exception:

PYTHON: Re-raising Active Exceptions
def authenticate_user(token):
    try:
        if token != "SECRET123":
            raise PermissionError("Invalid authentication token")
    except PermissionError:
        print("[AUDIT LOG]: Unauthorized login attempt detected!")
        raise  # Re-raises the PermissionError without modifying stack trace

try:
    authenticate_user("WRONG")
except PermissionError as e:
    print(f"Caller handled re-raised exception: {e}")
► OUTPUT
[AUDIT LOG]: Unauthorized login attempt detected! Caller handled re-raised exception: Invalid authentication token

Custom Exception Classes

🎯 Defining Domain-Specific Exceptions

In production projects, built-in exceptions like ValueError are often too generic. Creating a custom exception inherits from Exception and gives your domain distinctive identity.

PYTHON: Custom Banking Exception
# 1. Define custom exception class
class InsufficientFundsError(Exception):
    """Raised when a withdrawal exceeds account balance."""
    def __init__(self, balance, amount):
        self.balance = balance
        self.amount = amount
        super().__init__(f"Cannot withdraw ₹{amount}. Current balance is ₹{balance}.")

# 2. Bank account simulation
class BankAccount:
    def __init__(self, initial_balance):
        self.balance = initial_balance

    def withdraw(self, amount):
        if amount > self.balance:
            raise InsufficientFundsError(self.balance, amount)
        self.balance -= amount
        return self.balance

# 3. Usage and handling
account = BankAccount(5000)
try:
    account.withdraw(7500)
except InsufficientFundsError as err:
    print(f"❌ Transaction Declined: {err}")
    print(f"Deficit amount: ₹{err.amount - err.balance}")
► OUTPUT
❌ Transaction Declined: Cannot withdraw ₹7500. Current balance is ₹5000. Deficit amount: ₹2500

Exception Chaining (raise ... from ...)

When translating a low-level exception into a high-level domain exception, use raise NewError(...) from original_error to preserve diagnostic root causes:

PYTHON: Explicit Exception Chaining
class DatabaseConnectionError(Exception):
    """High-level database failure."""

def connect_to_db(port_str):
    try:
        port = int(port_str)
    except ValueError as err:
        # Chain the original ValueError as the direct cause
        raise DatabaseConnectionError("Database port configuration invalid.") from err

try:
    connect_to_db("port_five")
except DatabaseConnectionError as exc:
    print(f"High-level error: {exc}")
    print(f"Original root cause: {type(exc.__cause__).__name__} → {exc.__cause__}")
► OUTPUT
High-level error: Database port configuration invalid. Original root cause: ValueError → invalid literal for int() with base 10: 'port_five'

The assert Statement

🧪 Anatomy of assert

The assert statement tests an internal condition: assert condition, "Error Message". If the condition evaluates to False, Python raises an AssertionError.

PYTHON: Internal Invariant Checking
def calculate_discount(price, discount_rate):
    # Assert internal preconditions for debugging
    assert 0 <= discount_rate <= 1.0, f"Discount rate must be between 0 and 1. Got: {discount_rate}"
    return price * (1 - discount_rate)

print("Valid discount  :", calculate_discount(1000, 0.15))

try:
    calculate_discount(1000, 1.5)  # 150% discount triggers assertion
except AssertionError as e:
    print("Assertion caught:", e)
► OUTPUT
Valid discount : 850.0 Assertion caught: Discount rate must be between 0 and 1. Got: 1.5
⚠️ DANGER: Never Use assert for User Input Validation

Python allows running scripts with optimizations enabled using the -O flag (e.g., python -O app.py). When optimized, Python completely removes all assert statements from bytecode! If you rely on assert to check passwords, input bounds, or permissions, your security checks disappear in production. Always use if not condition: raise ValueError(...).

Safe User Input Loops

Real-world terminal applications should prompt the user repeatedly until a valid value is supplied:

PYTHON: Reliable Input Loop Pattern
def prompt_positive_integer(prompt_text):
    while True:
        raw_val = input(prompt_text).strip()
        try:
            value = int(raw_val)
            if value <= 0:
                print("⚠️ Value must be greater than zero. Try again.")
                continue
            return value
        except ValueError:
            print(f"❌ '{raw_val}' is not a valid whole number. Try again.")

Exception Handling in Functions

🚫 Returning Magic Sentinel Values

Returning -1 or None to indicate failure forces every caller to remember to check if res == -1. If a caller forgets, negative values silently corrupt calculations down the line.

✅ The Pythonic Way: Let Errors Propagate

Raise an explicit exception or allow it to bubble up to the layer that has enough business context to handle it (such as the UI controller or API endpoint).

import json

def load_student_config(filepath):
    try:
        with open(filepath, "r", encoding="utf-8") as f:
            data = json.load(f)

        return data

            print(f"Input '{v}' ≤ 0 rejected. Retrying...")
            continue
        accepted_val = v
        break
    except ValueError:
        print(f"Non-integer '{simulated}' rejected. Retrying...")

print("Finally accepted positive integer:", accepted_val)

🎓 Architecture & Data Pipeline

A resilient data ingestion pipeline that processes raw student marks from CSV, rejects corrupt rows (out-of-range, non-numeric, or missing fields) without crashing, generates an audit text report, and outputs structured metrics to JSON.

PYTHON SCRIPT: main.py
import csv
import json
from pathlib import Path

class InvalidMarkRangeError(Exception):
    """Raised when marks fall outside the legitimate 0-100 score boundary."""

def process_marks_pipeline(csv_input, report_out, json_out):
    csv_path = Path(csv_input)
    report_path = Path(report_out)
    json_path = Path(json_out)
    
    report_path.parent.mkdir(parents=True, exist_ok=True)
    json_path.parent.mkdir(parents=True, exist_ok=True)

    valid_records = []
    rejected_records = []

    try:
        with open(csv_path, "r", newline="", encoding="utf-8") as f:
            reader = csv.DictReader(f)
            if not reader.fieldnames or "marks" not in reader.fieldnames:
                raise KeyError("CSV must contain 'marks' column.")
            
            for line_no, row in enumerate(reader, start=2):
                name = row.get("name", "Unknown")
                raw_mark = row.get("marks", "")
                try:
                    score = float(raw_mark)
                    if not (0.0 <= score <= 100.0):
                        raise InvalidMarkRangeError(f"Score {score} outside [0, 100]")
                    valid_records.append({
                        "roll": row.get("roll_no", "N/A"),
                        "name": name,
                        "marks": score
                    })
                except ValueError:
                    rejected_records.append((line_no, name, f"Non-numeric marks: '{raw_mark}'"))
                except InvalidMarkRangeError as imre:
                    rejected_records.append((line_no, name, str(imre)))
    except FileNotFoundError:
        print(f"❌ Critical: Input file '{csv_input}' not found.")
        return

    if not valid_records:
        print("No valid student marks to process.")
        return

    avg_marks = round(sum(r["marks"] for r in valid_records) / len(valid_records), 2)
    top_scorer = max(valid_records, key=lambda x: x["marks"])

    # 1. Output TXT Audit Report
    with open(report_path, "w", encoding="utf-8") as f:
        f.write("=" * 46 + "\n")
        f.write("        STUDENT MARKS AUDIT REPORT\n")
        f.write("=" * 46 + "\n")
        f.write(f"Valid Records Processed   : {len(valid_records)}\n")
        f.write(f"Rejected Corrupted Records: {len(rejected_records)}\n")
        f.write(f"Batch Average Marks       : {avg_marks}%\n")
        f.write(f"Highest Marks Achieved    : {top_scorer['name']} ({top_scorer['marks']}%)\n")
        f.write("-" * 46 + "\n")
        f.write("ACCEPTED STUDENTS:\n")
        for s in valid_records:
            f.write(f" • [{s['roll']}] {s['name']:<14}: {s['marks']}%\n")
        f.write("-" * 46 + "\n")
        f.write("REJECTED RECORDS (AUDIT LOG):\n")
        for line, s_name, reason in rejected_records:
            f.write(f" • Line {line} ({s_name}): {reason}\n")
        f.write("=" * 46 + "\n")

    # 2. Output Structured JSON Metrics
    payload = {
        "valid_count": len(valid_records),
        "rejected_count": len(rejected_records),
        "average_marks": avg_marks,
        "top_student": top_scorer,
        "accepted": valid_records
    }
    with open(json_path, "w", encoding="utf-8") as f:
        json.dump(payload, f, indent=2)

    print(f"✅ Pipeline complete: {len(valid_records)} accepted, {len(rejected_records)} rejected.")
    print(f"✅ Audit report written to: {report_path.name}")

process_marks_pipeline("data/students_raw.csv", "output/audit_report.txt", "output/summary_metrics.json")

14 Common Mistakes and Best Practices

Common Anti-Pattern Incorrect Code Snippet Refactored Best Practice
1. Bare except: except: pass except ValueError: log.error(...)
2. Catching Exception too early Putting broad except Exception before specific Place specific subclasses (e.g. KeyError) first
3. Silent error swallowing except FileNotFoundError: pass Log the error or assign sensible defaults explicitly
4. Bloated try blocks Wrapping 100 lines of setup and logic in try Wrap only the 1–2 risky lines
5. Exceptions for normal flow Using exceptions as a standard loop break Use standard condition loops: while i < n:
6. Confusing ValueError / TypeError Raising TypeError when value is out of range TypeError = wrong type; ValueError = wrong value
7. Vague error messages raise ValueError("Invalid") raise ValueError(f"Age {a} must be ≥ 0")
8. Losing root cause in re-raise raise CustomError("failed") raise CustomError("failed") from err
9. assert for user validation assert age >= 18 if age < 18: raise ValueError(...)
10. Assuming finally suppresses Expecting unhandled exception not to raise finally executes, then unhandled error raises
11. Ignoring file corruptions Catching FileNotFoundError but not JSONDecodeError Handle both missing file and corrupt content
12. Returning fake success values Returning -1 or None on error Raise meaningful exception or let caller catch
13. Double logging Printing in function and printing again in caller Log once at system boundary or re-raise
14. Mutating during iteration Deleting dict keys inside loop → RuntimeError Iterate over list(d.keys()) copy

8 Debugging Exercises

Analyze each buggy snippet. Expand the accordion to view the diagnosis and solution:

Exercise 1: Why does total = 0; items = ["10", "20", "abc"]; for x in items: total += int(x) crash?

Diagnosis: int("abc") raises a ValueError because "abc" is not an integer string literal.

Correction:

total = 0
for x in ["10", "20", "abc"]:
    try: total += int(x)
    except ValueError: print(f"Skipping non-numeric '{x}'")
print("Total:", total)  # Output: Total: 30
Exercise 2: Identify the bug: data = {"roll": 101}; print("Marks: " + data["marks"])

Diagnosis: Raises KeyError: 'marks' because the key does not exist.

Correction:

data = {"roll": 101}
marks = data.get("marks", "Not Entered")
print("Marks:", marks)
Exercise 3: What is wrong with try: 10/0; except Exception: print("A"); except ZeroDivisionError: print("B")?

Diagnosis: Handler ordering bug. except Exception catches ZeroDivisionError first, making the second handler unreachable dead code.

Correction: Place except ZeroDivisionError: first.

Exercise 4: Why does nums = [1, 2, 3]; print(nums[3]) fail?

Diagnosis: Raises IndexError: list index out of range. In a 3-element list, valid indices are 0, 1, and 2.

Correction: Access nums[2] or check if idx < len(nums):.

Exercise 5: Why does import json; json.loads("{'id': 10}") crash?

Diagnosis: Raises json.JSONDecodeError. JSON specification strictly demands double quotes ("id") for property keys.

Correction: Use json.loads('{"id": 10}').

Exercise 6: Explain the error in def add(a, b): return a + b; add(5, "10").

Diagnosis: Raises TypeError: unsupported operand type(s) for +: 'int' and 'str'.

Correction: Convert add(5, int("10")) before passing.

Exercise 7: Why does open("notes.txt") raise FileNotFoundError even though the file exists?

Diagnosis: The script's Current Working Directory (CWD) does not match the file's folder. Relative paths depend on execution location.

Correction: Use Path(__file__).parent / "notes.txt" for absolute path resolution.

Exercise 8: What is the bug in def test(): count += 1; count = 0; test()?

Diagnosis: Raises UnboundLocalError: local variable 'count' referenced before assignment because assignment makes count local to test().

Correction: Declare global count inside test().

Quick Revision & Master Cheat Sheet

📝 Master Keyword Cheat Sheet
Construct Syntax Primary Purpose
try try: ... Wraps statements that may fail at runtime.
except except Err as e: ... Handles specific exception types when raised.
else else: ... Executes only if the try block raised zero errors.
finally finally: ... Executes unconditionally for resource cleanup.
raise raise ValueError("msg") Explicitly raises an exception object.
Bare raise raise (inside except) Re-raises the currently active exception unchanged.
raise ... from raise E2() from E1 Explicitly chains causes while preserving original traceback.
assert assert cond, "msg" Tests internal preconditions during development/testing.
☝ Top 5 Golden Rules for Exception Handling
  1. Never use bare except: or silently swallow exceptions with pass.
  2. Always place specific exception subclasses before broad parent classes.
  3. Never use assert for critical user authentication or data validation.
  4. Inherit custom exceptions from Exception, never directly from BaseException.
  5. Keep try blocks minimal: wrap only the statements that can genuinely fail.

20 Practice Questions & Detailed Solutions

Test your mastery with these 20 graded questions. Expand each card to verify your answers:

Q1 (Beginner): What is the fundamental difference between a SyntaxError and an Exception?

Answer: A SyntaxError occurs during the parsing phase before the code starts executing; Python cannot even begin running the script. An Exception occurs while the program is actively executing when an operation cannot be completed (e.g., division by zero or a missing file).

Q2 (Beginner): When does the else clause of a try-except statement execute?

Answer: The else clause executes if and only if the try block ran to completion without raising any exceptions.

Q3 (Beginner): Which exception is raised when looking up a nonexistent key in a dictionary using square brackets?

Answer: KeyError.

Q4 (Beginner): What exception occurs when attempting to execute "10" + 5?

Answer: TypeError (unsupported operand type(s) for +: 'str' and 'int').

Q5 (Beginner): Does a finally block execute if a function executes a return statement inside the try block?

Answer: Yes. Python guarantees that the finally block executes before the function actually returns control to the caller.

Q6 (Beginner): Why is writing except: pass considered one of the worst anti-patterns in Python?

Answer: It silently intercepts and swallows every single exception (including syntax errors in callbacks, typos, and memory errors) without logging or reporting, making debugging nearly impossible.

Q7 (Beginner): How do you catch both ValueError and ZeroDivisionError in a single except block? 
except (ValueError, ZeroDivisionError) as err:
    print("Caught:", err)
Q8 (Intermediate): What happens if except Exception is placed before except FileNotFoundError?

Answer: FileNotFoundError is a subclass of Exception. Because Python checks handlers top-down, except Exception intercepts the error first, making the except FileNotFoundError block unreachable dead code.

Q9 (Intermediate): What is the purpose of a bare raise statement inside an except block?

Answer: It re-raises the currently active exception object, allowing the local block to log or clean up while letting the original error propagate up the call stack with its original traceback intact.

Q10 (Intermediate): From which built-in class should custom application exceptions inherit?

Answer: Exception (never BaseException directly, so that system exit signals like KeyboardInterrupt remain unhindered).

Q11 (Intermediate): Why should assert never be used to validate user form inputs in production web apps?

Answer: If Python is executed with the -O (optimization) flag, all assert statements are stripped out of bytecode at compile time, bypassing your validation entirely.

Q12 (Intermediate): What is the difference between IndexError and KeyError?

Answer: IndexError occurs when accessing a sequence (like a list or tuple) using an integer index beyond its length. KeyError occurs when looking up a mapping (like a dictionary) with a key that does not exist.

Q13 (Intermediate): Write a Python snippet that prompts the user for an integer until they provide a valid one. 
while True:
    try:
        val = int(input("Enter number: "))
        break
    except ValueError:
        print("Invalid! Try again.")
Q14 (Intermediate): What does raise NewError() from orig_error do?

Answer: It explicitly chains orig_error as the __cause__ of NewError, preserving full diagnostic context in the traceback.

Q15 (Challenge): Under what rare conditions might a finally block fail to execute?

Answer: If the operating system forcibly terminates the process (e.g. kill -9 / SIGKILL), if the machine loses power, or if code calls os._exit() directly (which bypasses Python runtime cleanup).

Q16 (Challenge): What exception is raised by import json; json.loads('{"val": 01}')?

Answer: json.JSONDecodeError because leading zeros in integer numbers are strictly forbidden by the JSON specification.

Q17 (Challenge): Explain why except BaseException: can make a script impossible to stop with Ctrl+C.

Answer: Pressing Ctrl+C sends KeyboardInterrupt, which inherits directly from BaseException. A bare or BaseException handler catches it and prevents the terminal from terminating the script.

Q18 (Challenge): How can you inspect the original exception that caused a chained exception?

Answer: Access the __cause__ attribute on the caught exception object (e.g. err.__cause__).

Q19 (Challenge): Write a custom exception AgeOutOfRangeError that stores both the entered age and allowed range. 
class AgeOutOfRangeError(Exception):
    def __init__(self, age, min_a=0, max_a=120):
        self.age = age
        super().__init__(f"Age {age} is outside valid bounds [{min_a}, {max_a}].")
Q20 (Challenge): What happens if an exception is raised inside an except block while handling another exception?

Answer: Python initiates implicit exception chaining, outputting a traceback showing: "During handling of the above exception, another exception occurred:", displaying both error traces for debugging.
